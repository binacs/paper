# Deep Speech 2: End-to-End Speech Recognition in English and Mandarin

> **Why it matters:** An early, concrete account of making large-RNN training and serving fast on GPUs: synchronous data parallelism with a hand-written ring all-reduce, a GPU CTC kernel, a preallocating allocator and latency-first request batching.

Version read: arXiv v1 (8 Dec 2015, the only version listed). The ICML 2016 paper is a condensed version; section and table numbers below follow arXiv v1.

## Problem

Deep Speech 2 (DS2) replaces a hand-engineered ASR pipeline with one end-to-end network (spectrogram in, characters out, CTC loss) for English and Mandarin. Progress depended on iterating quickly over large models trained on 11,940 hours of English (Table 9) and 9,400 hours of Mandarin (Sec. 5). The systems problems were to cut training time for each experiment and to serve the model to many users at low latency, which needs a forward-only model and efficient small-batch GPU inference.

## Core design

### Model choices that shape the system (Sec. 3)
- 1–3 convolutional, 1–7 recurrent and fully connected layers with CTC (Sec. 3.1). SortaGrad orders the first epoch's minibatches from shortest to longest utterance (Sec. 3.2–3.3). Length sorting also matters for the GPU CTC kernel (App. A.2).
- Row convolution above the recurrent stack sees a fixed amount of future context, so forward-only RNNs can be deployed (Sec. 3.7).

### Multi-GPU synchronous SGD (Sec. 4.1)
- Data parallelism, one process per GPU, all-reduce of gradients each step. Typical runs use 8 or 16 GPUs with global minibatch 512 or 1024. Weak-scaling runs fix 64 utterances per GPU (Fig. 4).
- Synchronous SGD is chosen over asynchronous parameter servers (Dean et al.) because it is reproducible and deterministic; non-determinism is treated as a sign of a serious bug.

### Custom ring all-reduce (Sec. 4.1, App. A.1)
- Ring algorithm built on MPI send/receive plus CUDA kernels for the element-wise reduction.
- OpenMPI runs with the `smcuda` transport so GPUDirect moves GPU buffers directly, avoiding host copies between GPUs on the same PCI root complex. Several ring segments run concurrently between neighbouring devices to exploit the tree-structured interconnect.
- Node design (A.1, Fig. 8): 2 CPUs and 8 Titan X GPUs, as many GPUs as possible under one root complex (PLX switches), FDR InfiniBand between nodes used mainly for gradients. Datasets are replicated on each node's local RAID-0 disks and cached in 384 GB of host RAM, so the network carries only weight updates and no central file server is needed.

### GPU CTC loss (Sec. 4.2, App. A.2)
- The original CPU CTC (OpenMP) forced softmax outputs and gradients across PCIe, which is costly for Mandarin's roughly 6000-character output (Sec. 3.9).
- One CUDA thread block per utterance. Entries within an alpha/beta column are computed in parallel; columns run sequentially in time.
- Every entry of a column is computed, including invalid ones, which hold garbage or -inf. A log-space sum that drops -inf inputs, plus the element-wise alpha+beta step, cancels them out.
- Gradients for repeated characters use a key-value sort once per utterance and a key-value reduction (ModernGPU) per column. alpha lives in shared memory; only one beta column is kept.
- CPU and GPU results are not bit-identical but train equally well with length-sorted utterances.

### Memory allocation (Sec. 4.3)
- `cudaMalloc` and `std::malloc` caused significant overhead. The replacement is a CPU and GPU allocator modelled on jemalloc's last-level shared allocator with a buddy algorithm. All GPU memory is preallocated at start to avoid fragmentation; CPU blocks go to `mmap` in 12 GB pieces.
- Activations dominate weights, and single allocations can exceed 1 GB for the longest utterances.
- If a request exceeds free GPU memory, the allocator returns page-locked host memory (`cudaMallocHost`), accessed over PCIe at reduced bandwidth, so training keeps making progress after an outlier instead of failing.

### Deployment (Sec. 7)
- **Batch Dispatch (7.1):** user requests are batched on the GPU with an eager policy: each batch runs as soon as the previous one finishes, whether or not more work is waiting. The paper calls this less computationally efficient but best for latency.
- **Small-batch kernels (7.2):** FP16 inference with no measurable accuracy change. Since almost all served batches are tiny, matrix multiply is bandwidth-bound, and custom kernels target that regime.
- **Beam search (7.3):** Mandarin beam search keeps only the fewest characters whose cumulative probability reaches 0.99, capped at 40.
- **Deployed model (7.4):** five forward-only recurrent layers (2560 units), a row convolution with τ = 19, one 2560-unit fully connected layer.

## Limitations

- Inconsistency in the paper: the 98th-percentile latency at 10 streams is 67 ms in Sec. 1 and 70 ms in Sec. 7.1.
- Table 7 reports all-reduce time only. There is no breakdown of communication's share of a step, and no numeric speedup over cuBLAS (Fig. 7 is described only qualitatively in the text).
- The OpenMPI baseline is slower at 128 GPUs than at 64 (Table 7), which suggests it was not tuned for that scale.
- Overlap of communication with computation and reduced-precision gradients are not discussed. (Own analysis) Both became standard levers later.
- Serving numbers come from one low-end GPU at 10–30 concurrent requests. The efficiency cost of eager batching is not quantified, nor is how often the host-memory fallback slows training.

## Relation to other systems

- **Deep Speech 1 (Hannun et al.):** the baseline for the 7x speedup (Abstract).
- **DistBelief-style asynchronous parameter servers (Dean et al.):** cited and rejected for synchronous all-reduce, for determinism.
- **OpenMPI 1.8.5:** kept as the transport (with `smcuda` and GPUDirect), but its all-reduce is replaced (Table 7).
- **cuBLAS 7.0 and Nervana kernels:** small-batch deployment baselines; DS2's kernels outperform both (Fig. 7).

## Takeaways for practice

- Keep training deterministic where you can. DS2 used synchronous SGD so that non-determinism would flag bugs.
- Benchmark the collective on its own. Table 7 shows the largest all-reduce gains inside one node, and topology (GPUs under one root complex, concurrent ring segments) drove the design.
- Once the big kernels are fast, the small CPU-side ops dominate: moving CTC to the GPU removed PCIe round trips and cut 10–20% of training time.
- In GPU kernels, computing all entries and masking invalid ones with -inf can be simpler than computing only valid ones. (Own analysis) It avoids per-element branching.
- Own the allocator: preallocate, use a caching or buddy scheme, size for activations rather than weights, and give outlier inputs a slow path (pinned host memory) instead of a crash.
- Shape the model for serving: row convolution made forward-only RNNs deployable, and the full deployed stack (forward-only, FP16, pruned beam) stayed within 5% relative CER (Sec. 7.4).
- Real serving batches are tiny, so inference is bandwidth-bound. Tune kernels for small N and use reduced precision instead of relying on GEMM libraries tuned for large batches.
- Choose the batching policy on purpose. Eager dispatch minimizes latency at low load and still batches more as load rises.
- Prune the decoder: a cumulative-probability cutoff gave 150x fewer Mandarin LM lookups.
