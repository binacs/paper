# OpenHands: An Open Platform for AI Software Developers as Generalist Agents

> **Why it matters:** It is the reference open-source agent harness that separates an event-stream agent loop from a per-session Docker sandbox driven through a small REST "action execution" server, the split most later agent-sandbox systems follow.

## Problem

Agents that code, run commands and browse need a uniform action format, an execution environment that is realistic (a Linux userland with shell, Python and browser) yet "avoids negative side effects on the users' systems" (§1), a way to compose specialised agents, and reproducible multi-benchmark evaluation. Table 1 positions OpenHands (formerly OpenDevin) as the only framework, versus AutoGPT, LangChain, MetaGPT, AutoGen, SWE-agent and AutoCodeRover, covering sandboxing, browsing, multi-agent collaboration and evaluation together.

## Core design

### Agent abstraction and event stream (§2.1)
- An agent is a `step(state) -> action` function (Fig. 3). **State** centres on the **event stream**, "a chronological collection of past actions and observations" including user instructions and feedback, plus side data: accumulated LLM cost, delegation metadata, execution parameters.
- **Actions** are few and code-shaped, following CodeAct: `CmdRunAction` (bash), `IPythonRunCellAction` (Jupyter cell), `BrowserInteractiveAction` (BrowserGym DSL), plus `MessageAction`, `AgentFinishAction` and `AgentDelegateAction`. The authors argue a programming-language action space subsumes tool-calling: a Python function or REST call is just code run in the sandbox.
- **Observations** report environment changes back into the stream: command output, cell results, browser state and user messages.
- So the event stream is both the agent's memory (its prompt is built from it) and the control-plane log that the UI, evaluation harness and delegation all consume.

### Sandboxed runtime (§2.2, Appendix F)
- **Per-session container.** "OpenHands spins up a securely isolated docker container sandbox" for each task session. Every action from the event stream runs there.
- **Action execution server.** A REST API server runs inside the container. It receives actions, runs them, and returns observations (Appendix F calls this a client-server architecture). It hosts three back-ends:
  - a persistent **bash shell**;
  - a **Jupyter IPython kernel**;
  - **Chromium driven by Playwright**, exposing BrowserGym primitives such as navigate, click, type and scroll. Browser observations include HTML, DOM, the accessibility tree, a screenshot and the open tabs.
- **Workspace.** A user-configured host directory is mounted into the container as the workspace.
- **Arbitrary base images (Appendix F).** OpenHands builds an "OH runtime image" on top of any user image, adding the action-execution client. Each image gets a **hash tag** (MD5 of the build folder: source plus Dockerfile) for reproducibility and a **generic tag** `runtime:oh_v{VERSION}_{BASE_IMAGE}_tag_{IMAGE_TAG}` pointing at the latest build for that base and version. An exact hash match is reused; otherwise the build starts incrementally from the generic image, else from scratch. This layered cache is what makes per-task environments (e.g. one image per SWE-bench repo) cheap to provision.
- **Server-side state.** The server tracks session state (working directory, loaded plugins) inside the container, not in the agent.

### Agent-computer interface: AgentSkills (§2.3, App. I)
- AgentSkills is a Python library auto-imported into the Jupyter kernel. It includes `edit_file` (adapted from SWE-agent and Aider), `scroll_up`/`scroll_down`, `parse_image` (which calls a VLM) and `parse_pdf`.
- A skill is added only if the LLM cannot easily write the code itself, or if the skill calls an external model. Tools are therefore library functions inside the sandbox, not host-side tool endpoints.

### Multi-agent delegation (§2.4) and agent hub (§3)
- `AgentDelegateAction` starts a sub-agent on a subtask. The sub-agent's events go into the same stream, and delegation metadata is kept in State. The canonical example is CodeActAgent handing web work to BrowsingAgent.
- The hub includes:
  - **CodeActAgent**, the default generalist;
  - **BrowsingAgent**, a zero-shot WebArena-style agent;
  - a **GPTSwarm** graph agent;
  - **micro-agents**, which are prompt specialisations of a generalist agent.

### Evaluation framework (§4)
- 15 benchmarks (Table 2) across software (SWE-bench, HumanEvalFix, BIRD, BioCoder, ML-Bench, Gorilla, ToolQA), web (WebArena, MiniWoB++) and misc. (GAIA, GPQA, AgentBench, MINT, EDA, ProofWriter), with no benchmark-specific prompt engineering; the same runtime serves interactive use and evaluation.

## Limitations

- **The security model is thin.** Isolation is a plain Docker container per session (shared host kernel, namespaces/cgroups). The paper does not discuss root vs non-root users, network egress policy, syscall filtering, secrets, resource quotas or kernel-escape risk; Appendix F covers only image building and tagging. "Securely isolated" is asserted, not analysed. The mounted host workspace is a direct write path to the user's machine, and the ethics section (App. B) relies on human oversight rather than technical containment.
- **Provisioning is container-centric.** No account of cold-start latency, warm pools, snapshot/restore, per-host density, parallel evaluation orchestration or per-instance image management, although the hash-tagged layered build is the building block for these. Pausing, migrating or persisting sandboxes across sessions is not discussed.
- **Agent capability.** App. A admits agents "still struggle with complex tasks". Results mix agent versions (v1.5 vs v1.8), and SWE-bench uses only the Lite subset, for cost reasons.

## Relation to other systems

- **SWE-agent (NeurIPS 2024).** Its Agent-Computer Interface is a 100-line windowed viewer, linter-gated edits, terse search and explicit "no output" feedback. OpenHands ports the editor into AgentSkills but embeds it in a general code-action space (bash, IPython, browser) behind a stable runtime API, not a fixed command set. Table 3's 26.0 vs 18.0 on SWE-bench Lite compares different models, so it mixes harness and model effects.
- **Firecracker (NSDI'20) / gVisor.** Firecracker gives each tenant a KVM microVM with its own guest kernel; gVisor interposes a user-space kernel (the Sentry) on syscalls. Both are stronger boundaries than the plain Docker containers OpenHands uses. Because the runtime is just "any image plus an action server over REST", either could replace Docker without touching the agent; the paper does not do this.
- **Kubernetes Agent Sandbox (SIG Apps).** Per its docs, an orchestrator rather than an isolation layer: `Sandbox` (singleton stateful pod, stable identity, persistent storage, pause/resume), `SandboxTemplate`, and `SandboxWarmPool` + `SandboxClaim` for pre-warmed allocation; isolation is delegated to gVisor or Kata via RuntimeClass. It supplies exactly what OpenHands leaves out; the OpenHands action server is the kind of workload that would run inside such a Sandbox.
- **Modal Sandboxes.** Per its docs: containers for untrusted code on gVisor (or a VM runtime with its own kernel), 5-minute default / 24-hour max lifetime plus idle timeouts, pre-built named images, filesystem snapshots and tunnels. It is a managed, multi-tenant version of the same per-task sandbox, with lifecycle and snapshot primitives the paper lacks.

## Takeaways for practice

- Keep the agent loop separate from execution through a narrow, typed **action/observation protocol over the network**. That makes the sandbox backend swappable: local Docker, a remote pool, gVisor, a microVM, or a Kubernetes Sandbox CRD.
- **Treat the event stream as the source of truth.** It serves as prompt memory, as the audit log, and as the replay record for evaluation. Make it append-only and persist it outside the sandbox.
- **Make environment images content-addressed.** Hash-tagging the build context plus incremental rebuilds from a "latest per base" image is a cheap way to provision one image per task or repository at evaluation scale. Pair it with a registry and warm pools to hide cold starts.
- Plain containers are not a security boundary for untrusted, LLM-generated code. Add a stronger runtime (gVisor, Kata or Firecracker), a non-root user, default-deny egress, CPU/memory/PID quotas and scoped credentials, and be cautious about bind-mounting host workspaces.
- Put tools as libraries inside the sandbox (AgentSkills) rather than as host-side endpoints. That reduces host attack surface and keeps actions reproducible.
- Delegation, where sub-agents write into the same stream, cost almost nothing in accuracy on WebArena: 15.3 via delegation vs 15.5 direct (Table 5). A scheduler can therefore treat sub-agents as tasks that share one sandbox, rather than as separate environments.
