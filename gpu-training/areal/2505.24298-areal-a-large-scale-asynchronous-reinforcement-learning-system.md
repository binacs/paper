# AReaL: A Large-Scale Asynchronous Reinforcement Learning System for Language Reasoning

> **Why it matters:** The dominant cost in RL for reasoning LLMs is the batch-synchronous barrier between generation and training, and removing it requires a systems change (interruptible rollout, staleness-bounded admission control) and an algorithm change (a decoupled PPO objective) made together.

## Problem

RL post-training for long-CoT models is inference-heavy serving bolted onto a training job: thousands of responses per iteration, each potentially tens of thousands of tokens, then one gradient update. Standard systems (verl, and AReaL's own synchronous variant) alternate strictly — generate the whole batch, then train on it. Section 2.2 (Fig. 1) separates two costs of that barrier, which have different fixes:

1. **Long-tail generation.** Decode lengths within a batch are heavily skewed and the generation phase cannot end until the longest sequence finishes; everything that finished early idles. The usual mitigation — one- or two-step overlap, training on outputs one or two versions stale — takes *training* off the critical path but still generates each batch from a single model version, so the intra-batch tail is untouched (§1).
2. **Poor scalability of batched decode.** Spreading generation over more devices shrinks the per-GPU decode batch, pushing decoding into the memory-IO-bound regime where extra devices buy little throughput. Hence sublinear scaling: more GPUs help generation only up to a point, and the barrier prevents spending them elsewhere.

No idle fraction is quantified directly; the evidence is end-to-end (§6.2, §6.3).

## Core design

### Four decoupled services (§3.1, Fig. 2)

- **Interruptible rollout worker** — serves `generate` and `update_weights`; the only component holding generation state.
- **Reward service** — scores responses, running unit tests for code. Separate so sandboxed verification (CPU-bound, high-variance) never blocks decode.
- **Trainer workers** — pull from the replay buffer until a full batch exists, run the PPO update, write parameters to distributed storage. Each buffered sample is consumed exactly once.
- **Rollout controller** — control plane: reads prompts, issues `generate`, routes completions to the reward service, writes rewarded trajectories to the buffer, issues `update_weights` after each update.

Rollout workers never stop: no phases, only a continuous generation stream with periodic weight swaps.

### Interruptible rollout (§3.1)

On new weights the worker **interrupts all in-flight generations**, loads the new parameters, **discards the KV cache computed under the old weights**, recomputes it, and resumes decoding the unfinished suffix. The token prefix is kept, so resume costs one prefill, not a re-decode.

The consequence: **a single trajectory contains token spans from several policy versions** — the "inconsistent policy versions" challenge (§3.2), since vanilla PPO assumes one behavior policy. Measured: +12% throughput (1.5B), +17% (7B) on 4 nodes (§6.5).

### Staleness-aware admission control (§4.1)

The controller admits a new generation request only if

```
floor((N_r - 1) / B) <= i + eta
```

with `N_r` the cumulative generated-trajectory count (including the request), `B` the training batch size, `i` the current policy version, `eta` the maximum permitted staleness. Violating requests are rejected, and batches prefer *older* trajectories so the buffer drains oldest-first instead of drifting.

`eta = 0` degenerates exactly to synchronous RL, making `eta` a single freshness/utilization knob. A very small non-zero `eta` can *throttle* generation while a long tail is outstanding, so larger `eta` is recommended for throughput. Settings used: **`eta = 4` for coding, `eta = 8` for math** (§6.1).

### Decoupled PPO objective (§4.2)

Standard PPO uses the sampling policy as both importance-sampling reference and trust-region center. On stale multi-version data those roles conflict: centering the trust region on an old policy drags the current policy backwards. AReaL separates `pi_behav` (what sampled the tokens) from a recent **proximal policy** `pi_prox` (the trust-region center). Eq. 5:

```
J(theta) = E[ sum_t (pi_prox / pi_behav) * min( u_t(theta) * A_t , clip(u_t(theta), 1-eps, 1+eps) * A_t ) ]
u_t(theta) = pi_theta(a_t | s_t) / pi_prox(a_t | s_t)
```

The off-policy correction becomes a per-token reweighting factor and clipping happens around `pi_prox`. In practice `pi_prox` is the parameter set immediately before the current update (not an EMA as in Hilton et al. — too expensive at 32B), with token log-probs recomputed when each global batch arrives: an extra forward pass the system pays for.

**Proposition 1** (§4.2, proved in the appendix) justifies applying this to interrupted trajectories: for a sequence whose contiguous spans came from versions `pi_theta ... pi_theta+k`, there exists a single behavior policy whose samples are distributionally equivalent. The two mechanisms are co-designed, not independent.

### Implementation (§5)

PyTorch on **ReaLHF**; generation **SGLang v0.4.6**, training **Megatron-Core v0.11.0**, scheduling SLURM. Reward computation and TCP transfer run on threads pipelined with generation; rollout workers use asyncio so a slow request does not head-of-line block others. Training uses padding-free packing with dynamic micro-batch allocation (sort descending, pack under a token budget rather than a fixed micro-batch count).

## Limitations

- **The 3:1 inference:training split is static** — hand-tuned, not re-partitionable online. Named as future work; the obvious next scheduling problem.
- **Single-turn tasks only** (AIME24/25, AMC23, MATH-500, LiveCodeBench). Multi-turn and agentic rollouts, where trajectories interleave model output with environment latency, are out of scope and change the interruption semantics.
- **`eta` still needs tuning, and degradation without the decoupled objective is non-monotonic** (23.3 at eta=4 vs. 35.7 at eta=8, Table 2) — not a smooth curve you can reason about.
- **Accuracy is matched, not improved**, and the headline numbers are internally inconsistent. The intro's "improved solution accuracy" is not uniform in Table 1 (1.5B: 42.2 vs. verl 43.1; 32B: 61.0 vs. 61.2 synchronous); 2.77× (abstract/§6.2), 2.57× (§1) and 2.5× (§6.3) measure different things and are never reconciled; "linear scaling to 512 GPUs" appears only in §1. The defensible claim is parity at roughly half the wall-clock.
- **Hidden compute**: recomputing `pi_prox` log-probs per global batch is a full forward pass synchronous PPO does not pay. Weight transport from storage to rollout workers is undescribed (§5), so update latency — which bounds how small `eta` can usefully be — is uncharacterized.

## Relation to other systems

- **HybridFlow / verl** (EuroSys '25, arXiv 2409.19256) — the baseline, already in this repo. Orthogonal and intra-iteration: hybrid single/multi-controller programming model plus 3D-HybridEngine for zero-redundancy actor resharding (1.53×–20.57× over earlier frameworks). It keeps the generate→train barrier, so the long tail remains; Fig. 4 also shows it OOMs at 32k/32B. verl optimizes the phases; AReaL deletes the phase boundary. **OpenRLHF** (arXiv 2405.11143) sits in the same synchronous paradigm — Ray + vLLM + DeepSpeed + HF Transformers, 1.22×–1.68× over prior frameworks — an ergonomics and inference-backend win, with no asynchrony by design.
- **StreamRL** (arXiv 2504.15930) — closest contemporary. Also attacks long-tail skew, but via disaggregated serving: per-stage dedicated resources, disaggregated stream generation to fill pipeline bubbles, an output-length **ranker** to predict long-tail samples, skewness-aware dispatch; up to 2.66× throughput, 1.33× cost-effectiveness cross-DC. StreamRL *predicts and schedules around* the tail; AReaL *preempts* it and absorbs the staleness in the loss.
- **AsyncFlow** (arXiv 2507.01663) — asynchronous streaming post-training with a distributed storage/transfer module, producer–consumer workflow deferring updates within staleness thresholds, engine-agnostic interfaces; 1.59× average. Same staleness-bounded asynchrony, framed as dataflow decoupling rather than a PPO modification.
- **One/two-step overlap schemes** — the state of practice AReaL supersedes (see Problem). **DeepScaleR / DeepCoder** are recipes trained with verl, anchoring Table 1's starred numbers, not systems contributions.

## Takeaways for practice

- **Measure the barrier, not the GPUs.** For long-CoT RL the headline inefficiency is a scheduling artifact (wait-for-longest); measure what fraction of a step sits behind the generation barrier before buying parallelism tricks.
- **Asynchrony is a systems *and* an algorithms change.** Table 2 is the key implementer result: same system, eta=4, 23.3 without the decoupled objective vs. 42.2 with. Build async rollout, keep vanilla PPO/GRPO, and you get the throughput while silently losing the model. Budget for the extra `pi_prox` forward pass.
- **Bound staleness with admission control, not hope.** One integer plus oldest-first batch formation suffices, is trivially instrumented, and collapses to the synchronous system at `eta=0` — an easy migration and an easy A/B.
- **Preemption beats prediction when resume is cheap.** Interruptible rollout works because resuming costs one prefill. If your backend cannot cheaply rebuild KV cache for a partial sequence, StreamRL's length-ranker approach is the alternative.
- **Give verification its own service**, pipelined on CPU threads — sandboxed unit-test execution belongs off the GPU critical path.
- **Expect the static resource split to become the bottleneck.** Making 3:1 elastic per job and per training phase is a cluster-scheduler problem, not an RL one.
