# ZeRO-Offload: Democratizing Billion-Scale Model Training

> **Why it matters:** It shows that the *optimizer* half of mixed-precision training — fp32 states plus the Adam update — can be moved to host CPU and host DRAM at a provably minimal 4M bytes/iteration of PCIe traffic, so a single commodity GPU trains 13B-parameter models without model refactoring.

## Problem

Mixed-precision Adam training keeps fp16 parameters, fp16 gradients, and fp32 parameter/momentum/variance copies, which the paper totals at `16 x M` bytes of *model states* for a model of M parameters (Sec. 2). At that rate the model states alone are 128 GB for Megatron-LM, 176 GB for T5, and 284 GB for Turing-NLG (Sec. 2) — far beyond a single device, so billion-scale training has required multi-GPU (and often multi-node) model or pipeline parallelism, i.e. a cluster and significant model surgery.

Prior scale-up work offloaded *data but not compute*; L2L (layer-to-layer) keeps only the layer in flight on the GPU, swapping tensors synchronously per layer, and the paper's critique is that it "offers limited efficiency due to extra communication overhead, does not offer a way to scale out across devices, and requires model refactoring" (Sec. 2). The stated design goals are efficiency, scalability (work with data parallelism without multiplying CPU memory by the DP degree), and usability (no model code changes) (Sec. 1).

## Core design

### Offload as a graph-partitioning problem (Sec. 3)

ZeRO-Offload models one training iteration as a data-flow graph and treats offloading as a cut on it. Circular nodes are model states (`parameter16`, `gradient16`, `parameter32`, `momentum32`, `variance32`); rectangular nodes are computations (forward, backward, param update); edge weight is bytes moved per iteration — 2M for fp16 producers, 4M for fp32 producers (Sec. 3.1, Fig. 2). Activation checkpointing is assumed so that activations never cross the bus (Fig. 2 caption); activation memory is explicitly out of scope (Sec. 3, footnote 1).

Three constraints then prune the space:

- **Limit CPU compute (Sec. 3.2).** Forward and backward are `O(MB)` in model size M and effective batch B; norm computation and the weight update are `O(M)`. Since the CPU is orders of magnitude slower, any O(MB) node must stay on the GPU — so forward and backward are fused into a single `FWD-BWD Super` node, and only O(M) work is offload-eligible.
- **Minimize CPU–GPU volume (Sec. 3.3).** The graph is a cycle, so any cut crosses at least two edges of at least 2M each: the minimum achievable volume is **4M bytes per iteration**. Splitting the fp32 states from the update node costs at least 6M, so `p32`, `momentum32`, `variance32`, the param update and the fp32→fp16 cast are co-located in one `Update Super` node; separating `p16` from `FWD-BWD` also costs 6M (4M + 2M), so `p16` stays on the GPU. The ordering argument is bandwidth: CPU memory bandwidth is "at least an order of magnitude faster than the PCI-E bandwidth," and GPU memory another order faster than CPU memory (Sec. 3.3).
- **Maximize memory saving among the 4M-volume cuts (Sec. 3.4, Table 1).** Offloading `g16` alone leaves 14M (1.14x); offloading `Update Super` alone gives 4M (4x); offloading both gives the largest reduction (that row of Table 1 extracted inconsistently, so its figures are left out).

The result (Sec. 3.5, Fig. 3): **CPU holds all fp32 model states plus fp16 gradients and runs the parameter update; GPU holds fp16 parameters and runs forward/backward.** The paper claims this is the *unique optimal* strategy — no alternative gives more memory saving without increasing either CPU compute or CPU–GPU volume (Sec. 3, Sec. 3.5).

### Schedules (Sec. 4)

Single GPU (Sec. 4.1, Figs. 3 and 5): forward needs no communication. Gradients go to CPU per-parameter or in small groups as they are produced, so only a small staging buffer lives in GPU memory and each transfer overlaps the remaining backward graph. The CPU then runs Adam on its fp32 states and copies updated fp16 parameters back.

Multi-GPU (Sec. 4.2, Figs. 4 and 5): ZeRO-Offload keeps ZeRO Stage-2 partitioning. Gradients are averaged on the GPU with `reduce-scatter`; each rank offloads only *its* gradient partition and owns the matching CPU-side optimizer-state partition for the whole run; after the CPU update, parameter partitions return to GPU and an `all-gather` completes the step. This is the key scalability property: a single copy of the optimizer states is kept on CPU regardless of data-parallel degree, and the aggregate GPU→CPU volume stays constant as GPUs are added (Sec. 4.2) — whereas naive offload + DP would scale CPU memory with DP degree (Sec. 1). It composes with tensor-slicing model parallelism (Megatron-LM) by offloading the states and update of each MP process.

### Making the CPU side not the bottleneck (Sec. 5)

- **CPU-Adam (Sec. 5.1, Algorithm 1/2):** a hand-written Adam using three levels of parallelism — SIMD vector instructions, loop unrolling, and OpenMP threads — with AVX512 and an auto-tuned `unroll_width` of 8. The fp16 parameter copy back to GPU is tiled (`tile_width`): when a tile completes, `Copy_to_GPU(p16, p32)` fires so the next tile's Adam math overlaps the previous tile's transfer.
- **One-step delayed parameter update, DPU (Sec. 5.2, Fig. 6):** after a warm-up, the CPU update at step i is overlapped with the GPU forward/backward of step i+1, so step i+1 trains on parameters derived from gradients of step i-1. It changes training semantics, so convergence is checked empirically; the paper enables DPU after 40 iterations in both convergence experiments (Sec. 6.2.4).

## Limitations

- **Only model states are offloaded** (Sec. 3, footnote 1). Activation memory is out of scope and must be handled by activation checkpointing, which the design already assumes.
- **DPU changes training semantics.** The paper validates it empirically (GPT-2 pretraining over 100K iterations, BERT-large SQuAD) rather than proving anything; the GPT-2 loss curve with DPU is slightly worse early (around 2K–5K iterations) before catching up (Sec. 6.2.4, Fig. 12).
- **It loses to pure ZeRO-2 at scale.** ZeRO-2 outperforms ZeRO-Offload at 64 and 128 GPUs, where aggregate GPU memory is sufficient and the CPU hop is pure overhead; ZeRO-Offload's win is in the 1–32 GPU range, where ZeRO-2 runs out of memory (Sec. 6.2.3).
- **Host resources are a hidden requirement.** No required CPU DRAM size or core count is stated; the only figures are the DGX-2 testbed spec (1.5 TB DRAM, 32 GBps PCIe), and the analysis assumes that class of host.
- **The optimality claim is scoped.** It assumes whole model states are offloaded — a footnote concedes partial offload could reduce volume further (Sec. 3.3) — and is relative to Adam-style mixed-precision training with activation checkpointing.
- (Own analysis) No NVMe tier, no per-tensor or partial offload ratio, and no automatic decision of *how much* to offload — the strategy is a fixed, statically optimal cut rather than a policy adapting to the ratio of model size to device memory.

## Relation to other systems

- **ZeRO / ZeRO-2 (same group):** ZeRO-Offload inherits Stage-2 gradient + optimizer-state partitioning and reuses `reduce-scatter`/`all-gather`, but adds a host tier so one rank's partition does not have to fit in HBM. Empirically complementary: ZeRO-2 wins at 64–128 GPUs, ZeRO-Offload wins where ZeRO-2 OOMs (Sec. 6.2.3).
- **Megatron-LM:** tensor-slicing model parallelism, used here as a baseline *and* as a composable layer — MP degree 2–8 is what lifts single-node capacity to 70B (Table 3, Sec. 6.2.1).
- **L2L:** the closest capacity-oriented baseline. L2L reaches a larger single-GPU model (17B vs 13B) but needs 28M bytes/iteration vs ZeRO-Offload's 4M, requires model refactoring, and has no scale-out path (Sec. 2, Sec. 6.2.1–6.2.2).
- **PyTorch DDP:** the usability reference point — 1.4B single-GPU ceiling, 30 TFLOPS (Sec. 6.2.1, Sec. 1).
- (Own analysis) **ZeRO-Infinity** later generalizes this tiering to NVMe and to partial/arbitrary offload ratios, which is exactly the "whole-state" restriction this paper's optimality argument carves out. **PyTorch FSDP CPU offload** productizes the same shard-plus-host-optimizer idea inside the framework rather than as a library. Both comparisons are qualitative and are not made by the paper.

## Takeaways for practice

- The graph-cut framing is the reusable artifact: write per-iteration bytes on each edge and the compute class (`O(MB)` vs `O(M)`) on each node, and placement becomes a cut problem with a lower bound instead of a guess.
- Offload the **O(M) optimizer step together with all the states it touches**. Splitting fp32 states from the update is what makes naive offload bandwidth-bound (6M+ instead of 4M, Sec. 3.3).
- Host-side compute must be engineered, not assumed: the stock framework CPU optimizer took 1.39 s against 0.22 s at 1B parameters (Table 4), which would have put the CPU on the critical path.
- Pin one host-side state partition per rank for the whole run; that is what keeps host memory from scaling with DP degree (Sec. 4.2).
- Overlap is where the throughput comes from: per-parameter gradient transfer during backward, tiled parameter copy-back, and optionally the one-step-stale update. Staleness buys 1.12–1.59x but changes semantics — enable it after warm-up and validate on your own task.
- Capacity planning: (Own analysis) a ~4M-bytes/iteration PCIe tax for the largest model-state reduction is the right trade only while aggregate GPU memory binds; past that, a pure sharded data-parallel run is faster (Sec. 6.2.3).
