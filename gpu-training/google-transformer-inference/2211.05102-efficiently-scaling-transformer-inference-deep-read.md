# Efficiently Scaling Transformer Inference

> **Why it matters:** It gives an analytical cost model for choosing how to shard a 500B-class dense Transformer across 64+ accelerators, separately for prefill and decode, and shows that multiquery attention sharded over batch is what makes long-context decoding fit in memory.

## Problem

Decode is a sequential loop of one-token forward passes, while prefill processes all B x L_input tokens in one pass (Sec. 2.2). The paper splits cost into compute, memory time (weights plus KV cache) and chip-to-chip communication. Weight loading and non-attention compute shrink as chips are added. Communication "decreases less quickly (or not at all)" for a fixed layout, so it becomes the bottleneck at scale (Sec. 2.1).

Three regimes pull the design in different directions (Sec. 2.1):
- **Lowest latency:** many chips and small batches, at low MFU.
- **Long context:** a multihead KV cache can exceed the weights and must be reloaded at every step, leaving compute idle.
- **Offline throughput:** large batches to minimize cost per token.

The metric is MFU: observed throughput divided by peak-FLOPS throughput (Sec. 2). Cost is reported as chip-seconds per token (Sec. 4.4).

## Core design

### Notation (Sec. 3.1)
The target is a TPU v4 slice with a 3D torus (X x Y x Z). A subscript marks which mesh axes a tensor dimension is sharded over; for example, BLE_xyz splits E over all three axes. An axis that is not named means the tensor is replicated over it. Partial sums are combined with reduce-scatter and all-gather, and all-to-all moves sharding from one dimension to another.

### Feedforward layouts (Sec. 3.2)
- **1D weight-stationary (Megatron-style baseline):** compute and memory time fall almost linearly with chip count, but communication latency "remains roughly constant independent of the number of chips" (Sec. 3.2.1).
- **2D weight-stationary:** each weight is sharded on both E and F (E_x F_yz). The activation reduction alternates between the d_model and d_ff axes, so no chip needs a fully replicated activation. Communication scales as O(1/sqrt(n_chips)). This beats 1D when sqrt(n_chips) exceeds d_ff/d_model, which means n_chips > 16 when d_ff = 4 d_model (Sec. 3.2.2).
- **Weight-gathered (X, XY, XYZ):** when the activations are larger than the weights, the activations stay put and the weights are all-gathered just before each einsum. Weights are stored in the 2D layout, so one stored layout serves both prefill (gathered) and decode (stationary). Communication grows linearly in BL for weight-stationary layouts but only in sqrt(BL) for weight-gathered ones, so weight-gathered wins once there are enough tokens per batch (Sec. 3.2.3, Fig. 3).

### Multiquery attention placement (Sec. 3.3)
Multiquery attention shares one K/V head across all query heads, which shrinks the KV cache by a factor of n_heads. Sharding it by heads forces K/V to be replicated on every chip and loses that saving. The paper instead shards Q/K/V over **batch** during decode. This cuts per-chip KV loading by a factor of n_chips, at the cost of one all-to-all on the small per-step tensors. The text says prefill uses head sharding, because the KV load there is spread over many query tokens.

### Parallel attention/FFN block (Sec. 3.4)
Attention and the FFN read the same layernormed input, and their outputs are summed. This saves one layernorm per layer, allows fused input and output projections (larger matmuls), and removes one of the two all-reduces per layer.

### Low-level work (Sec. 3.5–3.6)
- **Looped CollectiveEinsum:** overlaps collectives with matmuls. The reduce-scatter goes into the hidden dimension rather than batch or sequence, which exposes more overlap.
- **Kernels:** faster top-k/top-p sampling, Softmax and Swish.
- **Incremental prefill.**
- **int8 weight-only quantization (AQT):** activations are not quantized.

### Resulting policy (Sec. 4.1)
During prefill, choose weight-stationary or weight-gathered based on the number of tokens in the batch. During decode, always use 2D weight-stationary. The implementation uses JAX/XLA and was originally based on T5X (Sec. 4).

## Limitations

- **Hardware scope:** the paper covers only TPU v4 3D-torus hardware and dense, decoder-only models. The authors claim the methods generalize to NVLink topologies but do not show it (Sec. 7).
- **Static batches (Own analysis):** each run uses a fixed batch with fixed lengths (context 2048, 64 output tokens). There is no arrival process, no continuous batching, no queueing or SLO analysis, and no variable output lengths.
- **KV cache as a fixed reservation:** the cache gets a fixed share of memory (30% in Table 1), with no paging, prefix sharing or eviction.
- **Prefill/decode split not evaluated:** pairing batch-1 prefill with batch-64 decode relies on sampling several outputs per input or on pipelining separate prefill and decode servers (Sec. 4.4). No such serving system is evaluated.
- **Weight-only quantization:** int8 applies to weights only (Sec. 3.6).
- **Cross-hardware comparison:** the FasterTransformer results run on A100s and these on TPU v4, so the paper compares MFU rather than wall-clock time per dollar (Sec. 5).
- **Stated limit:** the authors say FLOPs and communication volume fundamentally limit dense inference, and they name MoE sparsity, adaptive computation and communication compression as future directions (Sec. 7).

## Relation to other systems

- **Megatron / NeMo Megatron:** its 1D tensor parallelism is the paper's baseline. This paper adds 2D sharding and weight-gathered prefill, and reduce-scatters into the hidden dimension rather than sequence, unlike Korthikanti et al. (Sec. 3.2.1, 3.5).
- **FasterTransformer:** combines tensor and pipeline parallelism on GPUs. The paper reports higher MFU at 64-way than FT reaches at 32-way, and attributes the gap to a communication bottleneck in FT (Sec. 5).
- **DeepSpeed Inference:** uses ZeRO offload to CPU/NVMe. This paper stays in HBM and scales out instead (Sec. 6).
- **GSPMD / Alpa:** general automatic partitioners (Alpa uses ILP search). This paper hand-derives inference layouts from an analytical model (Sec. 6).
- **vLLM (Own analysis):** handles KV-cache memory management and dynamic batching, which this paper does not. The two are complementary: this paper decides how to shard the model, and vLLM manages the cache.
- **DistServe / Sarathi-Serve (Own analysis):** DistServe turns the separate prefill and decode servers hinted at in Sec. 4.4 into an SLO-aware system. Sarathi-Serve instead co-schedules chunked prefill with decode. Both build on the observation that prefill and decode want different batch sizes and layouts.

## Takeaways for practice

- **Plan prefill and decode separately:** decode wants a weight-stationary layout that minimizes latency, and large-token prefill wants a weight-gathered layout that maximizes MFU. A 2D stored layout lets both share the same resident weights.
- **Model communication explicitly:** 1D tensor parallelism stops reducing latency once communication dominates, and 2D sharding pays off past about 16 chips (with d_ff = 4 d_model).
- **Do not replicate the multiquery KV cache:** multiquery attention (and, by extension, grouped-query attention) only saves memory if the cache is not replicated, so shard it over batch during decode. This is a placement decision for the partitioner or scheduler.
- **Price latency tiers separately:** small-batch, low-latency serving runs at low MFU (14% for 540B decode in Table 2), and cost tracks parameter count only above roughly batch 512 (Sec. 4.4).
- **Use weight-only int8 for latency-bound decode:** Sec. 4.4 reports a cost improvement of "just over a factor of 2" at low latency targets.
- **Compare configurations in chip-seconds per token:** use it as the cost metric across chip counts and batch sizes, and sweep (chips, batch, layout) to find the Pareto frontier.
