# DynamoLLM: Designing LLM Inference Clusters for Performance and Energy Efficiency

> **Why it matters:** It treats instance count, tensor parallelism and GPU frequency as three energy knobs that live on different timescales, and it shows that one controller per timescale can cut serving energy by about a third to a half on production-like traces while keeping P99 latency within SLO.

## Problem

LLM fleets are usually provisioned for peak load at one setting: TP8 at the top clock (1980 MHz on H100). The paper's characterisation on a DGX H100 with vLLM and Azure Coding/Conversation traces (§III) shows why this wastes energy.

- **Heterogeneity (§III-A, Tables I–III).** Requests fall into nine buckets, short/medium/long input × output (Table IV), each with its own energy-optimal configuration. For Llama2-70B at medium load, short-short requests are cheapest at TP2, 1.2 GHz; long-long requests need TP8 and are best at 1.6 GHz (Table I). The optimum also moves with load (Table II: TP4 at 1.2 GHz when low, 2 GHz when high), model size (Table III: Falcon-180B needs TP8) and SLO slack (10× vs 5×).
- **Dynamism (§III-B, Figs. 1–2).** The length mix drifts and load is diurnal: Coding peaks at 2.8× its average and 34.6× its valley.
- **Switching costs (§III-C).** A new 8×H100 instance takes ~6–8 min (Table V). Naive re-sharding costs ~1–2 min on the critical path. A frequency change costs 50–80 ms against a 20–30 ms decode iteration (Fig. 3).

## Core design

### Request pools and profiles (§IV-A, §IV-D)
- Requests go to per-type **pools** (nine by default). Input length is known on arrival; output length is predicted as short/medium/long by a BERT-based proxy. An overloaded pool spills to the next-larger one.
- **Offline profiles.** Per model: energy, TTFT and TBT over TP2/4/8, 800–1980 MHz in 200 MHz steps, a few load levels and each request type, interpolated with SciPy `interp1d`. Profiles are stored globally and cached per cluster.
- **Optimisation (Eq. 1).** Per pool, minimise Σ over TP ∈ {2,4,8} of instance count × energy per instance at (load, frequency), subject to a GPU budget, total load and per-instance SLO. Solving this MILP (PuLP) takes ~100 ms or more, too slow for fine-grained control, so it is decomposed.

### Hierarchical controllers (§IV-B, Fig. 4)
Each level sets one knob, assumes the levels below run at maximum performance, and passes its result down as a constraint.

| Controller | Knob | Epoch | Decision |
|---|---|---|---|
| Cluster manager | Instances per pool (scale out/in) | ~30 min | Forecast peak load per type from weekly load templates. Divide by per-instance capacity, assuming TP8 at 1980 MHz. |
| Pool manager | TP degree (shard up/down) | ~5 min | Split the pool's GPUs into TP2/TP4/TP8 instances by Eq. 1 with frequency fixed at maximum. Route each request to the lowest-energy instance that meets its SLO. |
| Instance manager | GPU frequency | ~5 s | Drop frequencies that would break the SLO at the current load. Pick the lowest-energy frequency left. |

- **Fragmentation.** Each pool gets one instance fewer than its peak need and spills the rest upward, so only the largest pool is over-provisioned.
- **Overhead table.** A controller reconfigures only if projected savings exceed the recorded transition cost; reconfigurations are staggered so some instances keep serving.
- **Misprediction (§IV-D).** On a growing queue the instance manager reorders by deadline, raises the clock to maximum, has the pool manager move unstarted requests, and as a last resort drops long-waiting requests for client retry.

### Making reconfiguration cheap (§IV-C)
- **Scale-out.** Cluster-local weight caches, VM snapshots with the engine pre-initialised, and background VM creation ahead of the next epoch from the forecast take the 6–8 min off the critical path.
- **Re-sharding.** The TP change is a bipartite matching between current and target GPUs; maximum-weight matching keeps as many shards in place as possible, and the rest move GPU-to-GPU over NVLink in parallel. With T = time to move 1/8 of the model (~50 ms for Llama2-70B), transitions cost 0–4T (Table VI, Fig. 5), e.g. TP4→TP8 ≈ T, TP4→TP2 ≈ 2T. The old instance serves meanwhile only if both copies fit in memory (not for 70B at TP2/TP4). KV-cache migration is not described.
- **Frequency.** nvidia-smi is kept resident and the controller runs privileged to cut call overhead; the 5 s epoch avoids per-iteration switching (Fig. 3).

Implementation (§IV-E): on vLLM, with gRPC controllers; cluster and pool managers in a dedicated VM, instance managers beside each engine.

## Limitations

- **Measured vs modelled.** The 35% and 42% results are real-cluster runs, but the power-measurement method is not described; week-long energy, carbon and cost come from a simulator with no reported validation.
- **One model.** Results are for Llama2-70B; other models are said to "follow the same trends" without data.
- **Savings shrink at high load** (23.4%): the method harvests over-provisioning and off-peak slack.
- **SLO accounting.** Median latency rises, there is no SLO-attainment metric, and the fallback drops requests.
- **Scope.** Three-class output prediction; co-located prefill/decode on homogeneous H100s; no KV-cache migration. The TensorRT-LLM port is claimed, not evaluated, and no code is released.

## Relation to other systems

- **Splitwise (ISCA 2024).** Same Microsoft group, and DynamoLLM's 1 h traces come from it. Splitwise splits prompt and token phases onto separately provisioned machines, possibly different hardware, and reports 1.4× throughput at 20% lower cost, or 2.35× throughput at the same cost and power. It is a static design-time choice of hardware per phase. DynamoLLM keeps the phases co-located and instead tunes TP and clock at runtime per request class. The two approaches are complementary.
- **DistServe (OSDI 2024).** Also disaggregates prefill and decode. It picks parallelism and placement per phase to maximise goodput under TTFT/TPOT SLOs, with up to 7.4× more requests or 12.6× tighter SLOs. Its objective is goodput per GPU, and its parallelism is chosen offline for a given workload. DynamoLLM's objective is energy, and it re-chooses parallelism every ~5 minutes as load shifts.
- **Llumnix (OSDI 2024).** Live-migrates requests and their in-memory state across instances for load balancing, de-fragmentation and priorities. It reports about 10× better tail latency and up to 36% cost savings. Llumnix moves requests between fixed instances, while DynamoLLM reshapes the instances themselves (TP degree, clock). Llumnix-style migration is exactly what DynamoLLM lacks when its old instance must stop during re-sharding.
- **Thunderbolt (OSDI 2020, Google).** A fleet power-capping system. It throttles throughput-oriented batch tasks through Linux CPU bandwidth control, using a two-threshold policy with randomised unthrottling. This enables 9–25% power oversubscription while protecting co-located serving. It is a reactive safety mechanism for CPU fleets; DynamoLLM proactively minimises energy for latency-bound GPU serving and cites it only as background.

## Takeaways for practice

- Give each knob a loop at its own timescale (capacity ~30 min, TP ~5 min, DVFS ~5 s) and pass constraints down, rather than solving one joint MILP online.
- GPU frequency is the strongest single knob (19% alone, Fig. 6): expose it to the serving layer, keep the control path hot, never switch per iteration.
- Keeping weights in place (matching + NVLink peer copies) turns re-sharding from minutes into milliseconds; budget memory headroom so the old instance keeps serving.
- Per-class pools pay off only with reconfiguration: static pools cost 20% more energy (Fig. 6), and too many pools fragment capacity (Fig. 13).
- For energy results, separate measured from simulated numbers and check P50 as well as P99.
