# MegaScale-Infer: Efficient Mixture-of-Experts Model Serving with Disaggregated Expert Parallelism

> **Why it matters:** It takes disaggregation one level below prefill/decode. Each MoE layer of the decode phase is split into attention nodes and expert nodes that scale independently and can run on different GPU types. The paper shows that the split only pays off with a micro-batch pipeline and an RDMA-native M2N transport to replace NCCL.

## Problem

During decoding, attention is memory-bound. Each request reads its own KV cache, so a bigger batch does not raise attention's arithmetic intensity. Dense FFNs are compute-bound once the batch is big enough. MoE breaks that, because every expert sees only a fraction of the batch. The paper's roofline example (§2.3) uses Mixtral 8x22B on A100. The FFN needs about 156 tokens per batch to become compute-bound. With top-2 of 8 experts, each expert gets only about 39 tokens, so theoretical FFN MFU is only about 25%. Raising the batch to fix this is limited by the TPOT SLO and by KV-cache memory on the same GPUs. When attention and experts share a GPU, as in standard EP/TP serving, both run at the same batch, and the experts stay underutilized.

## Core design

**Disaggregated expert parallelism (§3).** Prefill and decode already run on separate clusters, following DistServe- and Splitwise-style prior work. The paper covers only the decode cluster, which it splits again:
- *Attention nodes* replicate the QKV and output projection weights, hold the KV cache, and run data-parallel. Tensor parallelism stays inside a node, on NVLink.
- *Expert nodes* each hold one expert, using 1 to 8 GPUs in one server with TP inside. Together they form the EP group.
- Gating and top-k run on the attention side. A fused kernel covers gating, top-k, per-expert token counts, weight normalization and the token scatter (§6). Tokens then go to the expert nodes over M2N and come back over N2M.
- Many attention replicas feed each expert, so the expert batch is the sum over all replicas. Expert GEMMs become dense enough to be efficient while each attention replica keeps a batch that fits its memory and SLO.

**Ping-pong pipeline (§4.1).** Without a pipeline, attention nodes sit idle while experts compute, and the reverse. The global batch is cut into *m* micro-batches that shuttle between the two node pools, with two exchanges per MoE layer. Let T_a and T_e be the per-micro-batch compute times, T_f = max(T_a, T_e), and T_c the one-way communication time. Full overlap needs three conditions:
1. T_a ≈ T_e (balanced pools);
2. T_c < T_f (communication shorter than compute);
3. m·T_f ≥ 2·(T_f + T_c). This gives **m ≥ 2(1 + T_c/T_f)**, so m ≥ 3 when T_c < T_f/2 and m ≥ 4 otherwise.

Iteration latency is T_total = (T_a + T_e + 2T_c) + T_f(mL − 1) (Eq. 5). More micro-batches hide more communication but cut the per-expert GEMM size. The search therefore caps m at N_m = 4 (§4.2).

**Deployment-plan search (§4.2, Algorithm 1).** The search enumerates attention TP size, expert TP size, the number of attention nodes n_a, and m. For each combination it binary-searches the largest global batch B that meets the SLO, then keeps the plan with the best throughput per dollar: (B/T_total) / (tp_a·n_a·Cost_a + tp_e·E·Cost_e). The performance model is linear and fitted from profiles (T_a = k1·b_a + k2, T_e = k3·b_e + k4). Balancing the two gives n_a = k1·E/(k3·K). T_c comes from profiled bandwidth utilization. The plan must also satisfy a KV-cache memory constraint (Eq. 8). The search costs O(M²·N_m).

**Heterogeneous hardware (§4.3).** The attention pool should get GPUs with the most memory bandwidth and capacity per dollar. The expert pool should get GPUs with the most FLOPS per dollar. Table 3 normalizes prices to L20 = 1.00. On that scale, H20 gives 2214 GB/s and 80 TFLOPS per unit cost, and L40S gives 800 GB/s and 335 TFLOPS. The paper therefore uses H20 for attention and L40S for experts. The text says GPU types are enumerated per role. Algorithm 1 as printed searches only TP sizes, node counts and m.

**M2N communication library (§5).** The paper finds three problems with NCCL for this pattern: GPU-to-CPU copies on the path, group-setup overhead, and grouped P2P operations limited to 8 at a time. It also relies on GPU synchronization. In a 1-to-N microbenchmark (Fig. 5), NCCL's median latency sits well above raw perftest, and its P99 latency jumps at 32 receivers. M2N replaces this as follows:
- The sender writes pre-registered GPU tensors directly with RDMA write-with-immediate and polls the completion queue. There is no GPU sync, no host copy and no group initialization.
- The receiver polls the CQ, flushes with GDRCopy, and sets a shared flag that the next kernel waits on.
- In the network, ACKs go to a high-priority queue, and congestion control is tuned for the unbalanced many-to-few traffic.
- It is built as a PyTorch extension of about 4.9k lines of C/C++ and 5k lines of Python, on GPUDirect and GDRCopy (§6).

**Expert load imbalance (§6).** Popular experts get on-device redundant replicas. A greedy placement minimizes the maximum per-node load, using traffic from the previous time window. The paper reports no measurements for this mechanism.

## Limitations

- **Decode only.** Prefill is handed off to a separate cluster, and the paper gives no design for it. There is also no end-to-end TTFT/TPOT study across both phases.
- **Throughput-oriented evaluation.** Results are throughput at one fixed 150 ms TPOT bound, with no latency distributions, SLO sweep or goodput metric.
- **Older baselines.** The baselines are vLLM 0.6.6 and TRT-LLM 0.15. There is no comparison with DeepSeek-style large-EP serving (attention DP plus expert EP without physical separation).
- **Strong assumptions.** The pipeline needs T_c < T_f and balanced pools. The plan is fitted from offline profiles. The paper does not show how it rebalances when context lengths change (attention time grows with KV length) or when expert popularity drifts.
- **Expert imbalance and fault tolerance.** Expert imbalance gets one paragraph of design and no data. Fault tolerance is not discussed, yet a failed expert node stalls every attention replica that feeds it.
- **N2M direction.** The expert-to-attention return path is mentioned but not separately designed or measured.
- **Fabric.** The testbeds have 2 to 8 RDMA NICs per node, and the paper credits this bandwidth for m > 3 adding little. Weaker fabrics would need larger m, at a cost in GEMM efficiency.
- **No code.** No official implementation is released.

## Relation to other systems

- **DistServe (OSDI 2024):** Disaggregates prefill and decode onto different GPUs and searches per-phase parallelism against TTFT/TPOT goodput. MegaScale-Infer applies the same "split by resource profile, then search the plan" method one level down, inside the decode phase and per layer. It moves activations every layer, where DistServe moves the KV cache once per request.
- **Splitwise (ISCA 2024):** Splits the compute-heavy prompt phase from the memory-heavy token phase and provisions each separately, including cheaper hardware for token generation, judged on throughput, cost and power. MegaScale-Infer makes the same hardware-matching argument for attention (bandwidth-bound) versus experts (compute-bound).
- **Mooncake (FAST 2025):** Builds prefill/decode disaggregation around a pooled CPU-DRAM-SSD KV-cache store and a cache-aware scheduler with early rejection. Its focus is KV-cache capacity and reuse. MegaScale-Infer does not address the KV cache across requests, and the two designs are complementary.
- **DeepSeek-V3 serving (arXiv 2412.19437, §3.4):** Decode runs on 40 nodes / 320 GPUs. Attention uses TP4 with SP and DP80. Experts use EP320 with one expert per GPU, and 64 GPUs hold redundant and shared experts. Two micro-batches overlap one's attention with the other's dispatch, MoE and combine. Attention and experts share the same GPUs, so this is logical but not physical disaggregation, with the same hardware for both. MegaScale-Infer separates the pools physically, allows heterogeneous GPUs, and derives the micro-batch count instead of fixing it at two.
- **MegaScale (NSDI 2024):** ByteDance's training stack for more than 10,000 GPUs, reaching 55.2% MFU on 12,288 GPUs with compute-communication overlap and fault diagnosis. MegaScale-Infer carries the overlap-first, custom-network-tuning approach over to inference. It does not inherit MegaScale's robustness tooling, which the paper does not discuss.

## Takeaways for practice

- In MoE decoding, the expert batch is set by the attention fan-in, not by the per-GPU batch. Separating the pools lets each scale on its own axis: memory and KV for attention, FLOPS for experts.
- Size micro-batches from measured T_c/T_f: m ≥ 2(1 + T_c/T_f), usually 3 or 4. Going higher costs GEMM efficiency. Keep the cluster's communication-to-compute ratio below 1, or the pipeline cannot hide it.
- A scheduler needs a cost-aware placement solver that picks GPU type per role, plus TP sizes, the attention replica count and the batch, under SLO and memory constraints. A linear profile model is enough to drive the search.
- For latency-critical, many-to-many traffic with small messages (around 100 to 300 KB), collective libraries can be the bottleneck. Direct RDMA write-with-immediate, CQ polling and GDRCopy-based signaling, with high-priority ACKs and tuned congestion control, remove most of the tail latency.
- Heterogeneous fleets are an asset in serving. Bandwidth-rich, compute-poor inference GPUs (such as H20) fit attention, and compute-dense PCIe GPUs (such as L40S) fit experts. Placement has to treat GPU type as a decision variable.
- Plan for what the paper leaves open: expert-node failures, expert popularity drift, and rebalancing as context lengths change.
