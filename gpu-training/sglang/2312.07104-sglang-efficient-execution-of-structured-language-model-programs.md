# SGLang: Efficient Execution of Structured Language Model Programs

> **Why it matters:** It made the KV cache a first-class, tree-indexed LRU cache shared across requests and calls (RadixAttention), and showed that scheduling for cache hits, not just for batch fill, is the main lever for multi-call LLM workloads such as agents, few-shot evaluation, tree search and RAG.

Numbers and section references below are from arXiv v2 (6 Jun 2024), the latest arXiv version. The v2 PDF still carries a "Preprint. Under review" line; the NeurIPS 2024 proceedings version was not compared line by line.

## Problem

LLM applications increasingly run as *programs*: many calls per task, with shared few-shot prefixes, forked branches, multi-turn histories, tool loops and constrained (JSON/regex) outputs. Engines of the time treat each call independently. They drop the KV cache when a request finishes, so shared prefixes are prefilled again. They decode constrained output one token per forward pass even when the grammar forces several tokens. Black-box API calls each pay full input-token cost. SGLang pairs a Python-embedded frontend (`gen`, `select`, `extend`, `fork`, `join`) with a runtime that exploits the exposed structure. This note focuses on the runtime.

## Core design

### RadixAttention (Sec. 3)

- **Data structure.** A CPU-side radix tree with multi-token edge labels maps token sequences to KV tensors. The KV tensors sit on the GPU in a paged layout with a page size of **one token**, so any prefix boundary can be shared without copying.
- **Single memory pool.** Idle cached tokens and running requests share one pool. When the queue is long, cached tokens are evicted to admit a larger batch, so the cache costs nothing when live work needs the memory.
- **Eviction and ref counts.** LRU over leaves; a shared ancestor becomes evictable only once it is a leaf. Nodes used by the running batch have a non-zero ref count and are protected.
- **Multimodal.** Images are hashed so image tokens share the same tree (Sec. 6.2).

### Cache-aware scheduling (Sec. 3, Alg. 1, App. A.3)

- Metric: hit rate = cached prompt tokens / total prompt tokens.
- Each continuous-batching step matches waiting requests against the tree and sorts them by **longest matched prefix first**, not FCFS. Requests are admitted while evictable cache plus free memory covers them; their prefix nodes' ref counts are incremented; eviction runs on allocation failure.
- **Theorem 3.1.** Offline, DFS order over the requests' radix tree gives the optimal hit rate if the cache holds at least the longest request; longest-prefix-first equals DFS. Proof idea: each edge's KV is computed exactly once. Online arrivals and unknown output lengths make the policy approximate.
- **Known weakness.** Greedy prefix-first ordering can starve requests; fair scheduling is left to future work (Sec. 3, Sec. 8).

### Frontend hints and distribution (Sec. 3, App. A.4)

- On `fork`, the frontend sends the shared prefix first as a hint, then the branches. Removing hints or frontend parallelism hurts in the ablation (Fig. 8c).
- **Tensor parallelism:** each GPU holds a sharded KV cache; tree operations are unchanged, with no extra synchronization.
- **Data parallelism:** each worker keeps a sub-tree; a router keeps a *meta-tree* of all of them and dispatches by prefix affinity. Workers report evictions through a queue drained when the router is idle. Four-worker MMLU scaled linearly; the locality vs. load-balance trade-off is left open.

### Compressed FSM for constrained decoding (Sec. 4, App. B)

- A regex (e.g. a JSON schema) becomes an FSM; prior systems mask logits and decode one token per step.
- SGLang builds the FSM over characters/strings and merges chains of single-successor transitions into one **compressed edge**, appended in one forward pass (Figs. 10–11). The preprocessed FSM is reused across requests.
- **Retokenization (B.2):** prior text plus the forced string is retokenized so boundaries match the tokenizer; overhead is reported as minor.
- **Caveat (B.3):** forced strings can distort probabilities (e.g. "A" pushed toward "Above Average" when a letter grade was meant). Listing choices in the prompt mitigates but does not fix it.

### API speculative execution (Sec. 5)

For black-box endpoints, the first `gen` in a chain runs a few tokens past its stop condition. The interpreter matches the overflow against later primitives; if the model followed the template, later calls are served from the buffer, saving their latency and repeated input tokens.

## Limitations

- **Starvation** under greedy longest-prefix-first scheduling. This is acknowledged and left open (Sec. 3, Sec. 8).
- **GPU-only cache.** Extending the tree to DRAM and disk is listed as future work (Sec. 8). Later systems such as Mooncake built exactly this tier.
- **Exact-prefix matching only.** Fuzzy or semantic matching is future work. Non-prefix reuse (for example RAG chunks in a different order) gets no hits.
- **Probability distortion** from compressed FSM jumps (App. B.3). Compiler mode cannot trace data-dependent control flow.
- **Data-parallel locality vs. load balance** is not solved. The router evaluation is a four-worker MMLU run (App. A.4).
- *Own analysis:* the vLLM baseline is v0.2.5, chosen because later vLLM partly integrated RadixAttention (Sec. 6.1 footnote). The headline 6.4× is therefore against an engine without automatic prefix caching, and the gap to current engines is smaller. Most results are on 24 GB A10Gs, where freed KV memory translates strongly into batch size.
- *Own analysis:* the evaluation optimizes throughput and per-program latency, not tail-latency SLOs under mixed tenants; the interaction between prefix-affinity and SLO-aware scheduling is not evaluated.

## Relation to other systems

- **vLLM / PagedAttention (SOSP 2023).** Its abstract frames KV memory as OS-style paging to cut fragmentation, enable sharing within and across requests, and get 2–4× throughput over FasterTransformer and Orca. SGLang keeps paged storage (page = 1 token) but adds what PagedAttention lacks: cross-request retention after completion, a radix index for automatic multi-level prefix discovery, LRU eviction, and a scheduler that orders by hits.
- **Orca (OSDI 2022).** Its abstract introduces iteration-level scheduling and selective batching (36.9× throughput over FasterTransformer on GPT-3 175B). SGLang assumes this continuous-batching loop (Alg. 1) and changes *which* waiting requests enter each iteration.
- **Sarathi-Serve (OSDI 2024).** Its abstract targets the throughput–latency trade-off with chunked prefills and stall-free batching (up to 2.6×/3.7×/5.6× serving capacity over vLLM under tail-latency SLOs). Orthogonal: Sarathi makes remaining prefill cheaper to interleave; RadixAttention removes prefill already computed. Their objectives (SLO vs. hit rate) must be reconciled in practice.
- **Mooncake (FAST 2025).** Its abstract describes Kimi's KVCache-centric disaggregated architecture: separate prefill and decode clusters, and a KV cache pooled across CPU, DRAM, SSD and NIC resources, with 59%–498% higher effective capacity on traces. It realizes SGLang's "multi-tier RadixAttention" future direction at cluster scale, and adds SLO-aware scheduling and overload rejection.
- **Prefix-caching approaches.** *Prompt Cache* (arXiv 2311.04934) reuses attention states for user-declared, schema-defined prompt modules, including non-prefix ones, and reports about 8× GPU TTFT reduction. SGLang argues that this kind of non-prefix reuse can cost accuracy (up to 43%, per SGLang Sec. 7). *ChunkAttention* (arXiv 2402.15220) shares prefix KV chunks in a prefix tree with a specialized kernel (3.2–4.8× faster attention for 1–4K shared system prompts), but its abstract describes no LRU cache policy or cache-aware scheduler.

## Takeaways for practice

- Treat KV as an indexed cache with eviction and admission policy, in one pool with live work, rather than per-request scratch memory.
- Admission order is a locality decision: longest-prefix-first is optimal offline; add aging or a fairness bound against starvation.
- With data parallelism, route by prefix affinity, or hit rates fall as replicas duplicate prefixes.
- Pass program structure (fork points, shared prefixes) from SDK to server; cheap hints raise hit rate.
- Precompile grammars per schema and jump over forced spans, watching tokenization and probability artifacts.
- Measure hit rate in production: Chatbot Arena saw 52%–74%.
