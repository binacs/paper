# Robust LLM Training Infrastructure at ByteDance

> **Why it matters:** ByteRobust treats LLM-training reliability as one control loop: detect, localise, evict, restart, checkpoint. It backs the design with a fault census from about 778k production jobs, which makes it a reference design for fault tolerance at the 10k-GPU scale.

## Problem

At about 10k GPUs, failures are routine. The paper cites Llama 3's figure of one interruption every 2.78 hours. Failover at this scale often takes more than 10 minutes (Sec. 2.3).

Two kinds of incident make this worse:

- **Implicit failures** (hangs, MFU decline, NaN loss) leave no log line to act on. Diagnosing them by hand takes hours: one communication hang took over 1.5 h and one silent data corruption (SDC) case took over 8 h (Sec. 2.2).
- **Manual restarts** for code or data changes are frequent.

The paper's goal is to maximise effective training time ratio (ETTR) without depending on mature vendor diagnostics.

## Core design

The system has two parts (Sec. 3, Sec. 7):

- A control plane outside the job:
  - the Robust Controller (~20k LoC Go on Kubernetes CRDs, with one controller per job);
  - the Runtime Analyzer (~12k LoC Go).
- A per-pod Robust Agent (~5k LoC Python, gRPC heartbeats) that hosts four modules:
  - Monitor;
  - Diagnoser;
  - On-Demand Tracer (py-spy and flight-recorder stacks);
  - Checkpoint Manager.

### Detection: real-time checks (Sec. 4.1)

The agent runs second-level probes of NICs, switches, GPUs and the host, and these add no GPU work.

- **Network:** probes run every 30 s. Eviction needs two alerts within five minutes.
- **High-confidence signals** such as GPU Unavailable or Disk Fault evict the machine immediately.
- **Training metrics:** a 5x jump in loss or gradient norm counts as a fault.

### Localisation: hierarchical stop-time checks (Sec. 4.2)

Once the job is suspended, the system escalates through four steps:

1. **Diagnose.** Read logs and exit codes, then run targeted tests.
   - For NCCL errors: NVIDIA EUD, then intra- and inter-machine all-to-all and all-gather tests.
   - For NaN: also a bitwise-alignment run against a reference model.
2. **Reattempt.** If every test passes, assume a transient fault and restart.
3. **Rollback.** If the failure recurs, roll back recent user code through hot-update.
4. **Dual-phase replay.** If it still fails, assume an unknown fault such as SDC. Keep tensor-parallel (TP) and pipeline-parallel (PP) sizes fixed and shrink only the data-parallel (DP) size. Replay on horizontal groups, then vertical groups, and intersect the failing groups to isolate one machine.

### Over-eviction via stack aggregation (Sec. 5)

This handles hangs and fail-slow jobs.

1. The tracer dumps stacks of every training-related process (torchrun children, dataloader, checkpoint processes).
2. The Analyzer groups the stacks by string matching. The dominant clusters are taken as healthy and the rest are outliers.
3. It finds the TP, PP or DP group shared by the outliers and evicts that whole group, rather than pinpointing a single node.

For MFU decline, aggregation repeats every 10 s, and after 5 rounds the group flagged most often is evicted. In one case study, a hang mapped to a 6-machine pipeline, and later stress tests found defective CUDA cores on 2 of those machines.

### Recovery (Sec. 6)

**In-place hot-update.** Code and data changes are applied inside the existing pods, so recovery does not bring in fresh, possibly faulty machines.
- Urgent fixes stop training at once.
- Non-critical changes wait for the next failure restart, with a 24 h forcing window.
- Changes are recorded in a database for rollback.

**Warm standby.** Machines are pre-initialised and self-checked, then put in low-power sleep.
- Pool size is the P99 of a binomial model of simultaneous failures, built from historical per-machine daily failure rates.
- Only the evicted machines are swapped. Standby processes wait at a barrier until the controller activates them.

**Over-eviction-aware checkpointing.** The system checkpoints every step to host memory and SSD, locally and on a peer, and avoids HDFS.
- Each rank backs up its shards to a rank outside its own TP, PP and DP groups, so a group eviction cannot destroy both copies.
- Backup traffic goes in chunks on a separate CUDA stream during idle communication windows.
- A dual buffer overlaps the device-to-host copy, serialisation and send. Only the optimizer step waits for the local save.

## Limitations

- **Over-eviction is imprecise.** Evicting a whole PP group (8 machines in a 9,600-GPU job) usually yields 6–7 false positives, because only 1–2 nodes are faulty (Sec. 9).
- **The standby model assumes independent single-node failures.** Correlated rack or switch failures fall outside the P99 binomial model.
- **SDC remains hard.** EUD reaches only 70% recall, so the authors built an in-house test suite. EUD itself once lifted a GPU frequency lock and cost MFU. NaN incidents still average over an hour to resolve (Table 6).
- **No elastic resharding.** The parallelism configuration stays fixed. Without standbys the job waits for replacement machines.
- **Some numbers don't reconcile.** The explicit and implicit totals in Sec. 1 don't match the Table 1 row sums. The baseline timeout is ~10 min in the Table 3 caption but ~30 min in Sec. 8.1.1. The MoE rollback share in Table 4 differs from the text.
- **No public code.** The ETTR results come from two in-house jobs.

## Relation to other systems

- **MegaScale (NSDI 2024).** This is ByteDance's predecessor system.
  - It used RDMA-metric heartbeats, self-check tests and two-stage checkpointing (host memory, then HDFS).
  - It reported more than 90% ETTR and automatic handling of more than 90% of faults.
  - ByteRobust says MegaScale still needed manual investigation for implicit failures. It adds stack aggregation, escalation through rollback and replay, and HDFS-free recovery.
- **ByteCheckpoint (NSDI 2025).** It targets resharding and storage I/O with a parallelism-agnostic format.
  - It cuts average stall 54.20x, saves up to 9.96x faster and loads up to 8.80x faster.
  - ByteRobust instead solves where in-memory backups must live to survive a group eviction.
- **Llama 3 (arXiv 2407.21783).** It reports 466 interruptions in 54 days, 419 of them unexpected.
  - About 78% were attributed to hardware, including faulty GPUs (148, 30.1%) and HBM3 (72, 17.2%).
  - Effective training time was above 90%, with only 3 significant manual interventions.
  - ByteRobust's multi-job census shows a different mix: host, CPU, storage and manual-restart incidents carry a large share.
- **GEMINI (SOSP 2023).** It checkpoints every iteration into local and remote CPU memory, with near-optimal placement and traffic interleaving, and recovers more than 13x faster.
  - ByteRobust's checkpointing is similar in spirit. It adds placement across parallel groups.
- **Oobleck (SOSP 2023).** It recovers without a restart from pipeline templates, keeping f+1 replicas, and was evaluated up to 6.7B parameters.
  - ByteRobust argues that such elastic schemes support limited parallelism. It keeps full 3D parallelism and swaps in standbys instead.

## Takeaways for practice

- Track ETTR from day one, and log every incident by class, including manual restarts.
- Run cheap second-level host, NIC and GPU probes so faults are caught well before collective timeouts fire.
- Cluster stack traces and map them onto the parallelism topology. This localises hangs without vendor tools, and evicting the whole group is acceptable when standbys are cheap.
- Escalate in order of cost: evict, retry, roll back, then replay. Replay was needed for only 1.23% of failures.
- Size the standby pool from measured failure statistics. Apply code changes in place so recovery does not pull in unvetted machines.
- Co-design checkpoint replica placement with the eviction policy.
