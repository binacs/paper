# Oobleck: Resilient Distributed Training of Large Models Using Pipeline Templates

> **Why it matters:** Oobleck shows that the data-parallel replicas a hybrid-parallel job already has can serve as its fault-tolerance redundancy, if the job is planned ahead as a set of heterogeneous pipeline "templates" that can be re-instantiated in place without a restart.

## Problem

Large-model training is synchronous across hundreds to thousands of GPUs, so one failed node idles all of them until recovery. The paper cites OPT-175B, which saw 100+ hardware failures and 100+ major restarts (§2.2). Pure data-parallel jobs get redundancy for free: every replica holds the full model state, so elastic frameworks can drop a worker. Hybrid (pipeline + data, 3D) parallelism breaks this. Each stage owns only a slice of the model, and the parallel plan is tuned for a fixed GPU count.

Prior systems sit at two extremes (§2.2–2.3, Fig. 1):

- **Checkpoint-restart + re-planning (Varuna).** It reloads the last checkpoint and "morphs" the job to a new grid. Its grid topology means one GPU failure leaves others idle, and at high failure rates most wall-clock time goes to restarting and redoing lost work.
- **Redundant computation (Bamboo).** Each node also computes the next stage's forward pass, so it can take over for a neighbour. This costs time and memory even with no failures, runs out of memory on larger models, and still needs a full restart when two adjacent nodes fail.

## Core design

### Pipeline templates (planning)

A *pipeline template* fixes three things: the number of nodes a pipeline uses, the number of stages, and the layer-to-GPU mapping (§3.1). Templates are logically equivalent, since each holds the whole model, but physically different in size. They are generated once before training and never change. Execution then only has to pick and instantiate templates.

**Node-count selection as a Frobenius problem (§4.1.1).** The goal is that any surviving node count N' ≥ (f+1)·n₀ can be split exactly into pipelines built from templates. With p templates of node counts n₀ < … < n_{p−1}, this holds if the counts are **consecutive integers** and p > n₀ − 1. The Frobenius number is then n₀ − 1 (Appendix A, Thm A.1). Oobleck picks the smallest feasible n₀ (the fewest nodes that can hold the model) because shallower pipelines are faster. It makes p as large as possible, with the largest template at N − f·n₀ nodes. Fig. 4a shows templates of 2, 3 and 4 nodes.

**Layer/GPU mapping (§4.1.2).** For each template, a divide-and-conquer DP jointly partitions layers and GPUs. It tries stage counts from n to L and keeps the plan with the lowest modelled iteration time. That time is split into a warm-up/cool-down term, the slowest steady-state stage, and the remaining steady-state work (Eqs. 1–4). Planning assumes 4S microbatches so that bubbles are negligible. A stage may not span nodes. The DP costs O((L−n)·L³·n·M) per template. Memoization from the largest template makes the smaller ones cheap (O(Ln)).

### Instantiation and the f-failure guarantee

The user gives f, the number of simultaneous failures to tolerate. Oobleck instantiates **at least f+1 pipelines**. It enumerates vectors (x₀…x_{p−1}) with Σxᵢ·nᵢ = N and Σxᵢ ≥ f+1 using a coin-change DP in O(Np) (§4.2.1, Eq. 5, Fig. 7), then picks the plan with the highest modelled throughput. Because every pipeline holds a full model copy, the job survives any f failures. It survives more, as long as every stage still has at least one live copy (Fig. 2b: 8 of 12 nodes lost is fine when one copy of each stage remains). Losing all copies of a stage is unrecoverable (Fig. 2a). If fewer than (f+1)·n₀ nodes remain, Oobleck saves progress and exits, and the user restarts from a checkpoint (§3.4).

### Reconfiguration without restart (§5.1)

When the node-change monitor reports a failure, the affected pipelines are re-instantiated in three steps:

1. **Simple re-instantiation.** If a template matches the surviving node count of a broken pipeline, that template is used (Fig. 8a).
2. **Borrowing.** Otherwise, nodes are taken from other pipelines until the smallest template fits. Donor pipelines are re-instantiated on smaller templates (Fig. 8b).
3. **Merging.** If no node can be borrowed, two pipelines are merged. A template always exists for the merged size of 2n₀ − k (Appendix B, Thm B.1).

After re-instantiation, nodes **copy missing layers from surviving replicas**. No checkpoint is read from storage. This copy is the only reconfiguration cost the paper names (Fig. 11), and it does not measure its latency.

### Batch redistribution (§4.2.2, §5.2)

The global batch size B stays fixed, so the optimiser's semantics do not change. Each pipeline i gets an integer number of microbatches N_{b,i}, with Σ N_{b,i}·b·xᵢ = B. The split minimises the variance of per-pipeline iteration times (Eq. 6, an integer nonlinear program solved with Pyomo/MindtPy). This lets smaller, slower pipelines take less work and avoids stragglers. Eq. 6 is solved again after every reconfiguration. If B cannot be split into integers, Oobleck suggests a nearby batch size that can be distributed, rather than changing B silently.

### Implementation (§6)

Oobleck is written in Python on PyTorch and HuggingFace. It uses Merak (torch.fx tracing) to build pipelines and DeepSpeed to run them. Within a stage it uses FSDP rather than tensor parallelism. Gradients are all-reduced per layer and overlapped with compute. NCCL hangs on a dead peer until a timeout, so failure detection runs on a side channel: a CPU process per node holds a TCP connection to a central process.

## Limitations

- **Small evaluation scale.** Experiments use 30 GPUs with one GPU per node, because Bamboo and Varuna lack 3D parallelism (§7.1). At-scale behaviour (thousands of GPUs, multi-GPU nodes, TP inside nodes) is covered only by planning-latency measurements, not by end-to-end runs.
- **Planning cost grows quickly.** Planning cost rises steeply with layers × nodes: about 55 minutes for one template at 96 layers and 24 nodes × 8 GPUs (Table 3). It is a one-off cost, but that matters for very deep models on large clusters.
- **Homogeneous nodes, fail-stop failures.** Templates assume identical nodes and failures that stop a node cleanly. Stragglers, silent data corruption, NaNs and hangs that are not node loss are out of scope. The TCP heartbeat detects node loss only.
- **Unmeasured costs.** Reconfiguration and layer-copy latency are not measured on their own. Memory overhead is not quantified.
- **Heterogeneous pipelines run below the optimal plan.** After failures the job runs on smaller, non-optimal templates. The fixed global batch with integer microbatch splitting can be infeasible for small B (§4.2.2).
- **Stage wipe-out still needs a restart.** f is a guarantee on simultaneous failures. A correlated failure (rack, switch) that removes every copy of one stage still falls back to checkpoint-restart, so periodic checkpoints are still needed.
- **Narrow model coverage.** Only transformer LMs up to 6.7B parameters are tested.

## Relation to other systems

- **Checkpoint-restart / Varuna (EuroSys '22).** Varuna re-plans and reloads from remote storage after each failure. Oobleck plans once and recovers from peer replicas. Table 4 shows that even with checkpoint cost removed, Varuna's restart path loses about 90% throughput at 10-minute failure intervals.
- **Bamboo (NSDI '23).** Bamboo buys tolerance with always-on redundant forward compute and 2× model-state memory. Oobleck's redundancy is the DP replicas the job needs anyway, so it costs almost nothing when there are no failures, and it tolerates adjacent failures up to f.
- **CheckFreq / Check-N-Run.** These cut checkpoint cost but keep the restart path. Oobleck targets the restart itself.
- **GEMINI (SOSP '23, abstract only).** GEMINI keeps checkpoints in peer CPU memory, with placement chosen to maximise recoverability and checkpoint traffic scheduled into training's idle network time. It reports more than 13× faster recovery than existing solutions, with per-iteration checkpoints. It is complementary: GEMINI makes restart cheap, while Oobleck avoids restart for up to f failures. Both rely on "state is already on a peer."
- **MegaScale (NSDI '24, abstract only).** MegaScale's fault tolerance is operational: diagnostics across the stack, root-cause tooling, and straggler handling at more than 10,000 GPUs. The abstract does not describe the kind of in-job elastic re-plan Oobleck offers.
- **ByteRobust (arXiv 2509.16293, abstract only).** ByteRobust is production infrastructure that detects and localises CUDA errors, NaNs and hangs and isolates faulty machines. It reports 97% ETTR over a three-month job on 9,600 GPUs. It covers the fault classes Oobleck assumes away (non-fail-stop, silent faults), while Oobleck covers fast in-job continuation once a bad node is removed.
- **Elastic DP (TorchElastic, Horovod Elastic, Pollux).** These are restart-based or limited to data parallelism. Oobleck extends elasticity to hybrid parallelism.

## Takeaways for practice

- Treat the parallel plan as a **precomputed family** rather than one point. If you can enumerate configurations for N, N−1, …, (f+1)·n₀ nodes offline, recovery becomes table lookup plus state copy instead of re-planning plus reload.
- **Consecutive template sizes** (n₀, n₀+1, …) give a clean guarantee that every surviving node count can be used. This is a useful design rule for any elastic packer.
- The DP replica count is a **fault-tolerance knob**. Scheduling at least f+1 replicas, with every stage present in each, is a placement constraint a cluster scheduler can enforce, for example by spreading a stage's replicas across racks to avoid correlated wipe-out.
- Keep the **global batch fixed** and re-balance microbatches across unequal pipelines. Elastic recovery should not silently change optimiser hyperparameters.
- **Detect node loss outside NCCL** (side-channel heartbeat). Collective timeouts are too slow to drive recovery.
- Oobleck handles fail-stop node loss only. Pair it with checkpointing (GEMINI-style in-memory checkpoints for catastrophic cases) and with ByteRobust/MegaScale-style detection and isolation for hangs, NaNs and stragglers.
