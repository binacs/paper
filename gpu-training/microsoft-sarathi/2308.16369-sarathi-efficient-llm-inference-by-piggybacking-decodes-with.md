# SARATHI: Efficient LLM Inference by Piggybacking Decodes with Chunked Prefills

> **Why it matters:** It introduced chunked prefills mixed with decodes in one batch. That idea now underpins Sarathi-Serve, DeepSpeed-FastGen's Dynamic SplitFuse and the chunked-prefill modes of mainstream serving engines.

## Problem

LLM inference has two phases with opposite hardware profiles:

- **Prefill** processes all prompt tokens in parallel. It saturates GPU compute even at batch size 1. For LLaMA-13B on an A6000, prefill throughput plateaus once batch x length reaches about 512 tokens (§3.1, Fig. 4a).
- **Decode** produces one token per request per iteration. Each iteration must still stream all model weights from HBM, so "most of the computation time in baseline decoding is spent fetching model weights from GPU's global memory" (§4.3). Arithmetic intensity falls by more than two orders of magnitude relative to prefill (Fig. 4b). Large batches would amortise the weight reads, but the KV cache caps batch size: roughly 18 requests at 1K context for LLaMA-13B on a 48 GB A6000 (§3.1). Decode therefore stays memory-bound, and its per-token cost is 200x, 100x and 16.7x that of prefill at batch sizes 1, 2 and 18 (§3.1, Fig. 3).

The second problem is **pipeline parallelism**. With Orca-style iteration-level scheduling, micro-batches differ in compute time, causing bubbles (§3.2, Fig. 5): PB1 from differing prompt lengths, PB2 from prefill/decode micro-batch transitions, PB3 from differing KV-cache lengths in decode.

## Core design

The key insight (§3.3): build batches that are uniformly compute-heavy. Then the memory-bound decode work rides for free on compute-bound prefill work, and every micro-batch costs about the same.

### Chunked prefills (§4.2)
- A prompt is split into equal-sized chunks, and one chunk is processed per iteration. A causal attention mask over the already-cached KV of earlier chunks makes the result mathematically identical to a full prefill (Fig. 6).
- The chunk only needs to be big enough to saturate compute. LLaMA-13B reaches peak prefill throughput near 512 tokens, and a 256-token chunk loses about 12.5% of peak (§4.2). Models with larger hidden sizes, such as GPT-3, saturate at smaller chunks.
- Costs: each chunk re-reads the KV cache of all earlier chunks, and smaller chunks lower arithmetic intensity. The ablation in §5.4 measures these costs.

### Decode-maximal batching (§4.3)
- Each batch holds **one** prefill chunk plus as many decodes as fit. The maximum batch size is set by how much GPU memory is left for the KV cache after the model weights, divided by the KV-cache footprint of one maximum-length request (§4.3 gives the formula; it is not reproduced here). With a maximum batch of B, up to B-1 decodes piggyback on the chunk.
- Linear layers (QKV projection, output projection, FFN) run as one fused GEMM over the prefill-chunk tokens plus the decode tokens. Those layers dominate decode cost, and the weights are now read once for both. Attention still runs separately for the prefill and decode parts.
- Example (Table 2, LLaMA-13B, A6000): a mixed batch of 1021 prefill tokens plus 3 decodes keeps prefill at 0.229 ms/token, while decode cost falls from 12.49 to 1.2 ms/token, about 10x.

### Choosing the chunk size; tile quantization (§4.4)
- **P:D ratio.** This is the ratio of prefill tokens to decode tokens in the workload. Smaller chunks piggyback more decodes but lose prefill efficiency. Every decode can be overlapped only if there are enough prefill chunks to carry them. For example, with batch 4, chunk 128 needs P:D > 42 and chunk 256 needs P:D > 84. Throughput gain peaks near P:D = C/(B-1) (§5.1.3).
- **Tile quantization.** GEMM kernels tile the token dimension, so a dimension just past a tile boundary pays for a whole extra tile. On LLaMA-13B/A6000, 128 -> 256 tokens raises iteration time 27% (55 -> 69.8 ms), but one more token (257) jumps it to 92.33 ms, a further 32% (Fig. 7).
- **Rule.** First pick the chunk size for the prefill efficiency you want. Then make chunk + piggybacked decodes a multiple of the tile size. With tile 128 and target 256, the chunk becomes 256 - (B-1). The paper says the naive "smallest saturating chunk" is often not the most efficient choice.

### Pipeline-bubble reduction (§4, §5.3)
- Every micro-batch now holds about the same token count: one chunk plus about B-1 decodes. Compute per stage is therefore near-uniform, which removes PB1 and PB2 and shrinks PB3. Decodes no longer run as cheap stand-alone micro-batches behind expensive prefills.

### Implementation (§4.5)
- Built on nanoGPT with xformers attention and a pre-allocated KV cache. Single-GPU runs are real deployments. The pipeline-parallel results come from a simulator that the authors validate to within 5% on an 8xA100 DGX (§5.3).

## Limitations

- **Throughput only.** No TTFT or time-between-tokens results; piggybacked decodes now last a full chunk iteration, a latency cost the paper does not analyse. Sarathi-Serve made TBT SLOs central.
- **Static, homogeneous workloads.** Single-GPU runs use fixed sequence lengths and P:D, assuming identical requests in a batch (§6); only the simulated PP run samples lengths (Zipf, 1K-4K).
- **Chunk size is hand-tuned** to a known P:D and tile size; online selection is future work (§6).
- **Bounded gains.** Only decodes speed up, so end-to-end gains stay at 1.1-1.33x despite 3-10x decode speedups (Table 4).
- **Chunking overhead** from KV re-reads, plus quadratic attention for very long prompts (§5.4, §6).
- **The PP result is simulated**, and the prototype (nanoGPT, contiguous pre-allocated KV cache, no paging or preemption) is not a serving system.

## Relation to other systems

- **Orca (OSDI'22).** Iteration-level scheduling plus selective batching lets requests join every iteration, but Orca does not control batch *composition*: full prompts and decodes mix freely, so iteration costs vary. SARATHI adds the rule "one bounded chunk + maximal decodes"; best-case Orca reaches 1.11x vs SARATHI's 1.27x (§5.2).
- **vLLM / PagedAttention (SOSP'23).** vLLM attacks memory: paged KV blocks cut fragmentation and duplication, raising batch size (2-4x throughput over FasterTransformer and Orca). This is complementary: bigger batches give SARATHI more decodes to piggyback. Sarathi-Serve later used vLLM as its main baseline.
- **Sarathi-Serve (OSDI'24, follow-up).** Keeps chunked prefills and turns decode-maximal batching into stall-free scheduling: new chunks join without pausing ongoing decodes, under a token budget sized for tail latency rather than throughput alone. Its abstract reports 2.6x serving capacity over vLLM (Mistral-7B, one A100), up to 3.7x (Yi-34B, two A100s) and up to 5.6x for Falcon-180B with PP.
- **DeepSpeed-FastGen, Dynamic SplitFuse (arXiv'24).** Splits long prompts across forward passes and packs short ones to "exactly fill a target token budget", SARATHI's idea generalised to a fixed per-pass budget; the paper notes "a similar approach has been proposed in Sarathi". It reports up to 2.3x effective throughput over vLLM.
- **DistServe (OSDI'24).** The opposite pole: prefill and decode run on separate GPUs, removing interference and letting each phase pick its own parallelism under TTFT/TPOT targets, at the cost of KV transfer. It reports 7.4x more requests or a 12.6x tighter SLO.

## Takeaways for practice

- Decode at feasible batch sizes is memory-bound; measure per-phase arithmetic intensity and fill the spare FLOPs.
- Fuse decode tokens into prefill GEMMs so weight reads are shared; keep attention per sub-batch.
- **Tile-align token counts**: one extra token can cost about 30% (Fig. 7). Profile tile sizes per GPU and model.
- Under pipeline parallelism, **equalise per-micro-batch work**; a fixed token budget removes most bubble variance.
- Derive chunk size from TBT SLOs and observed P:D (as Sarathi-Serve does), not a static tuning pass.
- KV-cache capacity (paging, quantization) scales the benefit, since decodes per chunk are capped at B-1.
