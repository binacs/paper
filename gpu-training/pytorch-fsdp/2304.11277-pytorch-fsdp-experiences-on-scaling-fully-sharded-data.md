# PyTorch FSDP: Experiences on Scaling Fully Sharded Data Parallel

> **Why it matters:** FSDP turned ZeRO-3-style parameter sharding into a native PyTorch primitive co-designed with the tensor, autograd and CUDA caching allocator, and it is the default "data-parallel but sharded" baseline that most large-model training stacks are measured against.

## Problem

DDP replicates parameters, gradients and optimizer state on every GPU, so on a 40 GB GPU models beyond roughly one billion parameters run out of memory (§2.1). Pipeline and tensor parallelism constrain model structure or require code changes (§2.2). The authors argue that existing sharding systems are architecture-specific or depend on unstable framework internals (§1, §6). The design challenges they name are user experience, hardware heterogeneity, resource utilisation and memory planning.

## Core design

FSDP decomposes a model into **units** (typically submodules such as transformer blocks). Each unit's parameters are stored sharded; just before the unit's forward or backward runs, FSDP AllGathers the full parameters, computes, then frees them. Gradients are reduced with ReduceScatter so each rank keeps only its gradient shard (§3, Fig. 1). The outermost unit stays unsharded so its AllGather is skipped in backward (§3.3.1). Peak memory is then the sharded model plus the largest materialised unit.

### Deferred initialisation (§3.1, §4.1)
FSDP builds the model on a "fake" device and records the initialisation ops. It then replays them unit by unit on the GPU and shards each unit straight away. Replay fails when one unit's init reads another unit's parameter. The fallbacks are to build the full model on GPU before sharding, or to build on CPU and stream units to the GPU, which is slower (§4.1). Units come from manual wrapping or an `auto_wrap_policy`.

### FlatParameter (§3.2.1, §4.2)
NCCL collectives are fastest with even-sized inputs and few large calls. With total volume fixed at 2^30 FP32 elements, AllGather time rises sharply once each call is below about 33M elements (Fig. 2). FSDP therefore concatenates all parameters of a unit into one 1-D `FlatParameter`, right-pads it to a multiple of the sharding factor F (padding at most F−1 elements), and splits it into F equal chunks. Original parameters become views into the unsharded flat tensor (`torch.split`/`view`), so autograd works unchanged (§3.2.3). Peak parameter memory is O(Σᵢψᵢ/F + maxᵢψᵢ) with O(N) collectives per iteration for N FlatParameters, which makes wrapping granularity an explicit memory-versus-collective-count knob. `FlatParameter` subclasses `nn.Parameter` and is managed by a `FlatParamHandle`. Nested wrapping works because a module's FlatParameter takes only parameters not already assigned to a child unit.

### Sharding strategies (§3.2)
With world size W and sharding factor F:
- **F = 1, full replication:** equivalent to DDP (AllReduce).
- **F = W, full sharding:** lowest memory. With a bandwidth-optimal ring it has 1.5x the communication volume of DDP (AllGather in forward and backward plus ReduceScatter, versus one AllReduce).
- **1 < F < W, hybrid sharding:** shard within groups of size F, replicate across groups. Gradient reduction is a ReduceScatter inside the shard group followed by an AllReduce inside the replication group (Fig. 4: 16 GPUs, F = 8). Setting F to the GPUs per host keeps the sharding collectives on the intra-host fabric and cuts cross-host traffic, so the strategy exploits datacenter locality (§3.2.2).

### Communication–computation overlap (§3.3)
- **Separate stream:** AllGathers go on their own CUDA stream so they do not create false dependencies with the compute stream (Fig. 5).
- **Backward prefetch:** In backward, the next unit's AllGather is issued *before* the current unit's ReduceScatter, so two collectives are not exposed back to back on the single NCCL stream. The backward order is approximated by the reverse of the forward execution order recorded in the current iteration.
- **Forward prefetch:** For static graphs, FSDP uses the previous iteration's order to issue the next AllGather before the current unit's forward compute. This targets workloads whose CPU-side execution is too slow to issue collectives early enough.
- **Gradient accumulation:** Either accumulate with communication (ranks keep sharded gradients) or without communication (ranks keep unsharded gradients). The second uses more memory and skips collectives on non-sync steps (§3.3.4).

### Memory management and the rate limiter (§3.4)
The CUDA caching allocator reuses blocks per stream. Blocks freed after a cross-stream use (AllGather output consumed by compute) cannot be reused until the dependent kernels finish. If the CPU thread runs far ahead, it allocates many AllGather buffers, triggers `cudaMalloc` retries and full cache flushes, and throughput collapses. The **rate limiter** blocks the CPU thread so that at most two AllGathers are in flight, which the paper calls the minimum that still allows overlap (§3.4.2). The guidance is to check `num_alloc_retries` in `torch.cuda.memory_stats()` before turning it on (§5.3).

### Runtime hooks (§4.3)
Tensor `register_hook()` inserts pre-backward AllGathers. `AccumulateGrad` hooks launch ReduceScatter, and `queue_callback()` drains collectives before the optimizer step. The `fully_shard` API installs hooks without replacing modules.

### Mixed precision (§4.4)
Naive mixed precision costs (K_low + K_full)·Ψ bytes. FSDP keeps only the *sharded* full-precision parameters persistently and materialises the unsharded low-precision copy per unit, so the peak unsharded term drops from K_full·maxᵢψᵢ to K_low·maxᵢψᵢ. Collectives can also run in low precision. Because gradients are sharded, a sharded gradient scaler is provided.

## Limitations

- **Mathematical equivalence (paper):** FlatParameter chunking ignores parameter boundaries, so optimizers that need per-parameter global quantities (norm-based, second-order) cannot be applied locally without uneven sharding, padding or extra communication (§7.2). The authors leave optimizer and sharding co-design as an open problem.
- **Shared parameters (paper):** Tied weights must not be split across FlatParameters. The workaround is to hoist them into the lowest-common-ancestor unit, which keeps them unsharded for longer (§7.2).
- **Deferred-init fragility (paper):** Cross-unit initialisation dependencies break fake-device replay, and the fallbacks cost memory or time (§4.1).
- **Pipeline interop (paper):** Full sharding inside a pipeline stage re-gathers parameters for every microbatch. Avoiding that means keeping the whole stage unsharded after forward (§7.1). Tensor-parallel composition through DTensor is only a prototype (§7.1).
- **Unit-granular design (own analysis):** All parameters in a unit share one flat buffer, which complicates frozen layers, adapters and per-parameter state. PyTorch's later FSDP2 moved to per-parameter DTensor sharding.
- **Evaluation scope (own analysis):** The evaluation uses one platform (A100 + RoCE) and at most 512 GPUs, with DDP as the only baseline (no DeepSpeed or Megatron head-to-head). Forward prefetch gets no quantitative result. The paper does not say whether activation-recompute FLOPs count toward utilisation.
- **No fault tolerance or straggler handling (own analysis):** The paper covers neither.

## Relation to other systems

- **ZeRO (SC 2020):** Its abstract describes partitioning optimizer state, gradients and parameters to train >100B models on 400 GPUs at ~15 PFLOPS. FSDP is explicitly ZeRO-3-inspired. The differences are engineering ones: FlatParameter, integration with PyTorch's autograd and caching allocator, the rate limiter, and hybrid sharding as a topology knob.
- **Megatron-LM PTD-P (SC 2021):** Its abstract combines tensor, pipeline and data parallelism to reach 502 PFLOP/s on 3072 GPUs (52% of peak) for a 1T model. That needs model-specific tensor-parallel layers. FSDP is model-agnostic and leaves intra-layer splitting to DTensor 2D composition.
- **ZeRO-Offload (ATC 2021):** Its abstract offloads optimizer data and compute to the CPU, training >13B models on one V100. The FSDP paper targets the GPU-resident path and cites CPU offload only as orthogonal (§6).
- **GSPMD (arXiv 2021) / Alpa (OSDI 2022):** Both are compiler-based. GSPMD infers per-operator partitioning from a few annotations (50–62% utilisation on up to 2048 TPUv3 cores). Alpa searches an inter-/intra-operator plan space. FSDP runs eagerly through runtime hooks, with a few manual knobs (wrap policy, F).
- **MegaScale (NSDI 2024):** Its abstract reports 55.2% MFU for a 175B model on 12,288 GPUs (1.34x over Megatron-LM) and treats failure and straggler diagnosis as core. It builds on the Megatron 3D path. FSDP's paper does not address reliability and runs at about 1/24 of that scale.

## Takeaways for practice

- Collective size matters as much as volume. Use large, evenly sized flat buffers, and wrap so each AllGather stays above the NCCL efficiency knee.
- Map the sharding factor to topology: shard inside the fast domain and replicate across it. Topology-aware rank placement by the scheduler makes hybrid sharding pay off.
- Watch the allocator as well as the network. Allocator retries caused several of the throughput cliffs, and capping in-flight AllGathers fixes them cheaply. Export `num_alloc_retries` as job telemetry.
- Prefetch relies on recorded execution order. Dynamic graphs lose forward prefetch.
- Keep FP32 master weights only as shards, and size jobs with that in mind.
- Initialise large models on a fake/meta device, and test cross-module init dependencies early.
