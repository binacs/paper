# Efficient Large-Scale Language Model Training on GPU Clusters Using Megatron-LM

> **Why it matters:** It fixed the canonical "3D parallelism" recipe (tensor parallel inside a node, pipeline across nodes, data parallel outside), gave closed-form rules for choosing the degrees, and showed it sustaining 52% of A100 peak at 1T parameters on 3072 GPUs. Most later LLM training stacks start from this layout.

## Problem

Models with hundreds of billions to a trillion parameters fit in no single GPU, and each parallelism dimension breaks down when used alone. Data parallelism is capped by the global batch size and needs a full replica per GPU. Tensor (intra-layer) parallelism needs an all-reduce in every layer, which works over NVLink but slows sharply across nodes and shrinks the GEMMs. Pipeline parallelism with synchronous flushes wastes time in a "pipeline bubble" and can only split as finely as the layer count allows. The paper asks how to compose the three, which schedule to use, and how to set t, p, d and the microbatch size b, while keeping strict optimizer semantics (no stale weights).

## Core design

**PTD-P composition.** With n = p·t·d GPUs, the t tensor-parallel ranks sit inside one DGX A100 (8 GPUs, NVLink/NVSwitch), the p pipeline stages span nodes over InfiniBand, and d data-parallel replicas wrap the whole model-parallel group. Tensor parallelism uses Megatron's column-then-row GEMM split in the MLP and attention, costing two all-reduces per layer forward and two backward (§2.3, Fig. 5).

**Pipeline schedules (§2.2).**
- GPipe: all forward passes, then all backward passes. Bubble fraction = (p−1)/m, where m is the number of microbatches per pipeline. Activation memory grows with m.
- PipeDream-Flush (1F1B): it has the same bubble, but after a warm-up phase each stage alternates one forward and one backward pass. In-flight microbatches are therefore capped at p, not m, which saves a lot of memory when m ≫ p.
- **Interleaved 1F1B (new).** Each device holds v non-contiguous model chunks. For example, device 1 holds layers 1, 2, 9 and 10 rather than 1–4. Each microbatch then crosses each device v times, and the bubble shrinks to (1/v)·(p−1)/m. The cost is v× more pipeline point-to-point traffic, and m must be an integer multiple of p.

**Analytical guidance (§3).** Notation: B is the global batch, b the microbatch, and m = B/(b·d).
- Tensor vs pipeline: pipeline traffic is bsh per microbatch per stage boundary. Tensor traffic is 8bsh·(t−1)/t per layer per device. *Takeaway 1:* use tensor parallelism up to the GPUs per server (g = 8), then pipeline across servers.
- Data vs model parallelism: for fixed n, a larger d shrinks the bubble ((n−d)/b′ with t = 1), and data-parallel all-reduce happens once per batch, not once per microbatch. *Takeaway 2:* make the model-parallel size M = t·p only as large as memory requires, then fill the rest with d.
- Microbatch size: batch time ≈ (b′/b + p − 1)·(t_f(b) + t_b(b)) with b′ = B/d (Eq. 1). A larger b improves kernels but enlarges the bubble. *Takeaway 3:* the optimal b depends on the model's throughput and memory curves and on p, d and B, so measure t_f and t_b at a few values of b and plug them in.
- Activation recomputation: with c checkpoints per stage of l layers, memory = c·A_input + (l/c)·A_intermediate, which is minimised at c = √(l·A_intermediate/A_input). In practice, checkpoint every 1–2 transformer layers (§3.5).

**Scatter/gather communication (§4.1, Fig. 9).** Once tensor parallelism is in place, the activation sent between stages is replicated across the t ranks of a stage. Each sender transmits only 1/t of it, and the receiving node rebuilds the tensor with an NVLink all-gather. Cross-node bytes per pair drop to bsh/t, and all 8 HCAs are used, which is what makes interleaving affordable.

**Computation optimisations (§4.2).**
- Layout [b, s, a, h] → [s, b, a, h] to remove transposes and enable strided batched GEMMs.
- PyTorch-JIT fusions (bias+GeLU, bias+dropout+add) and custom fused scale+mask+softmax kernels (general and causal masks).

**FLOP accounting (§5, Eq. 3).** F = 96·B·s·l·h²·(1 + s/6h + V/16lh). This counts GEMMs only and includes the extra forward pass from recomputation, so the reported "% of peak" is hardware-FLOP utilisation, not model-FLOP utilisation.

## Limitations

- The configuration is chosen by heuristics and takeaways, not by an automated search. The model counts communication volume but not time, and ignores overlap.
- It assumes homogeneous, symmetric transformer stacks. Layer-to-stage assignment for asymmetric models (embedding/logit-heavy stages, encoder-decoder, MoE) is out of scope. Pipeline depth is capped by the layer count.
- The schedule still flushes every step, so small global batches still pay the bubble.
- The utilisation numbers count recomputation FLOPs (Eq. 3). The same work counted without the extra forward pass would be about 3/4 of the reported figure (my calculation from the 96 vs 72 coefficient, not a number in the paper). Later work such as MegaScale reports MFU instead.
- The "t = 8" rule reflects the DGX topology (8 GPUs on NVSwitch, 8 HCAs per node), not a general law.
- ZeRO-3 was compared without tensor parallelism, which favours PTD-P at scale.

## Relation to other systems

- **GPipe (Huang et al., 2019):** synchronous micro-batched pipeline with all-forward/all-backward. It has the same (p−1)/m bubble, but activation memory grows with m. PTD-P uses the 1F1B order to cap in-flight activations at p, then interleaves chunks to divide the bubble by v.
- **PipeDream / PipeDream-2BW (Narayanan et al.):** 2BW avoids flushes by double-buffering weights, with 1-stale updates (abstract: up to 20× speedup on GPT/BERT with similar accuracy). It also partitions automatically. This paper drops staleness in favour of strict semantics (PipeDream-Flush plus interleaving) and composes the pipeline with tensor parallelism.
- **ZeRO / DeepSpeed (Rajbhandari et al., 2020):** shards optimizer state, gradients and parameters across data-parallel ranks instead of splitting the model. Stage 3 gathers parameters every step over the inter-node network. Table 2 shows ZeRO-3 per-GPU throughput falling from 144 to 44 TFLOP/s when 175B training is scaled from 384 to 1536 GPUs, against 141 for PTD-P. In practice the two are combined, with ZeRO-1 optimizer sharding over d.
- **PyTorch FSDP (Zhao et al., 2023; abstract):** the PyTorch-native ZeRO-3-style fully sharded data parallel, co-designed with the dispatcher and caching allocator. It reports DDP-comparable performance with much larger models and near-linear TFLOPS scaling. It has the same trade-off versus PTD-P and is usually layered with tensor parallelism at very large scale.
- **MegaScale (Jiang et al., NSDI 2024; abstract):** a production system that builds on Megatron-style 3D parallelism. It adds computation-communication overlap, operator and data-pipeline optimisation, network tuning, and diagnosis, fault-tolerance and straggler tooling for runs on more than 10,000 GPUs. It reports 55.2% MFU for 175B on 12,288 GPUs, 1.34× Megatron-LM's MFU. It addresses the operational gaps left open here, including fault tolerance.

## Takeaways for practice

- Map parallelism dimensions to the bandwidth hierarchy. Put the chattiest dimension (tensor parallelism: per-layer all-reduce) on the fastest link (NVLink, within one node). Put the next one (pipeline: bsh per microbatch boundary) across nodes. Put the least frequent one (data parallelism: once per step) on the outermost level. A scheduler must keep each t-group on one node.
- Make model parallelism (t·p) only as large as memory forces, then scale with d. Bubble and communication costs both grow with model parallelism.
- Keep the bubble formula (p−1)/(v·m) at hand. More microbatches per step (larger B/d) or more chunks per device (v) amortise it. Interleaving pays only if the extra point-to-point traffic is cheap, which here required scatter/gather across all NICs.
- Tune the microbatch size empirically with Eq. 1 using measured t_f(b) and t_b(b). Do not set b = 1 by default.
- Full activation recomputation can raise end-to-end throughput when it unlocks a larger batch, despite costing about 33% at small batch.
- Kernel fusion and data layout gave double-digit gains (11–19%). The system-level design does not make operator work unnecessary.
- Plan checkpoint I/O: a 13.8 TB checkpoint is limited by filesystem bandwidth, and its cost scales with failure frequency.
