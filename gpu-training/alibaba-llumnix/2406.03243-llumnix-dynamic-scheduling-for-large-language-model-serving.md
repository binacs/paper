# Llumnix: Dynamic Scheduling for Large Language Model Serving

> **Why it matters:** It treats LLM requests like OS processes that can be context-switched between model instances, using live KV-cache migration with near-constant downtime, so a cluster scheduler can keep rebalancing after dispatch instead of living with its first placement decision.

## Problem

Engines such as vLLM and Orca optimize one instance. The cluster layer above them dispatches once, by round-robin or a load heuristic, and the request then stays pinned to that instance. Output length is unknown in advance and KV memory grows every token, so a good placement turns bad after dispatch. The paper measures three consequences (§3):

- **Preemption.** An instance runs out of KV blocks mid-decode and must preempt requests, which are recomputed or swapped later (Fig. 3).
- **Interference.** Decode-step time at equal sequence length depends on what else is in the batch (Fig. 4).
- **Cross-instance fragmentation.** The cluster's total free memory often fits the queued head-of-line request, but it is split across instances. Prefill suffers most (Fig. 5).

There is also no notion of **priority**: interactive and offline requests are treated the same.

## Core design

### Live migration of a running request (§4.2, Figs. 6–7)

Migrating by recomputing the prompt and generated tokens, or by stop-and-copy of the KV cache, causes a stall that grows with sequence length. Llumnix borrows pre-copy VM live migration and exploits one property of the KV cache: it is **append-only**. Blocks already written never change, so no dirty-page tracking is needed.

- **Multi-stage pipelined copy.** Stage 0 copies all completed KV blocks while the request keeps decoding on the source. Each later stage copies only the blocks produced during the previous stage. Copying is faster than decoding, so each delta is smaller than the last. In the final stage, the source drains the request out of its batch, copies the last few blocks and hands over. Downtime is therefore about one iteration's worth of copying, independent of total length. In the tested cases, two stages always sufficed (§6.2).
- **Handshake.** Before each stage, the source asks the destination to pre-allocate blocks, and the destination may refuse if memory is short. After each stage, the source checks whether the request finished or was preempted in the meantime, and aborts if so. Either side aborts if the other fails. On commit, the source frees its blocks and the destination resumes decoding. This covers two LLM-specific failure modes that VM migration lacks: the destination running out of memory during migration, and the request finishing mid-migration.
- **Transport (§5).** KV transfer uses Gloo Send/Recv through CPU buffers on a separate CUDA stream, not NCCL, because concurrent NCCL calls alongside inference are unsafe. vLLM's small, non-contiguous blocks are **fused** into one contiguous buffer per transfer. Tokens are streamed back through a Ray-actor frontend, so the client connection is unaffected by migration.

### Architecture: global scheduler + llumlets (§4.3, Fig. 8)

- **Global scheduler.** It sees only per-instance load metrics, not individual requests, so its cost does not grow with the number of running requests. It decides dispatch, which source and destination instances to pair for migration, and scale-out/scale-in.
- **Llumlet (one per instance).** It has two parts. A *local scheduler* (queuing, batching, block management) computes the instance's load and picks *which* request to migrate. A *migration coordinator* drives the handshake and tells the model executor to copy blocks. Llumlets report load periodically.
- This split keeps per-request decisions local and cluster decisions coarse. The point of it is scheduling scalability (§6.6).

### Virtual usage: one policy for four goals (§4.4, Alg. 1, Fig. 9)

Instead of writing separate policies for load balancing, de-fragmentation, priority and auto-scaling, Llumnix gives each request a **virtual memory usage**. A single load-balancing loop then acts on the sum of these values:

- Normal running request: virtual usage = physical KV usage.
- **Head-of-line queued request:** virtual usage = its full memory demand. This makes a fragmented instance look overloaded, so requests migrate off it and it gains contiguous space. That is de-fragmentation done by load balancing.
- **High-priority request:** physical usage plus a *headroom*, shared among the instance's high-priority requests. The headroom is profiled as the memory load at which decode speed stays ideal. This keeps high-priority requests on lightly loaded instances, giving less interference (execution priority).
- **Terminating instance:** a fake request with infinite virtual usage. Load balancing then drains the instance by migration, which makes scale-in cheap.
- A new instance looks empty, so load balancing fills it automatically.

Load is expressed as **freeness** F = (M − ΣV) / B, where M is total memory, V each request's virtual usage and B the batch size. F roughly means "iterations this batch can still run". A negative value means the instance is overloaded.

Policies:
- **Dispatch:** higher priority first, FCFS within a priority class. Each request goes to the instance with the highest freeness.
- **Migration:** runs periodically. Instances with F below one threshold become sources, those above another become destinations, and pairs are formed from the extremes. Sources prefer to migrate lower-priority, shorter requests.
- **Auto-scaling:** keeps the average normal-priority freeness within [x, y]. An instance is added when F stays below x and removed when F stays above y; the instance with the fewest running requests is drained.

Implementation: about 3,300 lines of Python, a library layered over vLLM, with Ray actors (§5). If the global scheduler fails, frontends fall back to simple dispatch and migration is disabled.

## Limitations

- **Small scale, short contexts.** The evaluation uses 16 A10s, LLaMA-7B/30B and the 2k-context vLLM of the time. Behaviour with 100k+ contexts, large TP/PP groups or RDMA fabrics is not shown. With long contexts, stage 0 moves gigabytes per request over shared links.
- **Memory is the only load signal.** Freeness is based on KV memory. Compute interference is handled only indirectly, by spreading load. There is no explicit TTFT/TPOT SLO model, and the priority headroom is profiled offline.
- **Hand-set knobs.** The paper gives no numeric migration thresholds. The auto-scaling range is tuned (§6.5 sweeps it), and stability against oscillation is argued informally.
- **Limited scope.** There are two priority classes, enforced only through headroom. Instances are homogeneous, with no prefill/decode disaggregation; the open-source project added that later, unevaluated here. A failed instance aborts its requests.
- **Baselines.** The baselines are round-robin and an improved INFaaS. Chunked prefill and disaggregated systems are not compared.

## Relation to other systems

- **vLLM.** Llumnix runs on top of it. vLLM handles memory exhaustion by local preemption (recompute or swap). Llumnix adds a cluster-level option: move the request to an instance with free memory. Block-granular paged KV is what makes incremental migration practical.
- **Orca.** Iteration-level batching inside one instance. Llumnix takes it as given and decides which instance a request should be on over time.
- **DistServe (OSDI'24).** It also moves KV caches between instances, but once and by design, from prefill to decode workers, to remove phase interference. Llumnix migrates repeatedly between equivalent instances for load, fragmentation and priority. The two are complementary.
- **Sarathi-Serve (OSDI'24).** Chunked prefill bounds per-iteration interference inside an instance. Llumnix instead reduces interference by spreading load across instances.
- **INFaaS / DNN serving (Clipper, Nexus, Clockwork).** These dispatch once per short, stateless request. Llumnix argues that long-lived, stateful LLM requests make rescheduling after dispatch worthwhile.
- **Classic preemption and migration.** Borg-style kill-and-restart is the analogue of vLLM's recompute. Gandiva migrates training jobs at mini-batch boundaries, too slow for inference (§7). Llumnix applies pre-copy VM live migration per request. Because KV is append-only, pre-copy converges, unlike VM pre-copy on write-heavy pages.

## Takeaways for practice

- **Make placement revocable.** If request state moves cheaply, dispatch can stay simple and greedy, and continuous rebalancing corrects mistakes caused by unpredictable output lengths.
- **Exploit append-only state.** Pre-copy of KV converges in about two rounds, with downtime of one iteration rather than O(length). The same holds for other log-structured state such as agent transcripts.
- **Express intent as fake load.** Virtual usage folds de-fragmentation, priority isolation and drain-for-scale-in into one load balancer: one control loop to tune instead of four.
- **Drain by migration.** Scale-in, maintenance and spot reclaim become cheap when an instance empties in seconds instead of waiting for its longest request.
- **Keep the global scheduler request-agnostic.** Instance-level aggregates plus local per-request choice avoid central scheduling stalls (§6.6).
- **Isolate the transport.** Migration must not block inference collectives (hence Gloo via CPU and fused blocks, not NCCL). Budget a separate channel's bandwidth.
- **Handshake for LLM-specific failures.** The protocol must handle the destination running out of memory and the request finishing mid-copy.
