# Ansor: Generating High-Performance Tensor Programs for Deep Learning

> **Why it matters:** Ansor showed that template-free search can match or beat hand-written templates and vendor libraries. It samples complete programs from an automatically built space and refines them with evolution and a learned cost model. It also spreads one tuning budget across a network's subgraphs with a gradient-based task scheduler.

## Problem

Vendor libraries (cuDNN, MKL-DNN) cover only common operators, and existing search frameworks have structural limits (§1–2):

- **Template-guided search** (AutoTVM, FlexTensor): "developing templates requires substantial effort," and "manual templates only cover limited program structures." FlexTensor's general templates still work at single-operator granularity.
- **Sequential construction** (the Halide auto-scheduler's beam search): it keeps the top-k candidates after each decision. But "the cost model trained on complete programs cannot accurately predict the final performance of incomplete programs," and the fixed decision order limits the space.

Ansor's goal has three parts: a large search space generated automatically, a search that only evaluates complete programs, and good use of a limited tuning budget across all subgraphs of a DNN.

## Core design

Ansor partitions a DNN into subgraphs using Relay's fusion algorithm (§3). It then loops over three components: the **program sampler** (§4), the **performance tuner** (§5) and the **task scheduler** (§6). TVM serves only "as a deterministic code generator" (§7).

### Hierarchical search space (§4)

- **Sketch generation (§4.1).** The state is `s = (S, i)`: a partial sketch `S` and a working node `i`. Nodes are visited in topological order from output to input. A queue holds the intermediate states, and a state with `i = 0` is terminal. The rules in Table 1 (each "Condition → action") are:
  1. *Skip*: ¬IsStrictInlinable.
  2. *Always Inline*: IsStrictInlinable, i.e. a simple element-wise operator.
  3. *Multi-level Tiling*: HasDataReuse, i.e. a compute-intensive operator with reuse.
  4. *Multi-level Tiling with Fusion*: HasDataReuse ∧ HasFusibleConsumer (a single consumer that can be fused).
  5. *Add Cache Stage*: HasDataReuse ∧ ¬HasFusibleConsumer. This is the one rule that leaves `i` unchanged.
  6. *Reduction Factorization*: HasMoreReductionParallel.
  - Users can add rules.
- **Tile structure.** On CPU the tiling is "SSRSRS" (S = a space-loop tile level, R = a reduction-loop tile level). A typical subgraph has fewer than 10 sketches.
- **Random annotation (§4.2).** The sampler randomly fills tile sizes, parallelizes outer loops, vectorizes inner loops, sets unroll pragmas and moves some computation locations. The sketch fixes the structure and the annotation fixes the details, which is what makes the space hierarchical.
- **GPU (§4.3).** The tiling becomes "SSSRRSRS". The first three space tiles bind to BlockIdx, a virtual thread (to cut bank conflicts) and ThreadIdx. Two extra rules add shared-memory caching and cross-thread reduction.

### Performance tuner (§5)

- **Evolutionary search (§5.1).** The initial population is fresh samples plus "high-quality programs from the previous measurement." The cost model predicts each program's fitness (throughput), and selection is proportional to that prediction. Programs are stored as sequences of rewriting steps, so they can be edited out of order. The operators are:
  - tile-size mutation, which moves a random factor between tile levels;
  - parallel mutation, which fuses or splits parallel loops;
  - pragma mutation, e.g. the auto-unroll max step;
  - computation-location mutation;
  - node-based crossover, which picks one parent per node and merges their rewriting steps.
- **Learned cost model (§5.2).** A gradient boosting decision tree (citing XGBoost) scores each innermost non-loop statement, and a program's score is the sum of those scores.
  - Features cover arithmetic and memory access. The full list is in the extended version's appendix (Appendix B in arXiv v5).
  - Throughputs are normalized to [0,1] per DAG.
  - The loss is squared error weighted by throughput, which emphasizes fast programs.
  - The model is retrained from scratch each time. The measured set is typically under 30,000 programs.

### Task scheduler (§6)

- **Units and objective.** One unit of time is one iteration: pick a task (subgraph), generate a batch of promising programs and measure them. For a single DNN, the objective `f` is the sum of subgraph latencies, each weighted by how often the subgraph appears.
  - Table 2 adds other objectives: a sum over several DNNs, a version with per-DNN latency targets (no time is spent once a target is met), the geometric mean of speedups against reference latencies, and per-task early stopping.
  - *The Table 2 formulas extract garbled and are omitted.*
- **Allocation.** After one round-robin warm-up, the scheduler picks the task with the largest |∂f/∂t_i|, using ε-greedy exploration. It estimates the gradient by mixing two predictions:
  - a backward one: the recent improvement over a window Δt;
  - an optimistic forward one: the latency the task would reach at the FLOP/s already achieved by similar tasks (FLOPs C_i, rate V_k over the similar set N(i)).
  - α and β weight these predictions. *The exact formula extracts garbled; arXiv v5 Appendix A derives it.*

## Limitations

Stated in the paper (§9):
- **Static shapes only.** Dynamic or symbolic shapes are left as future work.
- **Dense operators only.** Sparse operators such as SpMM would need a redesigned search space.
- **No special instructions.** Ansor optimizes at loop level and relies on LLVM and NVCC for platform-specific work, so it does not use Intel VNNI, NVIDIA Tensor Cores or ARM dot-product instructions for mixed- or low-precision operators.
- **Search cost.** Fully optimizing a DNN takes "several hours" per DNN (§7.4), and each new shape or hardware target needs a new search.

(Own analysis)
- Results depend on real on-device measurement. The paper does not cover measurement noise or sharing tuning devices across jobs.
- "Template-free" moves expert knowledge into a few hand-designed general rules rather than removing it.
- Static shapes plus no Tensor Core use is a poor fit for modern LLM serving, which has variable sequence lengths and batch sizes.

## Relation to other systems

- **AutoTVM / TVM:** AutoTVM searches inside per-operator templates written by hand. Ansor derives the space from rules, so there are no templates to maintain and fused subgraphs are covered. It reuses TVM only for lowering and code generation.
- **Halide auto-scheduler:** It scores and prunes incomplete programs with beam search. Ansor samples complete programs and then evolves them. The "Beam Search" variant in the Fig. 7 ablation stands in for this approach.
- **FlexTensor:** Its general templates work at single-operator granularity. Ansor's rules include tiling with fusion across a subgraph.
- **Tensor Comprehensions / Tiramisu (polyhedral compilers):** TC cannot beat TVM on conv2d or matmul, and Tiramisu needs manual scheduling (§8).
- **cuDNN / MKL-DNN / TensorRT:** These hand-tuned libraries are the baselines. (Own analysis) Ansor's advantage plausibly comes from subgraphs that the libraries neither fuse nor cover.

## Takeaways for practice

- (Own analysis) If your cost model is trained on finished artifacts, sample complete candidates and refine them. Do not score and prune partial ones. The same applies to placement and configuration search.
- (Own analysis) Treat the tuning budget as a scheduling problem. Ansor gives the next time slice to the job with the largest estimated marginal gain, with ε-greedy exploration. That maps directly onto sharing a GPU tuning or benchmark pool across many models.
- Weight the cost-model loss toward the region that matters (fast programs). While the data stays small (under 30K samples, §5.2), retraining from scratch is fine.
- (Own analysis) Measurement dominates the cost. Cache tuning logs by (shape, hardware) and reuse them across jobs.
- (Own analysis) Do not use Ansor for dynamic-shape serving or Tensor Core-bound kernels. Use libraries, kernel DSLs or newer schedulers there.
