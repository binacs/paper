# ByteCheckpoint: A Unified Checkpointing System for Large Foundation Model Development

> **Why it matters:** It stores a checkpoint as a parallelism-agnostic, globally indexed set of tensor shards, so any consumer (resumption on a new GPU count, post-training in another framework, a small evaluator) reshards at load time, while async pipelining and a tuned HDFS path keep training stalls under 1 s at 8,960 GPUs.

## Problem

In a production pipeline, checkpoints are used for more than failure recovery. They flow from pre-training to SFT/RL and are pulled constantly by automatic evaluation, and each consumer usually runs a different parallelism layout or framework. Over six months the platform logged 1,870 resharding events for resumption, 13,080 for cross-stage transitions and 19,844 for evaluation (Sec. 2.2). Before ByteCheckpoint each of these was an offline conversion job averaging 593–1,870 s (Table 1). Saving is expensive too: a GPT-175B checkpoint from 4,096 GPUs to HDFS can take about 200 s, longer than one iteration (Sec. 2.3). CheckFreq, Check-N-Run and Gemini assume the parallelism does not change. DCP and Megatron's MCP reshard at load time, but only for some parallelism strategies and frameworks, and their I/O does not scale (Sec. 2.3, App. F).

## Core design

### Decoupled representation (Sec. 3.2, Fig. 6–7)
- A tensor is keyed by its fully qualified name (FQN) and global shape. Each saved shard carries **ShardMeta = (fqn, nD_offsets, nD_lengths)**, its position in the global tensor, which is independent of the TP/PP/DP layout that wrote it. **BasicMeta** (stride, device) and **ByteMeta** (file, byte offset, length) complete the record.
- A single **global metadata file** maps shards to file byte ranges (`TensorShardToBasicByteMap`) and does the same for dataloader shards (`LoaderShardToByteMap`). Ranks write model, optimizer and extra-state files. Replicated dataloader state is saved once, and sharded token buffers are saved per rank so they can be resharded.
- **Irregular tensors.** ZeRO flatten-and-shard yields non-rectangular optimizer shards. DCP/FSDP all-gathers them through the CPU before saving. ByteCheckpoint splits each one into regular sub-pieces with their own ShardMetas, which takes communication off the save path.

### Architecture and workflow (Sec. 3.1, 3.3)
- `bytecheckpoint.save` / `bytecheckpoint.load` sit on three layers. Framework **Planners** (Megatron-LM, FSDP, DDP, veScale) emit ShardMetas. An agnostic **Execution Engine** runs the plans. **Storage I/O** backends cover memory, disk, HDFS and NAS. The code base is DCP-derived, about 20K lines of Python (Sec. 6).
- **Load-time resharding (Fig. 8).** Each rank reads the global metadata and intersects its new sharding spec with the saved ShardMetas to build a local plan. A coordinator gathers the plans, removes redundant reads and scatters them back. Ranks then load through a pipeline and finish with a barrier so the load is atomic. Dataloader token buffers are copied when only TP changes and split or merged when DP changes (Fig. 9).

### I/O optimizations (Sec. 4)
- **Balanced saving.** DCP and MCP make the first DP group write all replicated state. ByteCheckpoint assigns each replicated shard to the rank with the fewest accumulated bytes (worst-fit).
- **Redundancy-free loading.** Reads are split across DP replicas and redistributed via GPU all-to-all, which uses inter-GPU bandwidth that is idle during loading.
- **Plan/metadata cache.** Planning a 405B model on 8,960 GPUs took 62 s, so it happens once per session.
- **Async pipeline.** Saving runs D2H copy, then multi-process serialization, dump to shared memory and parallel upload. Loading mirrors it: read to /dev/shm, deserialize, H2D copy, all-to-all. A pinned host-memory pool with ping-pong buffers makes the blocking D2H step "almost negligible".
- **HDFS.** Multi-threaded random reads raise single-file reads from 400 MB/s to 2–3 GB/s. Writes go to fixed-size sub-files in parallel, merged by a metadata-only concat (about 3 GB/s per file). Dataloader state is prefetched during the step before a checkpoint, removing stalls of about 8 s.

### At scale (Sec. 5)
- On the storage side, the HDFS NameNode, DataNode and SDK were rewritten in C++ (about 2×). The NNProxy metadata proxy adds federation, rate limiting and caching. Capacity is hundreds of PB, with about 10 TB/s and about 100K metadata QPS. Old files are tiered from SSD to HDD.
- For control traffic, NCCL gather/scatter at 8,960 GPUs caused slow channel setup, hangs and OOM, and flat gRPC overloaded the coordinator. A machine-level tree of collectives following the TP-DP-PP structure replaced both.
- Monitoring records per-rank, per-phase timing and size, shown as heat maps (Fig. 11–12), with storage-side alerts in ClickHouse.

## Limitations

- **Baselines are compared on GPU state only**, because DCP and MCP do not save dataloader state. With dataloader state included, ByteCheckpoint's resharding can be slower than MCP's GPU-only figure (115.95 s vs 64.62 s at 4,800 GPUs, Table 4). Dataloader stragglers are left to future work.
- **The baselines were ported to HDFS by the authors**, with thread counts and chunk sizes matched. **ETTR is analytical** and assumes uniformly distributed failures.
- **Production loads take 130–266 s** (Table 8). Recovery time is bounded by durable storage, and the paper adds no in-memory or peer recovery tier.
- **Much of the I/O gain is HDFS-specific** (C++ rewrite, NNProxy, split-and-concat).
- **A new parallelism scheme needs a new Planner** that emits correct ShardMetas, and planning is still centralized (handled by caching).

## Relation to other systems

- **GEMINI (SOSP '23).** Checkpoints to local and remote host CPU memory with failure-aware placement and traffic interleaving, reporting >13× faster recovery (abstract). Its goal is fast same-layout recovery. ByteCheckpoint targets cross-layout portability on durable storage and uses GEMINI only as the basis for its ETTR model.
- **CheckFreq (FAST '21).** Two-phase snapshot/persist, online tuning of checkpoint frequency within 3.5% overhead, and a resumable data iterator (abstract). ByteCheckpoint applies similar async and dataloader-state ideas to 3D-parallel LFMs, but does not tune frequency.
- **PyTorch DCP.** The base ByteCheckpoint is built on. DCP has decoupled metadata and FSDP resharding, but no TP/PP planners, no fix for irregular shards, no writer balancing and no HDFS-grade I/O.
- **Megatron MCP.** Follows DCP's workflow with Zarr storage and is tied to Megatron. ByteCheckpoint's single format lets a Megatron checkpoint feed an FSDP job. DeepSpeed Universal Checkpointing likewise unifies the format but converts offline.
- **MegaScale (NSDI '24, same organisation).** Uses a two-stage save (GPU to host memory, then async upload to HDFS) and a single reader per DP group that broadcasts on recovery. ByteCheckpoint generalises both into balanced writers and split reads with all-to-all, and adds resharding.
- **ByteRobust (SOSP 2025, arXiv 2509.16293).** Its abstract covers fault detection, isolation and recovery, reporting 97% ETTR on a 9,600-GPU job over three months, and does not discuss checkpointing. ByteCheckpoint is the kind of state layer such a system relies on.

## Takeaways for practice

- Store checkpoints logically, as (FQN, global shape, n-D offset/length) plus a byte map. Resharding then becomes a metadata intersection, and offline conversion jobs disappear.
- Never all-gather to save. Split irregular ZeRO shards into regular pieces (Table 7).
- Balance writes across DP replicas, and on load split reads across replicas and redistribute over GPU interconnect (Table 5).
- Limit the blocking work to a pinned, double-buffered D2H copy, and cache plans. This is how stalls stay under 1 s at 8,960 GPUs.
- At 10K-GPU scale, the bottlenecks are in the control plane and storage metadata (NCCL control collectives, a single coordinator, NameNode concat, per-file metadata RPCs), not raw bandwidth.
- Treat dataloader state as part of the checkpoint and prefetch it. It is now the slowest part of resharding.
