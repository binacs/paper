# Mooncake: Trading More Storage for Less Computation — A KVCache-centric Architecture for Serving LLM Chatbot

> **Why it matters:** It makes the KV cache the unit of scheduling: spare CPU DRAM/SSD across a GPU cluster becomes an RDMA-connected, cluster-wide prefix cache beside disaggregated prefill/decode pools, showing at Kimi's scale (thousands of nodes, >100B tokens/day) that trading storage for prefill compute pays off.

(Preprint title: "Mooncake: A KVCache-centric Disaggregated Architecture for LLM Serving". FAST'25 Best Paper. FAST is the main source here; preprint-only material is marked.)

## Problem

A MaaS chatbot like Kimi wants maximum SLO-compliant throughput ("goodput") under TTFT (prefill) and TBT (decode) SLOs. Three pressures:

- **Long contexts.** Inputs are often 10–100× longer than outputs, and context windows grow from 8k toward 128k–1M. TTFT and prefill compute dominate cost (§3.3).
- **Reusable prefixes, small local caches.** Multi-turn chats and tool/agent system prompts share prefixes, but a per-node HBM/DRAM cache reaches only about half the theoretical hit rate (§2, §5.3).
- **Fixed GPUs under overload.** The system must reject, early, work it cannot serve within SLO (§2).

The bet: CPU, DRAM, SSD and RDMA NICs on GPU servers are underused; they can hold a far larger KV cache, and loading a prefix over RDMA beats recomputing it.

## Core design

### Architecture (Fig. 2–3)

Separate prefill and decode pools, a global scheduler (**Conductor**), and **Mooncake Store**, a KV pool over the GPU nodes' CPU DRAM/SSD. Per request:
  1. **KVCache reuse.** The prefill node loads matched prefix blocks from remote CPU memory.
  2. **Incremental prefill.** Only the uncached suffix is computed; new blocks go to CPU memory. Inputs above a chunk threshold ("typically larger than 1000 tokens", §3.1) are chunked and pipelined.
  3. **KVCache transfer.** KV streams layer by layer to the decode node, overlapped with prefill.
  4. **Decode.** The request joins a load-selected decode node's continuous batch; its local scheduler re-checks TBT SLO after prefill.

### Mooncake Store and the transfer engine (§3.2)

- **Blocks.** KV is stored as paged blocks of 16–512 tokens (256 in the evaluation). Each block is keyed by a hash of its contents *and its prefix* (a radix tree flattened into a hash map), enabling dedup; hot blocks get replicas.
- **Eviction.** LRU, never evicting a block that is in use.
- **API.** Object-level `put`, `get` and `change_replica`, built on batched transfer APIs (Listing 1). Sources and targets can be DRAM or GPU VRAM, using GPUDirect RDMA where available.
- **Transfer engine.** A per-server topology matrix ranks preferred/secondary NICs per memory type (Fig. 4); transfers are striped as 16 KB slices across NICs; endpoints are pooled with SIEVE eviction; failed links are rerouted to alternate NICs.

### Chunked pipeline parallelism for long prefill (§3.3)

- Cross-node TP needs per-layer RDMA all-reduces; SP (Ring/Striped Attention) needs per-layer exchanges that compete with KV transfer and hurt short requests.
- **CPP** groups every X prefill nodes into a pipeline. A request's tokens are split into chunks of at most `prefill_chunk`, and different chunks run on different stages at the same time. Communication happens only at stage boundaries and overlaps with compute. Short requests pay almost nothing, so groups need no dynamic repartitioning. No CPP-vs-SP measurement is given.

### Conductor scheduling (§4)

- **Cache-aware prefill placement (Algorithm 1).** For each prefill instance, Conductor:
  1. computes the block-level prefix match length;
  2. estimates TTFT = remote-load or transfer time + queue time + prefill time, with prefill time from a polynomial regression on input and cached length, fitted offline;
  3. picks the instance with the lowest estimated TTFT.
  
  If no prefill instance can meet the TTFT SLO, or the chosen decode instance cannot meet the TBT SLO, Conductor returns **HTTP 429** immediately.
- **Cache load balancing by hotspot migration (§4.2).** No popularity forecasting. If the best-matching instance is overloaded, the request goes elsewhere when fetching/recomputing there beats queueing; the receiver keeps a copy, so hot prefixes (system prompts) replicate as a side effect. Gated by a hand-tuned `kvcache_balancing_threshold`.
- **Overload-oriented scheduling (preprint §7, mostly cut from FAST).**
  - Load = SLO satisfaction (predicted max TTFT/TBT vs. SLO), not utilization.
  - **Early Rejection** moves the decode-side check to arrival, so prefill is not wasted on requests decode would reject.
  - This causes anti-phase P/D load oscillation (Fig. 9–10a), from the lag between admission and decode load materializing.
  - **Prediction-based Early Rejection**: assume uniform decode time t_d; project decode-pool TBT load at future t (add requests prefill finishes by t, drop completed ones) and admit on that. Per-request output-length prediction is future work.

## Limitations

- **Static P/D split.** Ratio is fixed (capacity peaks near 1:1, Fig. 15) and changed only on large load shifts; elastic systems switch roles dynamically.
- **Hand-tuned heuristics.** Manual migration threshold, offline prefill regression; transfer time under congestion is admittedly hard to predict.
- **Evaluation gaps.** CPP unmeasured; dummy LLaMA3-70B-shaped model; only vLLM v0.5.1 baselines (no DistServe/SGLang); overload results only in the preprint, as rejection counts.
- **Depends on reuse.** Gains track cache ratio (40–66% in traces, Table 2; preprint: ≤~50% reusable online). ~320 KB/token even with GQA makes the pool costly; compression is called orthogonal.
- **SSD tier uncharacterized.** Measurements cover DRAM+RDMA; no cross-tier eviction study.
- **Coarse rejection.** HTTP 429 only; no priorities, deferral or degradation.

## Relation to other systems

- **DistServe / Splitwise.** Established P/D disaggregation for goodput. Mooncake adds a cluster-wide KV pool and cache-aware placement, turning P/D into a storage/network problem, but keeps the ratio static where Splitwise allows role switching.
- **Sarathi-Serve (chunked prefill).** Co-locates P and D by piggybacking prefill chunks on decode batches; Mooncake argues this cannot hit full prefill MFU and tight TBT together. vLLM+chunked prefill used 1.90–3.33× Mooncake's prefill GPU time (Fig. 8).
- **SGLang RadixAttention / vLLM prefix caching.** Per-instance prefix reuse. Mooncake makes reuse global via a hashed block namespace plus match-length scheduling (the 1.38–2.36× hit-rate gain).
- **CachedAttention (AttentionStore).** Concurrent host/SSD hierarchy for multi-turn KV; Mooncake couples the cache with global placement, hot-block replication and RDMA P/D transfer.
- **LoongServe / Ring Attention (elastic SP).** Per-layer communication across GPUs for long sequences; CPP pipelines with stage-boundary traffic only, trading elasticity for simple, overlappable communication.
- **LMCache, NIXL, and SGLang HiCache (later ecosystem).** The open-sourced transfer engine and Store now back connectors for vLLM, SGLang and TensorRT-LLM (official repo): a reusable layer, not a Kimi-only stack.

## Takeaways for practice

- **Budget the KV cache as a cluster resource.** Size it in tokens against the hit-rate curve; one node's DRAM (~3M tokens) is far below the ~50M needed (Fig. 9).
- **Key blocks by prefix-inclusive hashes.** Dedup, replication and lookup without a central radix tree.
- **Schedule on estimated TTFT, not queue length.** Score hit length, location and transfer cost; global vs. local cache-aware placement cut average TTFT a further 14% (Fig. 5).
- **Replicate hot prefixes by migration.** Spilling overloaded hotspots to peers that keep a copy needs no popularity forecaster.
- **Plan for ≥100 Gbps of RDMA bandwidth** for KV transfer (congestion below that, Fig. 13); stripe across NICs topology-aware and overlap layer-wise with compute; TCP/Gloo are several times slower.
- **Admit by predicted SLO attainment across both stages.** Reject at arrival, before prefill burns GPU time, and project decode load forward to avoid P/D oscillation.
- **Use pipeline parallelism across nodes for long prefill** rather than cross-node TP/SP; it keeps short requests cheap and leaves NIC bandwidth for KV.
