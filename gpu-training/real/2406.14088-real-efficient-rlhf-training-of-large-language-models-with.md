# ReaL: Efficient RLHF Training of Large Language Models with Parameter Reallocation

> **Why it matters:** RLHF is a DAG of heterogeneous model function calls, and ReaL shows that letting parameters *move* between calls — each call getting its own device mesh and 3D-parallel strategy — is worth more than tuning any single global parallelization.

## Problem

PPO-style RLHF runs six model function calls over four LLMs per iteration: actor generation, reward inference, critic inference, reference inference, actor training, critic training (Sec. 2.1). They differ sharply in arithmetic intensity, memory footprint and sequential structure, yet prior systems fix one placement discipline for the whole iteration. The paper's profiling (Fig. 1) names two failure modes:

- **Symmetric** plans (DeepSpeed-Chat style: every LLM parallelized across the whole cluster with one strategy) over-parallelize small calls and pay heavy synchronization and collective-communication cost.
- **Asymmetric** plans (OpenRLHF style: disjoint GPU groups per LLM) run independent calls concurrently but idle GPUs whenever inter-call dependencies serialize the graph.

The missing degree of freedom, ReaL argues, is the location and shape of the parameters themselves.

## Core design

**Parameter reallocation between function calls.** The scheduling unit is a *model function call* — one task (generate / infer / train) on one LLM. Between two calls on the same LLM, ReaL may change both device mesh and parallel strategy, inserting an explicit redistribution step. In the searched plan for 70B actor + 7B critic (Table 2), actor generation runs TP=2, PP=4, DP=16 with 4 micro-batches while actor training on the same weights runs TP=2, PP=16, DP=4 with 2 micro-batches; the heuristic baseline (Table 3) uses TP=8, PP=4, DP=4 everywhere. The discovered pattern (Fig. 10–11) is systematic: for decoding prefer TP over PP (pipeline sync dominates when there is almost no work per step) and maximize DP within the memory budget; for training prefer larger PP with more micro-batches, trading bubbles for less TP traffic.

**Execution-plan representation.** The workflow becomes a dataflow graph 𝒢 = (𝒱, ℰ) whose nodes v_i^t are function calls indexed by call *and* iteration, with edges for data and parameter-version dependencies (Sec. 4) — spanning iterations so independent work from t+1 can overlap tail work of t. A plan assigns each call a device mesh D_i and a strategy S_i = (dp_i, tp_i, pp_i, mbs_i), the last being a micro-batch count for memory control. A mesh is a 2-D (N nodes × M devices) grid, constrained to span whole hosts or a slice evenly dividing one host — (1,1), (1,2), (1,4), (1,8), (2,8), …, (N,8) on an (N,8) cluster — so meshes tile the cluster and no GPU is stranded. The plan materializes as an augmented graph 𝒢_p with extra nodes for data transfer, parameter redistribution and host offloading. Any algorithm expressible as a DAG of such calls fits, not only PPO.

**Profiler-guided MCMC search.** Search runs against an estimator, not real runs (Sec. 5.1). A profiler measures per-layer forward/backward and communication times at power-of-two input sizes plus intra- and inter-node bandwidth, interpolating linearly. Time cost comes from a discrete-event simulation (Algorithm 1): a priority queue on ReadyTime, StartTime = max(ReadyTime, last completion on that mesh) — overlapping meshes mutually exclude — and TimeCost = max EndTime; transfer time is approximated as data size ÷ bandwidth rather than measured with NCCL. Memory is static (gradients, optimizer state) plus peak active (KV cache, activations, reallocable parameters); a plan is valid only if the per-device peak fits. The search is Metropolis–Hastings with P(p) ∝ exp(−β·cost(p)), cost = TimeCost times a large penalty α on OOM (Sec. 5.2). It starts from a greedy plan minimizing the sum of isolated call times, perturbs the mesh and strategy of one random call per proposal, accepts with min(1, P(p_new)/P(p_old)), and returns the lowest-TimeCost plan seen within a fixed time budget. The space is vast — over 500 options per call on an (8,8) cluster, >10^16 plans, >10^24 beyond 1000 GPUs — so pruning drops TP degrees above the per-node GPU count, plans underusing their mesh, and plans likely to OOM or communicate heavily (Fig. 14). The search is single-threaded but parallelizable (Sec. 8.2).

**Runtime engine and redistribution cost.** A centralized master worker runs on CPU with one asyncio coroutine per call, awaiting parents then issuing socket requests that carry only *data locations*; intermediate data never leaves the GPUs. One model worker per GPU serves RPCs, polling local model handles round-robin, FIFO per handle (Sec. 3, 6). Redistribution (Fig. 6) is a two-level broadcast: the outer loop remaps pipeline stages from pp₁ to pp₂, moving each stage pair's shared-layer parameters between the corresponding (dp₁, tp₁) and (dp₂, tp₂) sub-meshes; the inner loop has each destination GPU greedily pick the lowest-cost source (local preferred), with sources broadcasting TP shards in parallel. Host offloading uses a separate CUDA stream, and inter-call *data* transfer reuses the same machinery with TP/DP roles swapped, since outputs are DP-sharded and TP-replicated. The paper does not optimize this cost: it does "not focus on developing an optimal communication algorithm … as long as the cost is minor compared to other workloads in RLHF" (Sec. 6), and Sec. 8.2 reports these broadcasts take far less GPU time than the plotted kernel classes, so they are omitted from Fig. 11. No isolated latency figure for a reallocation appears anywhere.

## Limitations

Stated by the paper (Sec. 7):

- **Predictability is assumed.** Cost estimation needs predictable function calls; "an unstable cluster or dynamic workflow (e.g., the generation length varies significantly during training) can violate this assumption." The evaluation uses random data with *fixed* generation length "for fair comparison" (App. A) — the regime that hides this.
- **No optimality guarantee** for the MCMC search.
- Orthogonal to per-call kernel/serving optimizations (PagedAttention) and fusion approaches (RLHFuse): ReaL does not subsume them.

My own analysis, not claims the paper makes:

- *(my analysis)* Static-plan-centric — one plan searched before the run, then executed. Nothing re-plans mid-training, so drift in response length degrades the plan silently; AReaL attacks exactly this.
- *(my analysis)* Redistribution is never costed in isolation. "Minor" is asserted and supported only by exclusion from Fig. 11; higher reallocation frequency, smaller batches or a thinner fabric than 3.2 Tbps RoCE is where it should break first.
- *(my analysis)* The mesh constraint plus single-job assumption implies a dedicated cluster: no cluster-scheduler interaction, preemption, elasticity or multi-tenancy. Micro-batch counts and an OOM penalty also stand in for a real memory planner — the 128k-vocabulary softmax blow-up (~250 GB in one configuration) is handled by shrinking the critic.

## Relation to other systems

- **HybridFlow / verl** (Sheng et al., EuroSys 2025; arXiv 2409.19256). Its abstract frames RLHF as single-controller dispatch overhead vs. multi-controller inflexibility, mixes both behind hierarchical APIs decoupling computation from data dependencies, and adds a *3D-HybridEngine* resharding the actor between training and generation with no memory redundancy; 1.53×–20.57× over baselines. That resharding covers *one* model across *two* phases on the same device set; ReaL makes mesh+strategy a free variable for every call of every model and searches the assignment, observing that HybridEngine-style resharding "was limited to the actor model on the same device mesh". verl's contribution is programmability, ReaL's is plan search.
- **OpenRLHF** (Hu et al., EMNLP 2025 System Demonstrations; arXiv 2405.11143). Its abstract sells accessibility: a Ray + vLLM + DeepSpeed + HuggingFace stack, easy to use and documented, 1.22×–1.68× faster than other frameworks. Its placement model is the asymmetric failure mode ReaL profiles — separate GPU groups per model, vLLM for generation — so dependencies leave groups idle. A Fig. 7 baseline, not a competing mechanism.
- **DeepSpeed-Chat** (Yao et al., arXiv 2023; 2308.01320). Its abstract claims affordability and an end-to-end InstructGPT-replicating pipeline with combined training and inference optimizations. Architecturally the symmetric extreme: ZeRO-3 DP everywhere, with a Hybrid Engine flipping to TP for generation — the closest ancestor of parameter reallocation, the right idea applied to one model, one transition, one mesh.
- **RLHFuse** (Zhong et al., NSDI 2025, "Optimizing RLHF Training for Large Language Models with Stage Fusion"; arXiv 2409.13221). Its abstract targets two causes of idle GPUs — data skewness in generation (long-tail samples) and pipeline bubbles in training — decomposing work into sample-level subtasks for generation/inference and micro-batch subtasks for training under a fused pipeline schedule; up to 3.7×. ReaL calls it "an orthogonal extension" to special cases of PPO: RLHFuse makes a *given* schedule denser, ReaL changes where and how each stage is parallelized. Composing the two is left undone.
- **AReaL** (Fu et al., NeurIPS 2025; arXiv 2505.24298), same group. Its abstract diagnoses synchronous RL as wasteful because each batch waits for its longest generation, and fully decouples the two: rollout workers generate continuously, training workers update whenever enough data arrives, with workload balancing to bound staleness and a modified PPO objective tolerant of stale samples; up to 2.77× at equal GPU count. It answers ReaL's own stated assumption — ReaL optimizes the *shape* of a synchronous iteration under predictable costs, AReaL removes the synchronous iteration.

## Takeaways for practice

- **Treat an RL/RLHF iteration as a DAG of heterogeneous tasks, not one job.** Per-task optima diverge (TP-heavy, DP-wide for decoding; PP-heavy with many micro-batches for training); one global (dp, tp, pp) left >50% on the table here.
- **Parameter movement is a scheduling primitive.** If weights reshuffle cheaply relative to compute, placement becomes a variable rather than a constraint — but measure that on your own interconnect instead of inheriting the assumption.
- **A cheap, ranking-faithful cost model beats a precise one.** Sub-25% error with preserved ordering at hundreds of µs per candidate drives a 10^16-plan search.
- **Penalize, don't filter, in constrained search spaces:** seed greedily, prune structurally, cap by wall-clock, and report time-to-95% as well as time-to-optimum.
- **Static planning assumes a stationary workload.** If sequence lengths or cluster health drift, re-plan periodically or go asynchronous.
- **Use memory utilization as a scale-out stop signal;** generation's sequentiality floors strong scaling whatever the plan.
