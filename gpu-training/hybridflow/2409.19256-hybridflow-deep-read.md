# HybridFlow: A Flexible and Efficient RLHF Framework

> **Why it matters:** It shows that an RLHF system can keep a single-controller's flexibility at the dataflow level while keeping multi-controller efficiency inside each model, and that the training↔generation weight reshard — not the arithmetic — is the thing worth engineering.

## Problem

RLHF is not one training job but a small dataflow graph over several LLMs: the actor generates responses, the critic/reference/reward models score them, then actor and critic are trained. The nodes have very different shapes. Generation is memory-bound and favours small tensor-parallel degrees and many replicas; training is compute-bound and favours 3D parallelism. The same actor weights must live under both layouts inside one iteration, and for a 70B actor that means moving on the order of 140 GB of parameters per iteration (§2.3).

Existing systems sit at one of two extremes. Single-controller RL frameworks (RLlib, RLlib Flow) express arbitrary dataflow cheaply, but their primitives assume data parallelism and small networks, and dispatching every operator from one controller to hundreds of accelerators is expensive (§1). Multi-controller RLHF systems — DeepSpeed-Chat, OpenRLHF, NeMo-Aligner — are efficient inside a model but hard-code the dataflow: computation, collectives and point-to-point transfers are interleaved in each worker's script, so changing one node forces edits in every dependent node (§1, §2.5). They also fix a placement: DeepSpeed-Chat colocates everything and pays a full-cluster reshard; OpenRLHF puts models on disjoint GPU groups, so every model but the actor idles during generation (§2.4).

## Core design

### Hybrid programming model

HybridFlow splits the two paradigms by level (§3). A **single controller** owns the inter-node dataflow: the RLHF algorithm is ordinary Python that calls `actor.generate_sequences()`, `reward.compute_reward()`, `critic.compute_values()`, `actor.update_actor()` in sequence. A **multi-controller** runtime owns intra-node computation: each model is a set of workers running SPMD code reused almost verbatim from Megatron-LM / FSDP training scripts.

The glue is a per-API **transfer protocol**. Each model method is annotated with `@register(transfer_mode=...)`, where a protocol is a pair of *collect* (gather worker outputs for the controller) and *distribute* (scatter controller data into each DP group) functions. Eight protocols ship, including `3D_PROTO`, `DP_PROTO` and `ONE_TO_ALL`, and users can add their own (§3, Appendix B). This is what decouples a node's internal parallelism from the dataflow: swapping the actor from 3D parallelism to FSDP changes the worker base class, not the algorithm script.

Worker classes form a shallow hierarchy — `ParallelWorker` → `3DParallelWorker` / `FSDPWorker` / `ZeROWorker` — with actor, critic, reference and reward model classes on top (§4.1). Devices are virtualised by a **ResourcePool**: models sharing a pool are colocated and execute sequentially in call order; models on different (non-overlapping) pools run asynchronously as soon as their inputs are ready (§4.1). Consequently the *same* algorithm script runs colocated or split — placement is a resource-binding decision, not a code change.

The claimed payoff is code size: PPO in roughly 8 lines, Safe-RLHF as ~5 more lines, ReMax as one extra generation call with the critic removed (§4.2). The framework itself is ~12k lines of Python: 1.8k for the hierarchical APIs, 2.4k for the 3D-HybridEngine, 1.9k for auto-mapping (§7).

### 3D-HybridEngine: zero-redundancy resharding

Actor training uses parallel sizes (p, t, d); generation uses (p_g, t_g, d_g) with d_g = pt/(p_g t_g), so that N_a = p·t·d = p_g·t_g·d_g·d (§5.1). Each training DP replica is split into d_g **micro DP groups** for generation, which is how generation gets a larger effective DP degree without re-sharding across the whole cluster.

The trick is *which* ranks form the generation groups (§5.3). Vanilla grouping (called HybridFlow-V) builds generation TP/PP groups from contiguous ranks, so on many devices the generation shard does not overlap the training shard and a second copy of weights must be materialised. HybridFlow instead forms generation TP and PP groups from ranks at strides t/t_g and p/p_g, and forms micro DP groups from the consecutive ranks along the generation TP/PP dimension. Then every device's generation shard is a superset of a chunk it already holds, the all-gather is confined to a micro DP group, and no redundant training-weight copy is kept.

Table 2 gives the analysis: communication volume drops from (tpd−1)/(tpd)·M (DeepSpeed-Chat, all-gather across the cluster) to (tp−1)/(tp)·M (HybridFlow-V) to (tp − t_g p_g)/(t_g p_g tp)·M = (d_g−1)/(tp)·M (HybridFlow); peak parameter memory drops from M to M/(t_g p_g); redundancy goes from (1/tpd)·M and (1/tp)·M to **0**.

### Auto device mapping

Given the dataflow graph, model specs, workload, N GPUs and per-GPU memory Q, Algorithm 1 enumerates placements (Bell number — 15 for PPO's four models), computes a minimum allocation per colocated set that avoids OOM (`get_min_alloc`), enumerates feasible allocations, and for each model searches a parallelism strategy via an `auto_parallel` module backed by a simulator (§6). Latency is summed within a colocated set and maximised across concurrent sets, and the lowest end-to-end iteration latency wins. Worst-case cost is O((N−1)!/((k−1)!(N−k)!)) for k models, tamed by caching per-model strategy searches.

## Limitations

The execution model is synchronous and batched: colocated models run sequentially to avoid contention and OOM, so within a stage a long-tail generation holds the whole batch (§9). There is no fine-grained GPU sharing between colocated models, which the paper lists as future work. Auto-mapping assumes homogeneous GPUs and a non-overlapping partition of the cluster; heterogeneous devices are explicitly out of scope (§9). The simulator-driven search optimises per-iteration latency under an assumed, uniform response length — the evaluation itself enforces equal response lengths for fairness because baselines may lack continuous batching, and optimizer-state offloading is disabled (§8.1). Fault tolerance is handled by conventional checkpointing and declared orthogonal; it is not evaluated (§9). The experiments use equal-size actor/critic/reference/reward models (one placement study aside), so cost models for strongly asymmetric model sets are only lightly exercised.

## Relation to other systems

**OpenRLHF** (arXiv 2405.11143) is the closest open-source contemporary: Ray + vLLM + DeepSpeed, with models placed on disjoint GPU groups. That removes resharding inside one model's lifetime but leaves non-actor models idle during generation and pays ZeRO-3 weight-sync traffic across machines; HybridFlow measures up to 89.1% less transition overhead than it (§8.2). OpenRLHF's own abstract claims 1.22×–1.68× over prior frameworks, i.e. a different order of ambition than HybridFlow's placement+reshard co-design.

**ReaL** (arXiv 2406.14088, MLSys 2025) attacks the same mismatch from the other side: instead of a hybrid engine specialised to actor train↔generate, it makes *parameter reallocation* the first-class primitive and searches "execution plans" (allocation + parallelism per stage) with a runtime estimator, reporting up to 3.58× over baselines on Llama up to 70B / 128 GPUs. Conceptually ReaL's plan search generalises HybridFlow's Algorithm 1; HybridFlow's contribution is the redundancy-free grouping that makes one specific reshard nearly free.

**RLHFuse** (arXiv 2409.13221, NSDI 2025) rejects the model-as-atomic-task view that HybridFlow's dataflow graph assumes. It splits generation into sample-level subtasks to overlap generation with inference, and training into micro-batch subtasks under a fused pipeline schedule, targeting long-tail sample skew and pipeline bubbles — exactly the two inefficiencies that HybridFlow's synchronous, stage-serialised execution leaves on the table; it reports up to 3.7× over existing systems.

**AReaL** (arXiv 2505.24298, NeurIPS 2025) and **StreamRL** (arXiv 2504.15930) push further, to asynchrony and disaggregation. AReaL decouples rollout from training workers with staleness control and a staleness-aware PPO, reporting up to 2.77× over synchronous systems at equal GPU count — a direct challenge to the batched loop HybridFlow optimises. StreamRL argues disaggregation, not colocation, is the right base: it names pipeline bubbles and skewness bubbles as the costs of existing disaggregated frameworks, adds stream generation and an output-length ranker with skewness-aware dispatch, and claims up to 2.66× throughput and 1.33× cost-effectiveness across datacenters. Both reframe HybridFlow's placement question (colocate vs split *within* a synchronous iteration) as a question of whether the iteration boundary should exist at all.

## Takeaways for practice

- Separate *dataflow control* from *intra-model execution*. A single controller over a handful of model nodes costs nothing at RLHF's graph size, and buys you algorithm changes (PPO → Safe-RLHF → ReMax) that touch only the driver script.
- Make per-API transfer protocols explicit. Collect/distribute pairs are what let a node's parallelism change without touching callers; without them, parallelism leaks into the algorithm.
- Budget for weight movement, not just FLOPs. The reshard between training and generation layouts is the dominant non-compute cost for 70B actors; choosing rank groupings so that generation shards overlap training shards removes both the extra memory copy and most of the traffic.
- Treat placement as a searched parameter with a cost model, and cache the per-model parallelism search. The best answer flips with scale — colocate everything at 16–64 GPUs, split or go standalone at 96–128 (§8.3) — so hard-coding one layout is wrong at some cluster size.
- Generation parallelism should be tuned independently of training parallelism, and smaller is not monotonically better: TP size has an optimum set by KV-cache pressure per GPU (Fig. 15).
- The synchronous-batch assumption is the next thing to question. If your rollout length distribution is long-tailed (reasoning, agentic traces), the later asynchronous/disaggregated designs address a bottleneck this architecture does not.
