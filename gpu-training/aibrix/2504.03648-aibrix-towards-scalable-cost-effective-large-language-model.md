# AIBrix: Towards Scalable, Cost-Effective Large Language Model Inference Infrastructure

> **Why it matters:** It is an open-source, Kubernetes-native control plane built to sit around vLLM rather than replace it, and it bundles the cluster-level pieces (LoRA placement, cache-aware routing, LLM-aware autoscaling, a shared KV cache tier, heterogeneous-GPU planning, accelerator fault tooling) that most teams otherwise assemble ad hoc.

## Problem

Engines (vLLM, TensorRT-LLM) optimise a single replica. Production serving also needs a system layer: autoscaling, cache-aware routing, multi-tenant adapters, heterogeneous hardware (§1). The paper argues existing layers do not fit LLM traffic (§2). Knative and Istio scale on QPS or concurrency, rate-limit with circuit breakers that cannot express token budgets, and add mesh overhead. KServe and Ray Serve host LLMs but lack batch scheduling, KV-cache coordination and heterogeneous-GPU optimisation. Specific pain points: DCGM metrics and QPS do not track GPU-bound LLM load, scaling is non-linear, and a new pod takes 2–3 minutes to become ready because of large images and slow model distribution (§3.2.4). Per-node prefix caches are bounded by local memory and cannot share or migrate KV (§3.2.5). Llama-3.1-405B and DeepSeek-R1 need multi-node serving, where vLLM focuses on parallelism, not scaling or rolling upgrades (§3.2.6).

## Core design

**Split (§3.1, Fig. 1).** The *control plane* holds model-metadata registration, autoscaling, adapter registration and policy enforcement. Its components are a LoRA Adapter controller, a RayClusterFleet controller for multi-node vLLM, the AI Runtime sidecar, a Cold Start Manager (tracks model artifacts across DRAM, local disk and cloud storage) and the LLM-Specific Autoscaler. The *data plane* has the API Gateway (fairness, rate limits, KV-locality routing), Serving Units (engine pod + AI Runtime sidecar) and a distributed DRAM-based KV cache runtime. Everything runs as Kubernetes controllers/CRDs around vLLM (with vLLM-side LoRA enhancements, §3.2.1).

**High-density LoRA management (§3.2.1, Fig. 2).** Adapters are registered, loaded and unloaded dynamically onto shared base-model pods, with discovery via Kubernetes Service/EndpointSlice. The public docs describe a `ModelAdapter` CRD (`model.aibrix.ai/v1alpha1`) (`baseModel`, `podSelector`, `artifactURL`). The controller creates a Service per adapter, lets one pod belong to several Services, and registers the adapter with vLLM via the runtime sidecar (docs, not paper). The paper gives no density or cost numbers.

**LLM-aware gateway and routing (§3.2.2, Fig. 3).** The gateway extends Envoy Gateway, weighs token patterns, prefill-cache availability and compute overhead, and accepts custom strategies. Built-ins: `random`, `throughput` (the instance with the lowest tokens/s), `least-request`, `least-kv-cache` (lowest average KV utilisation), `least-latency` (lowest queuing + serving latency) and `prefix-cache-aware` (prefer instances whose cache hit exceeds a threshold). "Least-GPU-memory" is mentioned but not listed.

**Unified AI runtime and GPU streaming loader (§3.2.3, Fig. 4).** A vendor-agnostic sidecar between control plane and engine handles model management, engine configuration and metrics, coordinating with the adapter controller, autoscaler and cold-start manager. §1 says the streaming loader bypasses disk I/O when loading weights. §3.2.3 gives no mechanism for it.

**LLM-specific autoscaling (§3.2.4).** The autoscaler bypasses the Kubernetes custom-metrics pipeline and keeps sliding-window aggregation of engine metrics (for example KV-cache utilisation) inside itself. §3.1 claims this gives "millisecond-level" scaling. Policies are pluggable: KPA (Knative-style) and APA (AIBrix's own), compared against native HPA. Per the docs, this is a `PodAutoscaler` CRD with `HPA`/`KPA`/`APA` strategies. KPA has stable/panic windows; APA uses tolerance bands. Token-based proactive scaling and SLO-driven scaling are listed as future work.

**Distributed KV cache pool (§3.2.5, Fig. 5, Table 1).** A DRAM pool outside the engine enables KV reuse across nodes and engines for multi-turn chat and agent traffic, via scan-resistant eviction (retain hot KV), asynchronous metadata updates, and cache–engine colocation over shared memory. It is framed as the base for KV migration and P/D disaggregation.

**Mixed-grain multi-node orchestration (§3.2.6, Fig. 6).** Kubernetes does coarse-grained resource management; Ray does fine-grained application orchestration inside a multi-node vLLM instance, managed by the RayClusterFleet controller. Goals: a simpler operator and room for P/D disaggregation.

**SLO-driven heterogeneous serving (§3.2.7, Fig. 8).** An off-path loop: a *Load Monitor* reads gateway statistics for the dominant workload pattern; a *GPU Optimizer* solves a Mélange-inspired ILP over offline profiles (AIBrix ships profiling tools) for the GPU mix balancing cost and SLO; the *Pod Autoscaler* reads its output as an external MetricSource and adjusts per-GPU-type replicas. The ILP itself is not given.

**Accelerator diagnostics and failure mock-up (§3.2.8, Fig. 9).** Diagnostics use accelerators' built-in capabilities (§1) to catch GPU faults early; a mock-up tool simulates GPU failures (NVIDIA, Ascend 910B) to test framework recovery. Signals and injection method are not described.

## Limitations

- *Stated by the paper (§4):* routing and heterogeneous serving are not fully evaluated under non-ideal workloads, so the results may not generalise. The GPU optimiser and profiling-based scaling depend on offline profiling, which may not suit dynamic workloads. Roofline-based profiling is proposed as a lighter alternative.
- *Stated by the paper (§3.2.7):* the Load Monitor assumes each model deployment uses distinct GPUs, so the optimiser does not consider GPUs shared across models.
- *Our analysis:* a system overview, not a controlled evaluation: routing and autoscaling numbers name no baseline policy, model, trace or cluster size; the KV experiment names no model and uses one 4× A10 setup.
- *Our analysis:* the Table 1 workload is heavily prefill-bound (~1.08M prompt tokens vs ~12.7K decode tokens), which favours a prefix-reuse tier. The gains on decode-heavy traffic are untested.
- *Our analysis:* the rounded figures in the text understate Table 1 in places. The text says ~60% for average TTFT, while the table shows 65.06%. The abstract's "70% reduction in inference latency" does not say which latency metric.
- *Our analysis:* no head-to-head comparison with other cluster-level systems (Llumnix, Mooncake, production-stack/LMCache, KServe). Pool consistency, failure handling, fabric and sizing are not described; the streaming loader, diagnostics and ILP are only described functionally.

## Relation to other systems

- **Llumnix (OSDI 2024):** live-migrates in-flight requests and their in-memory state across instances to handle load balance, isolation, fragmentation and priorities. AIBrix routes once at admission and does not migrate; KV migration is only a future use of its pool.
- **Mooncake (FAST 2025):** Kimi's KVCache-centric design separates prefill and decode clusters, builds a KV store from idle CPU/DRAM/SSD/NIC, and schedules around it under SLOs. AIBrix's DRAM pool targets the same cross-node reuse but as an add-on to colocated vLLM pods, without disaggregation or KV-centric scheduling.
- **DistServe (OSDI 2024):** puts prefill and decode on separate GPUs and co-optimises per-phase parallelism and placement for goodput under TTFT/TPOT SLOs. AIBrix only positions P/D disaggregation as future work; its optimiser picks GPU types per workload, not per phase.
- **KServe / Gateway API Inference Extension (official docs):** KServe's `InferenceService` CRD gives generic serving with KPA/KEDA scaling and vLLM/llm-d backends. The Inference Extension adds an `InferencePool` and an Endpoint Picker plugged into gateways (e.g. Envoy Gateway via ext-proc), routing on model-server metrics, prefix-cache state and LoRA availability. AIBrix's Envoy gateway is a vertically integrated take on the same idea (the paper cites the extension), plus its own autoscaler, KV tier and GPU planner.
- **vLLM production-stack (official README):** a Helm reference stack of vLLM engines, a router (round-robin, session-ID, prefix-aware in progress), observability and LMCache offload, with autoscaling and P/D on its roadmap. AIBrix adds controllers (adapters, autoscaling, Ray fleets) plus heterogeneous-GPU and fault tooling.

## Takeaways for practice

- Autoscale on engine signals (e.g. KV utilisation) aggregated inside the scaler; with 2–3 min cold starts, damping oscillation matters as much as speed.
- Route on LLM state (prefix hits, KV utilisation), not connection counts; it is cheap at an Envoy/ext-proc layer.
- A shared DRAM KV tier helps most without engine prefix caching; on top of it the gain is ~1.5× throughput on a reuse-heavy trace. Measure your own reuse ratio first.
- Heterogeneous GPU mixes cut cost when SLOs have slack; keep the solver off-path and feed it to the autoscaler as an external metric.
- For multi-node models, split coarse resources (K8s) from intra-instance placement (Ray) rather than forcing both into one operator.
- Build accelerator fault injection early; serving recovery paths are rarely exercised.
