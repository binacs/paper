# Efficient Memory Management for Large Language Model Serving with PagedAttention

> **Why it matters:** It turned the KV cache into a paged, OS-style managed resource (fixed-size blocks plus per-sequence block tables), which raised the effective batch size of LLM serving and became the default memory model for vLLM and most engines that followed.

## Problem

LLM decoding is memory-bound. Throughput depends on how many requests fit in one batch, and that is bounded by KV cache capacity, not FLOPS. On a 13B model on an A100-40GB, weights take about 65% of memory and the KV cache close to 30% (Fig. 1). For OPT-13B one token's KV cache is 800 KB (2 × 5120 hidden × 40 layers × 2 bytes), so a 2048-token sequence can need 1.6 GB (§3).

Earlier systems (FasterTransformer, Orca) store each request's KV cache in one contiguous tensor sized for the maximum possible sequence length (§3). This wastes memory three ways (§3.1):

- **Reservation:** slots held for future tokens that are not yet generated.
- **Internal fragmentation:** slots reserved past the request's real output length, which are never used.
- **External fragmentation:** gaps between contiguous chunks left by the allocator.

Compaction is impractical at KV-cache scale (§3). In the paper's measurements, only 20.4%–38.2% of KV cache memory in existing systems holds actual token state (§1, Fig. 2). Contiguous layout also blocks sharing: parallel samples and beam candidates each get a private copy of the same prompt KV.

## Core design

### PagedAttention and blocks (§4.1–4.3)
- The KV cache of each sequence is split into fixed-size **KV blocks** of B tokens, "like pages in virtual memory" (§4.2). Blocks do not need to be contiguous in GPU memory.
- The attention kernel "identifies and fetches different KV blocks separately" (§4.1) and computes attention block by block, so no contiguous KV tensor is needed.
- **Block tables** map each sequence's logical blocks to physical blocks and record how many slots of each block are filled (§4.2). A new physical block is allocated only when the last logical block is full (Fig. 6). This caps a request's waste at one partially filled block (§4.3).
- The KV cache manager (block engine) pre-allocates GPU memory as a pool of physical blocks. A separate CPU block allocator manages blocks swapped out to host RAM (§4.5).
- Default block size is 16 (§7.2).

### Iteration loop (§4.3)
Scheduling is at iteration level, Orca-style. In each step the scheduler picks the sequences to run and allocates any physical blocks they newly need. It then concatenates all input tokens of the iteration (whole prompts for prefill-phase requests, the latest token for decode-phase requests) into one sequence for the model.

### Sharing with copy-on-write (§4.4)
- **Parallel sampling:** all samples map their prompt logical blocks to the same physical blocks, each with a reference count. When a sample first writes into a shared block, vLLM copies the block (copy-on-write at block granularity) and lowers the reference count.
- **Beam search:** candidates share blocks across a tree, not only the prompt. When a beam is dropped, blocks whose reference count reaches 0 are freed. New candidates get new blocks (Fig. 9, k=4). Prior systems copy whole KV caches between beams. vLLM copies at most one block.
- **Shared prefix:** the provider can reserve physical blocks for a predefined system or few-shot prefix and map user prompts onto them, as with shared libraries in an OS. This is static, operator-defined sharing, not automatic cross-request prefix caching.
- The interface to decoding algorithms is `fork` (new sequence from an existing one), `append` (add a token) and `free` (delete a sequence) (§5).

### Scheduling and preemption (§4.5)
- **FCFS** for all requests. When blocks run out, the most recently arrived requests are preempted first.
- **All-or-nothing eviction:** either all of a sequence's blocks are evicted or none are, because every token's KV is needed at each step. A sequence group (beam candidates, parallel samples) is gang-scheduled, so it is preempted and rescheduled as a unit.
- There are two recovery paths:
  - **Swapping:** evicted blocks move to CPU RAM. Swap space is bounded by the GPU KV allocation.
  - **Recomputation:** the KV cache is dropped and rebuilt later by treating prompt plus generated tokens as a new prompt. Because that prompt is processed in one parallel prefill, recomputing is faster than the original decode. Recomputation has no OS equivalent (§8).
- Preempted sequences are not scheduled again until running ones finish and free blocks.

### Distributed execution (§4.6)
- Megatron-LM-style tensor parallelism. A single KV cache manager sits in a centralized scheduler, and all GPU workers share one logical-to-physical mapping. Each worker stores only the KV of its own attention heads.
- In each step the scheduler sends the token IDs and block tables to the workers. The workers run the model, synchronize with all-reduce and "do not need to synchronize on memory management" (§4.6).

### Implementation and kernels (§5)
- About 8.5K lines of Python (scheduler, block manager) and 2K lines of C++/CUDA, with a FastAPI frontend that serves an OpenAI-compatible API.
- There are three custom kernels:
  - fused reshape plus block write of new KV;
  - fused block read plus attention, adapted from FasterTransformer, with one warp per block;
  - fused, batched block copy for copy-on-write, so many small copies become one kernel launch.

## Limitations

- **Indirection cost:** block-table lookups make the attention kernel 20–26% slower than FasterTransformer's (§7.1). The paper argues this matters little because only attention is affected. §8 states that compute-bound or static-shape workloads, such as training, may not gain from paging.
- **Preemption is coarse:** FCFS, evicting latest arrivals first, all-or-nothing per sequence group. There is no SLO- or priority-aware scheduling, no fairness and no admission control.
- **Swap vs recompute is a tuning problem:** swapping is slow at small block sizes because of many small PCIe transfers, and recomputation does not depend on block size (§7.3). The paper evaluates both but gives no adaptive policy.
- **Sharing is limited:** shared prefixes are reserved ahead of time by the provider (§4.4). In the chatbot experiment the KV cache is not kept between conversation rounds (§6.5). Automatic, content-addressed prefix reuse across requests is left to later systems.
- **Prefill and decode interference is not addressed:** long prompts batched with decodes in one iteration (§4.3) can stall token generation. This later motivated chunked prefill.
- **Scope:** single-node tensor parallelism with a centralized scheduler. There is no pipeline parallelism across nodes, no prefill/decode disaggregation and no KV tier beyond CPU swap. Orca baselines are modeled through reservation assumptions (Oracle, Pow2, Max), not run as the original system (§6.1).

## Relation to other systems

- **Orca (OSDI '22):** contributes iteration-level scheduling and selective batching, which vLLM adopts (§2.3). vLLM calls the two complementary (§9): Orca decides *when* requests join a batch, PagedAttention decides *how many* fit. vLLM's gains over Orca come from memory utilization, not from scheduling.
- **FasterTransformer:** a latency-optimized inference engine without fine-grained (iteration-level) scheduling and with contiguous, max-length KV reservation. vLLM reuses its attention kernel as a starting point (§5). It beats FasterTransformer on throughput by up to 22× in request rate (§6.2) but loses 20–26% on raw attention-kernel latency (§7.1).
- **SGLang / RadixAttention (abstract only):** builds on paged KV but keeps KV after requests finish in a radix tree for automatic reuse across calls in multi-call LLM programs. It reports up to 6.4× throughput over prior systems. It generalizes vLLM's static shared-prefix mechanism into an LRU-managed cache.
- **Mooncake (abstract only):** Kimi's serving platform. It disaggregates prefill and decode clusters and pools CPU DRAM and SSD into a distributed KV cache with a KV-aware scheduler and early rejection. In vLLM, KV is per-GPU working memory; in Mooncake it is a cluster-level asset that scheduling is built around.
- **Sarathi-Serve (OSDI '24, abstract only):** tackles the prefill/decode interference that vLLM's batching leaves open. It uses chunked prefill and stall-free batching and reports up to 2.6×–5.6× serving capacity over vLLM under tail-latency SLOs. It keeps paged KV and changes the iteration composition.

## Takeaways for practice

- KV capacity, not compute, sets decode batch size. Measure KV *utilization* (token state vs reserved) as a first-class metric. Reservation and fragmentation can waste most of the KV memory (Fig. 2).
- Allocate KV on demand in small fixed blocks behind an indirection table. Bounding waste to one block per sequence is what converts memory into batch size.
- Reference-counted blocks with copy-on-write make sampling-heavy workloads (n>1, beam search, agents forking from a shared context) much cheaper. Design APIs around fork/append/free.
- Plan preemption explicitly. Evict whole sequence groups, and choose swap or recompute based on block size and PCIe bandwidth. At small blocks, recomputation is competitive (§7.3).
- A centralized block manager with stateless TP workers keeps memory management off the communication path: the control plane owns the block tables, the data plane only executes.
- Paging alone is not a scheduler. Pair it with chunked prefill (Sarathi-Serve), prefix caching (SGLang) and KV tiering or disaggregation (Mooncake) for SLO-bound or long-context serving.
