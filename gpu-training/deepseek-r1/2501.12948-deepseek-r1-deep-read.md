# DeepSeek-R1: Incentivizing Reasoning Capability in LLMs via Reinforcement Learning

> **Why it matters:** It shows that large-scale RL with only rule-based, verifiable rewards on a 671B MoE base can produce long chain-of-thought reasoning. That makes "generate long rollouts, then score them cheaply" a first-class training workload, which RL infrastructure has to be built around.

Version note: arXiv v1 (22 Jan 2025) is the original report. v2 (4 Jan 2026) is the expanded version matching the Nature paper (journal-ref: Nature 645, 633–638, 2025). Unless marked "v1", sections, tables and numbers below come from v2. I could not read v2's later appendices (D–J) in the fetched text, so the distillation result tables are cited from v1.

## Problem

Earlier post-training for reasoning relied on human-annotated chain-of-thought traces, supervised fine-tuning (SFT), or learned reward models (outcome or process). The paper asks whether reasoning can be incentivized by RL alone, with no human reasoning traces, if the reward is just "is the final answer verifiably correct and well formatted." It also asks how to turn the result into a usable general model (DeepSeek-R1), and how to transfer it to small dense models.

## Core design

### GRPO as the policy optimizer (Sec. 2.1, App. A.3)
- **No critic.** For each question, GRPO samples a group of outputs from the old policy. Each output's advantage is its reward normalized by the group's mean and standard deviation (Eq. 3). The paper's motivation is to cut PPO's cost: the PPO value model "is usually of similar size as the policy model" and adds "significant memory and computational overhead". Learning values is also hard when only a final outcome reward exists.
- **KL placement.** An unbiased KL estimator is added directly to the loss, not as a dense per-token reward as in PPO (App. A.3).
- **Reference model refresh.** The reference model is replaced with the latest policy every 400 steps (Sec. 2.1, 3.2.1).
- **PPO comparison** (Fig. 4, DeepSeek-Coder-V2-Lite, 16B MoE): with GAE λ = 0.95, PPO is "considerably worse" than GRPO. Tuned to λ = 1.0, PPO comes close to GRPO.

### Rewards (Sec. 2.2, 3.1, 3.2)
- **R1-Zero rewards are rule-based only.**
  - Accuracy reward: answer checking for math, and compiler plus predefined test cases for code.
  - Format reward: the reasoning must sit inside designated think tags.
  - The two are combined with equal weight.
  - Neural reward models are not used for reasoning: they are "susceptible to reward hacking during large-scale reinforcement learning", and retraining them is costly.
- **Language-consistency reward** (Sec. 3.2.1): the proportion of target-language words in the chain of thought. It slightly degrades benchmark scores, mostly code (App. B.6), and is kept for readability.
- **Second RL stage** (Sec. 3.2.2, Eq. 8–10):
  - Reasoning prompts keep the rule-based rewards.
  - General prompts use a helpful reward model and a safety reward model (Sec. 3.1) plus the format reward.
  - The language-consistency reward is added on top.

### Training pipeline (Sec. 3, App. B.3)
1. **R1-Zero:** pure RL directly on DeepSeek-V3-Base. A minimal template asks for reasoning, then answer.
2. **R1:** cold start on "thousands" of conversational, human-aligned long chain-of-thought examples, then:
   - a first RL stage focused on reasoning;
   - rejection sampling plus SFT on about 600k reasoning and about 200k non-reasoning samples (about 800k total, App. B.3.3 / Table 5);
   - a second RL stage for helpfulness and harmlessness.
   - The intermediate checkpoints are reported as Dev1, Dev2 and Dev3 (Table 3).
3. **Distillation:** plain SFT of Qwen2.5 and Llama bases on the 800k R1-generated samples, with no RL (App. B.4.3, Table 6).

### RL infrastructure (App. B.1)
The paper calls the framework "decoupled and extensible", with four modules that run in phases:
- **Rollout:**
  - Prompts are dispatched uniformly across multiple vLLM workers, each holding the actor model.
  - For the V3 MoE, cross-node expert parallelism is used, with redundant copies of hotspot experts to balance load.
  - The MTP head is used for self-speculative decoding, explicitly to cut "the completion time for the longest samples".
- **Inference:** forward passes of the reward model and the reference model.
- **Rule-based reward:** needs no GPU memory but is "time-consuming". It is scheduled asynchronously to overlap with the Rollout and Inference modules.
- **Training:** supports PPO, GRPO, DPO and others.
  - Each global batch is sorted by length and distributed across the data-parallel group (data packing).
  - DualPipe from V3 pre-training is used for pipeline parallelism.
- **Phase-wise offloading:** after every module except rule-based reward, its model instances are moved from VRAM to host memory or disk, freeing VRAM for the next phase. In effect, all phases are time-multiplexed on the same GPUs. (Own analysis: this is the paper's description. It does not quantify the swap overhead.)

### Batch shape (Sec. 2.1, 3.2.1)
- Each step uses 32 unique questions × 16 samples, for a training batch of 512.
- Each rollout produces 8,192 outputs, split randomly into 16 mini-batches and trained for a single inner epoch.
- (Own analysis: the paper states both numbers. It does not explain how one 8,192-output rollout maps onto 512-sample steps.)

## Limitations

- **Pure RL depends on reliable rewards** (Sec. 6). The rule-based approach only scales where outputs are automatically checkable, and "scaling up pure RL methods remains an open challenge". Learned reward models invite reward hacking (App. B.5).
- **Software engineering got little RL** because "long evaluation times" hurt RL efficiency. The paper proposes asynchronous evaluation as future work (Sec. 6).
- **Behavioural gaps:**
  - structured output and tool use are weaker than existing models;
  - the model overthinks simple questions;
  - language mixing appears outside Chinese and English;
  - few-shot prompting degrades results (Sec. 6).
- **Unsuccessful attempts** (v1 Sec. 4.2, v2 App. G.2):
  - Process reward models: steps are hard to define, and they lead to reward hacking and extra overhead.
  - MCTS: the token search space is too large, and self-search did not improve the model iteratively.
- **Systems detail is thin.** The paper gives no throughput, utilization, or rollout-vs-train time breakdown, and no weight-sync mechanism. B.1 is qualitative.

## Relation to other systems

All comparisons in this section are (Own analysis); the paper does not make them.
- **HybridFlow / verl:** both separate rollout, reference/reward inference, and training roles. verl colocates them and reshards weights between the generation and training layouts. DeepSeek's framework instead describes whole-module offloading of VRAM between phases, plus a CPU-side asynchronous reward stage.
- **OpenRLHF:** also uses vLLM for generation, with Ray-placed actor, critic, reward and reference models. R1's recipe needs no critic, and for reasoning prompts no reward-model GPU either. The resulting GPU footprint is policy plus reference for reasoning data.
- **DeepSeekMath (the origin of GRPO):** R1 reuses that algorithm at 671B-MoE scale. It adds periodic reference resets, a very long generation budget, and multi-stage reward mixing.
- **Asynchronous / off-policy RL systems (e.g., AReaL-style designs):** the paper's synchronous phases plus MTP speculative decoding for the longest samples point at the same long-tail rollout bottleneck that later asynchronous systems target. R1 itself stays on-policy, with a single inner epoch.

## Takeaways for practice

- **Plan for rollout-dominated steps with long tails.** Generation lengths reach 32K–64K tokens, with 16 samples per prompt. The paper uses speculative decoding specifically to cut the completion time of the longest samples. (Own analysis: length-aware scheduling, partial rollouts and preemption are natural levers.)
- **Treat reward computation as a separate, CPU-heavy, asynchronously scheduled service.** Code execution and test running are "time-consuming" but need no GPU (App. B.1). A sandbox fleet for verifiers is part of the RL cluster. (Own analysis.)
- **Expect model roles time-multiplexed on one GPU pool.** With phase-wise offload, host RAM and NVMe bandwidth become part of the step-time budget. (Own analysis.)
- **Use MoE expert parallelism in the rollout engine.** Replicate hot experts for load balance, as in V3 serving (App. B.1).
- **Size and cost the job explicitly.** The paper reports 147K H800 GPU-hours on a fixed 512-GPU allocation (Table 7).
- **Distillation is cheap and strong for small models.** SFT on R1 outputs beat RL on the 32B base (v1 Table 6). Inference platforms should expect heavy traffic generating teacher data.
- **Long verification blocks RL for agentic tasks such as SWE.** The paper names evaluation latency as the blocker (Sec. 6). A fast, isolated execution sandbox is the infrastructure that would unlock it. (Own analysis.)
