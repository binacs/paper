# Characterization of Large Language Model Development in the Datacenter

> **Why it matters:** The first public, job-level trace of a datacenter built for LLM development (pretraining, SFT, evaluation, debugging). It shows how LLM workloads overturn the assumptions of earlier DL-cluster studies, and it ties a failure taxonomy weighted by GPU time to two concrete systems: automated fault-tolerant pretraining and decoupled evaluation scheduling.

## Problem

Earlier GPU-cluster characterizations covered task-specific DL: many small, single-GPU jobs; low and fragmented utilization; and heterogeneous hardware. Examples are Philly (Microsoft 2017), Helios (SenseTime 2020) and PAI (Alibaba 2020). An LLM shop looks different. A few huge, long gang-scheduled pretraining jobs coexist with a flood of short evaluation and debugging jobs, all on homogeneous A100 nodes. The paper asks three questions:
1. How do LLM workloads differ from prior DL workloads in size, duration, utilization and queueing?
2. Where do GPU-hours go inside each workload type: pretraining, evaluation and debugging?
3. Which failures dominate, and what do they cost?

It then uses the answers to motivate two systems.

## Core design

### Acme and the trace
- Two clusters: **Seren** has 286 nodes / 2,288 GPUs, runs Slurm and has 1x 200Gb/s IB HDR per node. **Kalos** has 302 nodes / 2,416 GPUs, runs Kubernetes and has 4 IB HCAs for applications plus 1 for storage. Every node has 8x A100-SXM 80GB. Storage is a shared all-NVMe parallel file system. There are no serving jobs (§2.2, Table 1).
- The trace covers March to August 2023. Sources are scheduler job logs, 15-second hardware monitoring, runtime logs and fine-grained profiling (§2.3). The trace is public as AcmeTrace.
- The five-stage pipeline is data prep, pretraining, alignment (SFT/RLHF), evaluation and deployment. Evaluation runs periodically during pretraining on checkpoints (§2.1).

### Characterization findings (§3–§4)
- **Shorter, bigger, saturated jobs.** Jobs are shorter than in prior traces but larger on average. Per-job GPU utilization is polarized at 0% or 100% (§3.1, Figs. 2–3).
- **Skewed demand.** Pretraining is a tiny fraction of jobs but most of the GPU time. Evaluation is the reverse (§3.2, Fig. 4).
- **Unfair queueing.** Evaluation jobs are small and short but have the *longest* queueing delay. Capacity is reserved for pretraining, and trials arrive in bursts (Fig. 6).
- **Infrastructure.** GPU memory is heavily used, while host memory and NICs are mostly idle (§3.3–3.4, Figs. 7–9).
- **Pretraining profiling.** A 123B model on 2,048 GPUs: 3D parallelism (PP=4, TP=8) vs hierarchical ZeRO with 64-GPU shards. The ZeRO-style InternEvo V2 has higher SM utilization and avoids the activation-memory imbalance across pipeline stages (§4.1, Figs. 10–12).
- **Evaluation inefficiency.** Model loading and preprocessing dominate the start of a trial, and CPU metric computation idles the GPU at the end (§4.2, Fig. 13).

### Failure taxonomy (§5, Table 3)
- Errors are extracted from runtime logs with the paper's rule-plus-LLM diagnosis pipeline, then checked by hand. The logs cover 32,500 Kalos tasks (mostly evaluation, with 647 pretraining tasks) plus 675 Seren pretraining tasks (§5).
- There are three categories:
  - **Infrastructure:** GPU, NVLink, node, network and storage. Named examples are NVLinkError, CUDAError, ECCError, NCCLRemoteError and S3StorageError.
  - **Framework:** RuntimeError, ValueError, AttributeError, OOM and dataloader kills. These usually hit early in a job.
  - **Script:** user bugs such as a missing file, TypeError, ImportError or KeyError. These are the most frequent by count.
- Table 3 reports, per reason: count, average and median GPU demand, time-to-failure (TTF), share of failed GPU time, and time-to-restart (TR). Infrastructure failures are rare by count but hit the largest jobs after long runtimes, so they dominate wasted GPU time. Script errors are numerous but fail within about a minute on few GPUs, so they are cheap.
- **Operations.** The frameworks had no automatic recovery, so engineers restarted jobs by hand and took on-call shifts. The early 104B run lost substantial progress on checkpoint reloads. The later 123B run had fewer rollback losses thanks to shorter checkpoint intervals and graceful termination, but interrupted jobs still needed fast manual restarts (§5.3, Fig. 14).

### System 1: fault-tolerant pretraining (§6.1)
- **Asynchronous checkpointing.** Model and optimizer state are snapshotted to host memory, and a background thread persists them to remote storage. This takes checkpoint I/O off the critical path, which makes frequent checkpoints cheap and shrinks rollback.
- **Log compression.** Regex filter rules strip routine lines such as iteration and loss prints. An LLM "Log Agent" proposes new regexes, accepted by self-consistency voting over multiple samples, so the rule set grows over time.
- **Diagnosis.** Known signatures go through the rule set first. Otherwise the compressed log is embedded into a vector store, and a "Failure Agent" (GPT-4 at the time) queries it. The agent outputs the root cause, labels it user or infrastructure, and suggests a mitigation.
- **Recovery.** For infrastructure faults, a two-round pairwise NCCL test locates the faulty nodes. Those nodes are cordoned and the job restarts from the latest checkpoint. For loss spikes, the system rolls back to an earlier checkpoint and skips the offending data batches.

### System 2: decoupled evaluation scheduling (§6.2)
- A **trial coordinator** sits between the cluster scheduler and the LLM evaluation framework.
- **Decoupled model loading.** A precursor job pulls the checkpoint once from remote storage into node-local shared memory, and trials load it over PCIe. The bottleneck was the 25Gb/s storage NIC. The coordinator cleans up afterward.
- **Decoupled metrics.** GPU trials write their outputs to files, and separate CPU jobs compute the metrics, so GPUs are released at once.
- **Trial decomposition and packing.** Small datasets are batched and large ones split. The coordinator then does round-robin allocation over a queue sorted by prior runtime estimates, and gives priority to trials whose CPU metric phase is long.

## Limitations

- **One organization, one period.** The data is a single lab, A100-only, from 2023, with no serving. Shares depend on InternLM's process, such as how often evaluation runs and the Slurm vs. K8s split. GPU-time shares are not portable.
- **Failure counts are not MTBF.** Table 3 counts failed jobs, not hardware events per GPU-hour. The paper gives no failure rate normalized to fleet size or job scale, so its numbers cannot be compared directly to per-GPU-hour interruption rates in later reports.
- **Categories are partly implicit.** The text names examples per category, but Table 3 does not label every row. Some rows, such as connection errors and dataloader kills, need inference to place.
- **The systems are evaluated lightly.** The ~90% reduction in manual intervention is self-described as informal. Async checkpointing excludes persistence time. Evaluation scheduling is shown only for a 7B model on at most 4 nodes.
- **Diagnosis accuracy is unreported.** The agent depended on GPT-4, and no per-class precision or recall is given.
- **The queueing policy is left alone.** Capacity reserved for pretraining is taken as given, and evaluation is packed better around it.

## Relation to other systems

- **Philly (Jeon et al., ATC 2019):** A 2-month multi-tenant DNN trace focused on gang scheduling, locality and failures. Acme inverts it: shorter median jobs, larger gangs, and near-saturated rather than 48% median utilization. Acme also weights failures by GPU time rather than by count.
- **MLaaS in the Wild / PAI (Weng et al., NSDI 2022):** Alibaba's 6K+ heterogeneous-GPU trace, dominated by small and fractional-GPU tasks with low utilization. Acme is homogeneous, so the pain shifts from bin-packing heterogeneous GPUs to protecting giant gangs while keeping evaluation responsive.
- **Helios (SC 2021):** The team's earlier CV/RL trace, with the same methodology. It is the direct baseline in Table 2.
- **MegaScale (NSDI 2024):** A single-job training stack for more than 10K GPUs with deep fault and straggler diagnostics (per its abstract). Acme is fleet-level and covers the evaluation side, which MegaScale does not.
- **Llama 3 report (Meta, 2024):** Gives a root-cause breakdown of interruptions for one flagship run. Acme's Table 3 is fleet-wide and per failed job. Both point to GPU and interconnect hardware as the dominant cost (qualitative comparison only).
- **In-memory checkpointing (CheckFreq, Gemini):** Acme's async checkpointing uses the same snapshot-then-persist idea. The novelty is pairing it with automated diagnosis in production.

## Takeaways for practice

- **Weight failures by GPU time, not count.** Rare infrastructure faults on 800-GPU jobs cost far more than hundreds of script errors. Point alerting and automation at GPU-time loss.
- **Fail fast before full scale.** Script errors surface within minutes. Preflight checks or a small smoke run before a large gang allocation avoid churn.
- **Automate the restart loop:** log filtering, signature rules, an LLM fallback, pairwise NCCL tests, cordon, and restart from the latest in-memory checkpoint.
- **Make checkpoints cheap enough to take often.** Rollback loss, not checkpoint cost, hurt the 104B run.
- **Treat evaluation as its own latency-sensitive class.** Cache models on the node, offload metrics to CPU jobs, and split or pack trials by runtime estimate.
- **Check storage-NIC bandwidth, not only GPUs.** The 25Gb/s storage NIC, not compute, bottlenecked evaluation model loading.
