# MegaScale: Scaling Large Language Model Training to More Than 10,000 GPUs

> **Why it matters:** One of the few detailed public accounts of running a single LLM training job on more than 10k GPUs in production, covering throughput (MFU) and the fault-tolerance and diagnosis tooling that keeps a multi-week run going.

## Problem

At 10k-GPU scale two things limit an LLM pre-training run. **Efficiency**: model FLOPs utilization (MFU) falls as communication, pipeline bubbles, data loading and stragglers grow with scale, and fixed per-job costs such as communicator initialization grow badly too. **Stability**: the paper states that failures and stragglers "are the norm rather than the exception," and a run lasts weeks, so every failure costs detection, diagnosis and restart time plus the work since the last checkpoint. Two principles run through the design: algorithm–system co-design, and in-depth observability across the stack.

## Core design

### Algorithm–system co-design (§3.1)
- **Parallel transformer block (PTB):** the serial block `y = x + MLP(LN(x + Attn(LN(x))))` becomes `y = x + MLP(LN(x)) + Attn(LN(x))`, so attention and MLP run concurrently and their TP communication can be fused and overlapped. The paper cites prior work showing no quality loss at hundreds of billions of parameters.
- **Sliding window attention (SWA):** each token attends to a fixed window, so cost is O(s·w) instead of O(s²), and stacked layers still give a large receptive field. No window size is given.
- **LAMB:** layer-wise adaptive LR lets the global batch grow 4× without accuracy loss. Fewer, larger steps mean a longer steady 1F1B phase per step, so warm-up and cool-down bubbles are amortized; the paper says this removes 87.5% of pipeline bubbles.

### Communication overlap in 3D parallelism (§3.2)
Tensor parallelism (TP) stays inside a node. Data parallelism (DP) is placed across nodes in preference to pipeline parallelism (PP). DP uses a ZeRO-2-style sharded optimizer (§2).
- **DP:** an all-gather runs before each model chunk's forward and a reduce-scatter after its backward. The first all-gather is prefetched at iteration start, overlapping data loading; collectives are issued in the order of the compute that depends on them ("high priority first"). The last reduce-scatter is acknowledged to stay exposed.
- **PP (interleaved 1F1B):** in warm-up a forward pass needs only its receive, but paired send/recv ops block on the slower side, so MegaScale decouples them and the send overlaps compute. Cool-down is the mirror case; in the steady phase both are launched asynchronously.
- **TP/SP:** all-gather and reduce-scatter are fused into the parallel Linear layers on the FFN path, whose GEMMs are large enough to hide communication, and the GEMM is split into chunks that pipeline with communication in both directions.

### Operators, data pipeline, initialization (§3.3–3.5)
- FlashAttention-2, plus fused LayerNorm and GeLU kernels, to cut launch overhead and memory traffic.
- The next step's data is preprocessed during the end-of-step gradient sync. GPUs on one machine share a TP group and read identical data, so a "two-layer tree" uses one dedicated loader per machine into shared memory, from which each GPU copies its slice.
- Megatron-LM's communicator init on 2,048 GPUs was dominated by a blocking TCPStore and O(n²) global barriers. MegaScale switches to a non-blocking Redis store and reorders process-group creation to reduce barriers to O(n).

### Network and collective tuning (§3.6)
- Three-layer CLOS-like fabric of Broadcom Tomahawk 4 switches (64×400G ports), 1:1 down/up.
- **ECMP-collision mitigation:** each 400G ToR downlink is split into 2×200G via AOC, so uplink bandwidth is 2× downlink; eight 200G NICs per server go to eight switches (multi-rail); up to 64 servers share a ToR set and data-intensive jobs are placed under the same ToR.
- **Congestion control:** default DCQCN under all-to-all caused heavy PFC and head-of-line blocking, so MegaScale uses a hybrid of Swift-style precise RTT measurement and DCQCN-style ECN fast reaction.
- **Retransmit:** the NCCL retransmit timer and retry count are tuned to ride through link flapping, and the NIC's `adap_retrans` allows faster retransmission for short flaps.

### Fault tolerance: the robust training loop (§4)
- **Control plane:** a driver allocates resources through a custom Kubernetes and starts one executor Pod per node. Each executor runs the training processes plus a *robust training daemon* that sends periodic heartbeats.
- **Heartbeat payload (§4.2):** executor identity (IP, Pod name, hardware info), training-process status, stdout/stderr aggregated and keyword-filtered on the fly, and RDMA traffic metrics. Per-step RDMA traffic should look periodic: a drop or abnormal fluctuation raises an alert, and traffic stopping entirely triggers automatic recovery. Network monitoring runs at two levels — second-level health checks (ECN/PFC/QoS config, flapping, NIC faults) and millisecond-level checks for congestion and whether DP/PP transfers reach line rate.
- **Recovery flow:** triggered by an abnormal status report or a heartbeat missing beyond a time window. The driver suspends all executors, runs self-check diagnostics, submits the IPs of bad nodes to Kubernetes (which evicts them and backfills the same number of healthy nodes), and resumes from the latest checkpoint. A UI allows manual eviction.
- **Diagnostic tests (§4.3):** kept short to limit false positives and lost time — intra-host loopback bandwidth (RNIC to memory nodes and GPUs), RNIC-to-RNIC connectivity, an NCCL all-to-all within the node, and an NCCL all-reduce with ToR neighbors.
- **Two-stage checkpointing (§4.4):** stage 1 copies GPU state to pinned host memory in several seconds with optimized PyTorch serialization, and training resumes; stage 2 writes host memory to HDFS in the background. On restore, only one rank per group sharing a state partition (e.g., a DP group) reads from HDFS and broadcasts to its peers, avoiding HDFS read storms.

### Diagnosis tooling (§5)
- **CUDA event monitor (§5.1):** times critical code segments on every rank with CUDA events, avoiding extra synchronization, and is always on in production. Records go to a local file, a streamer forwards them to Kafka, and an analytical database serves live queries. Two views sit on top: a per-rank **heat map**, which exposed a small set of consistently slow machines, and a **trace timeline** merging events across ranks along the DP/PP/TP axes.
- **3D-parallel visualization for hangs (§5.2):** on a communication timeout each worker logs its in-flight event. Healthy workers waiting on a dead peer log what blocked them; workers on a faulty GPU are hung and log nothing, so the hung node shows up as the hole in the dependency graph, and is then evicted through the §4 loop. Note the paper does **not** describe Python stack-trace capture: straggler detection rests on CUDA-event timing and hang localization on these timeout logs.

## Limitations

- **Single-tenant, restart-the-world.** The fault loop evicts and backfills whole nodes for one job and assumes a spare healthy pool; cluster-level scheduling, cross-job spare capacity and preemption are out of scope. Any fault suspends all executors and restarts from the latest checkpoint, with no in-place or partial recovery, and with >100 restarts the ">90%" effective training time means roughly a tenth of the run is still lost.
- **Diagnostics coverage.** The self-checks target network and NCCL faults; silent data corruption and numerical faults are not addressed, the "MFU decreases over time" case (§6.3) was fixed by manual investigation, and hang localization relies only on timeout logs plus the fact that hung ranks stay silent — there is no stack-level tooling for a hang inside a collective or in Python control flow.
- **Model changes are not free.** PTB, SWA and LAMB alter the model and optimizer; convergence is shown on a 13B model (Fig. 10) and the production run, not at every scale, and SWA limits long-range attention per layer.
- **Reproducibility.** The baseline is a fixed older Megatron-LM commit (285068c8), no code is released, and heartbeat interval, timeout values and monitoring overhead ("negligible") are unquantified. Results are on Ampere GPUs.

## Relation to other systems

- **Megatron-LM:** the baseline, whose TP/SP and interleaved 1F1B MegaScale builds on. Its additions are overlap (decoupled PP send/recv, fused chunked TP comm, prefetched DP all-gather), model-level co-design, O(n) group initialization, and a fault-tolerance loop Megatron-LM does not provide.
- **DeepSpeed ZeRO:** MegaScale adopts ZeRO-2-style sharding for DP; its contribution is scheduling — issue order and prefetching so the collectives hide behind compute.
- **GPipe / PipeDream:** these attack bubbles with schedules; MegaScale instead changes the optimizer (LAMB) to permit larger batches.
- **Pingmesh, NetBouncer, EverFlow:** fabric-wide probing systems. MegaScale's tests are job-scoped and run only on suspected nodes during a pause, and its main signal is from the application (CUDA-event timings, RDMA traffic periodicity, timeout logs), not network probes.

## Takeaways for practice

- Treat **startup cost** as a first-class metric: process-group init can take tens of minutes at scale and every restart pays it. Use a non-blocking KV store and avoid O(n²) barriers.
- Build the **suspend → diagnose → evict → backfill → resume** loop into the scheduler/driver contract. The scheduler needs an API for "block these IPs and give me N replacements of the same shape."
- **Heartbeats should carry signals, not just liveness:** process status, filtered logs and RDMA byte counters catch silent failures where nothing crashes but traffic stops or drifts.
- Keep **always-on, sync-free per-rank timing** streaming into a queryable store; stragglers at ~0.5% of machines set the pace of the whole job. For hangs, have every rank log its in-flight collective on timeout — the silent ranks are the suspects.
- **Placement matters:** multi-rail NICs, split downlinks against ECMP collisions and ToR-affinity for communication-heavy jobs belong in placement policy, not only in the fabric.
- Use **two-tier checkpoints** and **deduplicated restore via broadcast** so frequent restarts stay cheap, and check whether a **model or optimizer change** removes a bottleneck before adding system complexity.
