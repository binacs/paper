# Insights into DeepSeek-V3: Scaling Challenges and Reflections on Hardware for AI Architectures

> **Why it matters:** A rare first-party account of how a frontier MoE model was co-designed with a bandwidth-crippled GPU (H800) and a cheap two-layer network, turned into a concrete wish-list for the next generation of accelerators and interconnects.

## Problem

Frontier LLM training and serving is bounded by three walls the paper names explicitly: memory capacity (model memory demand grows far faster than HBM, §2.1), compute cost per token, and interconnect bandwidth/latency, which dominates for fine-grained MoE with expert parallelism (EP). DeepSeek trained V3 (671B total / 37B active parameters) on 2,048 H800 GPUs, whose NVLink is cut down relative to H100 (§4.1), with "policy and regulatory constraints" keeping deployment at just over 2,000 GPUs (§5.1). The question is which model, numeric and network choices let such a cluster stay cost-competitive, and what hardware would remove the remaining workarounds.

## Core design

### Model-side: shrink memory and per-token compute
- **MLA (Multi-head Latent Attention, §2.1.2).** K/V of all heads are projected into one low-dimensional latent vector; only the latent is cached at inference. Table 1 puts V3 at 70.272 KB of KV cache per token versus 327.680 KB (Qwen-2.5 72B, GQA) and 516.096 KB (LLaMA-3.1 405B, GQA), directly raising batch size and context length per GPU.
- **DeepSeekMoE (§2.2).** Many fine-grained routed experts plus a shared expert; each token hits 1 shared + 8 routed experts. Training cost is 250 GFLOPs/token for V3 versus 394 for dense Qwen-72B and 2,448 for dense LLaMA-405B (Table 2), i.e. a 671B model trains cheaper per token than a 72B dense one. The low active count also enables local inference (≈20 TPS for V3 via KTransformers on a ~$10k consumer-GPU server, §2.2.2).
- **MTP (§2.3.3).** A multi-token-prediction head doubles as a speculative-decoding draft; acceptance of the second token is 80–90%, giving 1.8x decode TPS.

### Numerics: FP8 training and compressed communication
- **Fine-grained FP8 (§3.1; tech report §3.3).** FP8 GEMMs for Fprop/Dgrad/Wgrad, with per-tile scaling: 1x128 tiles for activations, 128x128 blocks for weights, E4M3 for all tensors, scales computed online. Embedding, output head, MoE gating, norms and attention remain BF16/FP32, as do master weights, gradients and optimizer state (tech report §3.3).
- **Accumulation workaround.** H800 Tensor Cores keep only the top 13 fraction bits when accumulating aligned products (effectively FP22, §3.1.1). Without mitigation the tech report measures nearly 2% max relative error at K=4096; DeepSeek promotes partial sums to FP32 on CUDA cores every 128 elements (tech report §3.3.2). This costs SM cycles, motivating the ask for FP32/configurable accumulation.
- **Low-precision storage/comm (tech report §3.3.3).** AdamW moments in BF16, cached activations in FP8, MoE dispatch in FP8, combine in BF16.
- **LogFMT (§3.2).** A per-1x128-tile log-domain format for activations on the wire; 8-bit LogFMT beat E4M3/E5M2 and 10-bit matched BF16 combine in ~7B dense experiments, but was *not deployed* because fusing encode/decode with all-to-all added 50–100% overhead (§3.2.1).

### Parallelism and overlap
- **No tensor parallelism in training (§4.2).** Tech report §3.2: 16-way PP, 64-way EP across 8 nodes, ZeRO-1 DP. Avoiding TP sidesteps the weak H800 NVLink.
- **DualPipe (tech report §3.2.1, Table 2).** Bidirectional pipeline fed from both ends; each forward chunk is paired with a backward chunk so compute hides EP all-to-all, which is mandatory since cross-node EP runs at roughly 1:1 compute-to-comm. Bubble drops to (PP/2−1)(F&B+B−3W) from (PP−1)(F+B) for 1F1B, at the cost of a second parameter copy and slightly higher activation memory.
- **Dual micro-batch overlap at inference (§2.3.1),** plus prefill/decode disaggregation using different EP group sizes.
- **Communication kernels (tech report §3.2.2; §4.4.1).** All-to-all uses 20 of 132 SMs (10 channels, warp-specialized) to drive IB+NVLink — compute stolen for data movement, hence the wish for a communication co-processor.

### Node-limited routing (§4.3)
- H800 nodes have 8 GPUs and 8×400G CX7 IB NICs. Intra-node NVLink is ~4x the per-GPU IB bandwidth (tech report: 160 GB/s achievable NVLink vs 50 GB/s IB, ~3.2x).
- Experts are split into 8 groups of 32, one group per node; the router restricts each token to at most 4 nodes. A token is sent over IB once per destination node and fanned out over NVLink, so IB traffic per token falls from 8t to Mt (M ≤ 4). With 3.2x asymmetry, up to ~13 experts per token could be reached at the same IB cost (tech report §3.2.2). Model architecture is explicitly shaped by the network topology.

### Multi-Plane Fat-Tree network (§5.1)
- Each GPU's NIC sits in its own plane; 8 independent two-layer fat trees built from 64-port 400G IB switches (plus a separate RoCE NIC per node for storage). Cross-plane traffic is forwarded inside the node (NVLink/PXN).
- Two layers reach 16,384 GPUs in theory. Planes isolate congestion and faults; multi-port NICs (ConnectX-8 has 4 planes natively) are the intended end state.
- Measured on 2,048 GPUs, MPFT and a single-plane multi-rail fat tree (MRFT) give essentially identical all-to-all and end-to-end training (Table 4).

### Hardware wish-list (§3–§6)
FP32/configurable accumulation and native block scaling (§3.1.2); hardware FP8/LogFMT compression (§3.2.2, §6.5); a unified scale-up/scale-out adapter or comm co-processor (§4.4.2); NVLink/PCIe prioritization and NIC on the I/O die (§4.5.2); low-latency RoCE, adaptive routing, better congestion control (§5.2.2); SDC detection (§6.1.2); in-network multicast/aggregation (§6.5); memory-semantic ordering primitives (§6.4).

## Limitations

- **Not a controlled study.** Mostly design rationale; the one network A/B (MPFT vs MRFT) shows parity, not a gain. Table 3 costs use the Slim Fly paper's cost model, not purchase data.
- **TPOT bounds are theoretical** (no latency, overheads or imbalance, §2.3.2).
- **Model shaped by the network.** Node-limited routing assumes an 8-GPU/8-NIC node and ~4:1 scale-up/scale-out ratio; it may be suboptimal on NVL72-class domains.
- **Partial MPFT.** ConnectX-7 lacks native multi-plane support; cross-plane traffic pays an intra-node hop (§5.1).
- **FP8 depends on software workarounds** (CUDA-core promotion); LogFMT never shipped.
- **Inconsistency:** §4.1 gives H800 NVLink as 400 GB/s, §4.3 as 200 GB/s (≈160 achievable); probably bidirectional vs unidirectional, unstated.
- Little fleet-scale reliability or scheduling data.

## Relation to other systems

- **Megatron-LM (SC 2021).** TP+PP+DP for dense models (502 PFLOP/s on 3,072 GPUs, 52% of peak; interleaved 1F1B +10%). DeepSeek drops TP and uses DualPipe, because its bottleneck is cross-node EP all-to-all, not TP all-reduce.
- **MegaScale (NSDI 2024).** Dense 175B on 12,288 GPUs at 55.2% MFU (1.34x Megatron-LM), focused on overlap and fault tolerance at 10K+ scale. DeepSeek reports a smaller MoE cluster at 43.7% MFU and focuses on numerics and topology, not fleet operations.
- **MegaScale-MoE (arXiv 2505.11432).** Closest peer: separate parallelism for attention and FFN, multi-level overlap and low-precision comm compression; 1.41M tokens/s for 352B MoE on 1,440 Hopper GPUs (1.88x Megatron-LM). DeepSeek additionally changes the model (node-limited routing) and the network to cut traffic.
- **Llama 3 (arXiv 2407.21783).** Dense 405B on up to 16K H100 over 400 Gbps RoCE, 4D parallelism with TP and CP, BF16 at 38–43% MFU. Llama 3 buys scale with GPUs; DeepSeek buys efficiency with sparsity, FP8 and a cheaper topology.
- **Alibaba HPN (SIGCOMM 2024).** Ethernet two-tier dual-plane fabric with dual-ToR, ~15K GPUs per pod. MPFT is the same "two tiers, multiple planes instead of three tiers" idea taken to 8 IB planes, one per GPU NIC.

## Takeaways for practice

- **Topology is a scheduling constraint.** Node-limited routing ties EP group placement to IB traffic per token; MoE-aware schedulers should expose node and plane locality, not just GPU counts.
- **Budget SMs for communication.** Without a comm offload engine, all-to-all takes ~15% of SMs; MFU targets and kernel libraries (DeepEP-style) must account for it.
- **Validate FP8 accumulation per GPU generation**; per-tile/block scaling plus periodic FP32 promotion is the working recipe.
- **KV bytes per token is the inference sizing metric.** MLA's 4.7–7.3x reduction vs GQA changes concurrency per GPU and the cost of KV offload over PCIe (§4.5).
- **Two-tier multi-plane fabrics are a real cost lever**: FT2 cost per endpoint at 8x the endpoints, no measured training penalty at 2K GPUs, and per-plane fault/congestion isolation.
- **MoE decode is bandwidth-bound.** The 14.76 ms vs 0.82 ms TPOT bounds show scale-up domain size matters more than FLOPs; prefill/decode disaggregation with different EP sizes is the software response.
