# Inference without Interference: Disaggregate LLM Inference for Mixed Downstream Workloads

> **Why it matters:** One of the first prefill/decode disaggregation designs (TetriInfer). It measures three kinds of interference separately and adds prefill-only fixed-size chunks and output-length-aware decode placement on top of the split.

## Problem

Downstream tasks differ in prompt and output length by more than two orders of magnitude, from summarisation (long in, short out) to content creation (short in, long out) (§1, Fig. 1). Coupled systems such as vLLM batch all of them together, ignoring that prefill is compute-bound with cost quadratic in prompt length, while decode is memory-bandwidth-bound and latency-critical (§2.1, Fig. 2). Three kinds of interference (§2.2):

- **Prefill–prefill (§2.2.1, Fig. 3):** a light prefill (about 18 tokens, ShareGPT's short-prompt median) slows down 2x with 7 co-running light prefills and 8x with 63. It slows down more than 10x next to heavy prefills (512 tokens). A heavy prefill slows down about 3x next to light ones. Latency jumps once the batch's total tokens pass the *accelerator-saturate threshold*.
- **Prefill–decode (§2.2.2, Fig. 4):** one heavy prefill in the continuous batch raises a light decode's per-iteration latency 5x. More than 7 co-running light decodes slow prefills by up to about 2.5x.
- **Decode–decode (§2.2.3, Fig. 5):** at batch 128, a half-heavy, half-light batch has 16% lower throughput and 23% higher latency than an all-light batch.

§2.3 maps these to three fixes: cap tokens per prefill step, separate the phases, and schedule decodes by predicted resource use.

## Core design

The architecture (Fig. 6b) has a centralised control plane, prefill instances, decode instances, and a small length-prediction model.

**Control plane (§3.2).** The *cluster monitor* gathers instance load about every 100 ms, broadcasts decode load to the prefill instances, and adds, removes and flips instances. The *global scheduler* sends each request to the least-loaded prefill instance, keeps a request status table, and streams output back. It does not choose decode instances; the prefill dispatchers do.

**Prefill instance (§3.3).**
- *Scheduler (§3.3.1):* non-preemptive FCFS, SJF or LJF over prompt length, which predicts prefill time. Requests are scheduled in rounds of `PrefillSchedBatch` to bound starvation.
- *Fixed-size chunked prefill (§3.3.3, Fig. 7):* `ChunkSize` equals the accelerator-saturate threshold, 512 tokens for OPT-13B on their testbed. Prompts are sliced and packed into chunks of exactly that size, with the last chunk zero-padded and a per-request cursor tracking progress. Unlike Sarathi, chunks hold **only prefill tokens**.
- *Length predictor (§3.3.2, Fig. 8):* OPT-125M is fine-tuned as a classifier over output-length buckets of OPT-13B, using labels from the target model's own responses. Bucket width (*granularity*, 200 in the design) trades precision for accuracy. It runs on each prefill instance in parallel with the main LLM; placing it at the global scheduler or at decode was rejected.
- *Dispatcher (§3.3.4), the first scheduling level:* after the first chunk is prefilled, decode instances are split into α (enough free resources for the predicted length) and β (not enough). The dispatcher samples two from α (power-of-two choices) and picks the one with less interference, keeping each instance's heavy-to-light decode ratio low.

**KV transfer (§3.3.4, Fig. 9).** There are three link classes: Direct (NVLink/HCCS), Direct-NIC (for example a 200 Gbps ConnectX-6 over Ethernet or InfiniBand) and Indirect (staged through CPU DRAM). A unified send/recv/read/write API sits over one- or two-sided stacks. Transfer is request-level only: the whole KV is sent after the last chunk. Chunk-level transfer (the paper points to Splitwise's layer-wise transfer), multi-link transfer and one-sided accelerator access are future work.

**Decode instance (§3.4), the second scheduling level.** It uses continuous batching on vLLM paged KV. Admission is vLLM greedy (can thrash), *reserve-static* (admit only if predicted memory fits now) or *reserve-dynamic* (admit only if memory is still free when the shortest remaining job finishes).

**Instance flip (§3.5).** An instance under 10% load for a minute is drained, then switched between prefill and decode by flipping an internal variable, with no restart or model reload. The flip takes about 5–7 ms excluding drain time.

**Implementation (§4).** A Python control plane, instances built on vLLM, and a C++ IB-Verbs network stack. **KV transfer is emulated.** Only the socket Indirect path exists. KV caches are produced offline and preloaded into decode memory, and at test time only metadata is sent while the decode side waits for a transfer latency computed from model shape and target bandwidth.

## Limitations

- **Emulated network, small scale.** No KV bytes cross a link (§4), and everything runs on one 4 x V100 box with OPT-13B. Real NIC/PCIe contention and the cost of large-model KV are not measured.
- **Heavy prefill does not pay off.** For the heavy-prefill workloads TetriInfer needs more resources and is not better on perf/$, and the authors call the design "not ideal" for HPHD (§5.1, Figs. 13–14). The paper reports both workloads in one paragraph, so this note gives no per-workload figures. Disaggregation uses 2x the cards of the coupled baseline, so savings depend on flipping idle instances.
- The predictor is coarse (74.9% accurate at 200-token buckets). Reservation policies beat greedy only with an oracle (Fig. 18).
- Only non-preemptive scheduling and request-level transfer. There is no SLO-driven per-phase parallelism, no KV/prefix reuse, and no migration between decode instances.
- v1 has inconsistencies: figure references, and NVLink given as 300 GBps in the text but 900 GBps in Fig. 9. No code is released.

## Relation to other systems

- **DistServe (OSDI 2024):** also disaggregates to remove interference, but co-optimises per-phase resource allocation and parallelism for TTFT/TPOT SLOs (goodput per GPU) and places phases by bandwidth (7.4x more requests or 12.6x tighter SLOs). TetriInfer has no parallelism search. It adds within-phase scheduling instead: prefill-only chunks, length prediction and interference-aware placement.
- **Splitwise (ISCA 2024):** splits phases across possibly heterogeneous machines (token generation on cheaper, lower-power GPUs) and optimises real backplane state transfer layer-wise (1.4x throughput at 20% lower cost). TetriInfer is homogeneous, emulates transfer, and sends KV per request.
- **Sarathi-Serve (OSDI 2024):** stays coupled, using chunked prefill with stall-free batching that piggybacks decodes on chunks (2.6x–5.6x capacity vs vLLM). TetriInfer's chunks are prefill-only, and decodes move to other instances.
- **Mooncake (FAST 2025):** Kimi's production system: KVCache-centric, with separate prefill and decode clusters, a KV cache pooled from CPU DRAM and SSD, an SLO-aware scheduler and prediction-based early rejection. KV storage and reuse, which it treats as first-class, are absent from TetriInfer.
- **Llumnix (OSDI 2024):** no phase split. It fixes imbalance, fragmentation and priority at runtime through live migration of requests and their KV. TetriInfer places each decode once, by predicted length, and never migrates. The two approaches are complementary.

## Takeaways for practice

- Measure P–P, P–D and D–D interference on your own hardware. The saturate threshold is model- and hardware-specific and should set the chunk size and prefill token budget.
- Disaggregation pays most for light-prefill, heavy-decode traffic and can lose on prompt-heavy traffic, so provision by workload class.
- A coarse bucketed length predictor is enough for power-of-two decode placement. Reservation-based admission needs better predictions, so make it degrade gracefully.
- Role flips with no model reload make the prefill:decode ratio elastic, and drain-then-flip is simple.
- Treat emulated-transfer results with care. Validate KV transfer cost on real RDMA or NVLink at your model size.
