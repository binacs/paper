# Fast Inference from Transformers via Speculative Decoding

> **Why it matters:** It showed that a small draft model plus a modified rejection-sampling rule can cut decode latency 2-3x with *exactly* the target model's output distribution, and it gave the α/γ/c cost model that serving systems still use to tune speculation.

## Problem

Autoregressive decoding takes one serial target-model pass per token. For large models at small batch, each pass is limited by memory bandwidth and communication, not by arithmetic (§1), so most of the accelerator's FLOPs go unused. Earlier speedups needed retraining or a new architecture, changed the outputs, or worked only for greedy decoding (§1, §5). The goal is to turn idle compute into lower latency with no retraining and an unchanged output distribution.

## Core design

**Speculative decoding step (Algorithm 1, §2.1).** A cheap approximation model M_q autoregressively drafts γ tokens x₁..x_γ, keeping its distributions q₁..q_γ. The target M_p then runs *once*, in parallel over the prefix and all γ extensions, and produces p₁..p_{γ+1}. Drafts are checked left to right. The first rejection stops the step. One more token is always sampled from M_p: a correction at the rejection point, or p_{γ+1} if every draft was accepted. Each target pass therefore emits between 1 and γ+1 tokens.

**Speculative sampling (§2.3).** For each draft x ~ q(x):
- if q(x) ≤ p(x), accept;
- otherwise reject with probability 1 − p(x)/q(x). In Algorithm 1 this is the test r ~ U(0,1), rejected if r > p(x)/q(x);
- on rejection, resample from the residual p'(x) = norm(max(0, p(x) − q(x))).

*Why the output is exactly p (App. A.1).* The probability of emitting x through acceptance is q(x)·min(1, p(x)/q(x)) = min(p(x), q(x)). The total rejection probability is 1 − Σ min(p, q), which equals Σ max(0, p − q), the residual's normaliser. So the rejection path contributes exactly max(0, p(x) − q(x)), and the sum is min(p, q) + max(0, p − q) = p(x). This holds for any q, so a bad draft model costs speed, never correctness (§3.6). Greedy, top-k, nucleus and temperature sampling are handled by "standardising" p and q first (§2.2), so the draft must use the target's sampling transform.

**Acceptance-rate analysis (§3.1–3.2).** β is the probability of accepting a draft at a given prefix, and α = E[β] under an i.i.d. assumption (Def. 3.1). With the divergence D_LK(p, q) = 1 − Σ min(p, q), they prove β = 1 − D_LK and α = E[Σ_x min(p, q)] (Thm 3.5, Cor. 3.6). Accepted runs are capped-geometric:

  E[tokens per target pass] = (1 − α^{γ+1}) / (1 − α)   (Eq. 1)

**Walltime model (§3.3).** c is the time of one M_q pass divided by the time of one M_p pass (Def. 3.7). If the γ+1-wide verification pass costs the same as a one-token pass, the expected speedup is

  S(α, γ, c) = (1 − α^{γ+1}) / ((1 − α)(γc + 1))   (Thm 3.8)

Some γ gives a speedup whenever α > c. With γ = 1 the speedup is at least (1 + α)/(1 + c) (Cor. 3.9). As c → 0, S is bounded by 1/(1 − α) (§3.6).

**Extra compute (§3.4).** With ĉ the per-token FLOP ratio of M_q to M_p (Def. 3.10), total arithmetic grows by

  (1 − α)(γĉ + γ + 1) / (1 − α^{γ+1})   (Thm 3.11)

Accepted drafts are "free" concurrency. Rejected drafts are wasted verification FLOPs.

**Choosing γ (§3.5).** Pick the integer γ that maximises Thm 3.8 for the measured α and c (Fig. 3). Larger γ pays off only at high α and wastes more FLOPs (Table 1). Adaptive γ is left to future work.

**Draft model choices (§3.6).** Same-family models about 100x smaller worked best. n-gram models (c ≈ 0) and copy-from-context heuristics also work. A.5 adds a "lenience" knob l that scales q before the comparison, trading exactness for speed.

## Limitations

- **It spends idle compute.** The paper says the method "is not helpful for configurations where additional computation resources are not available" (§6). Every walltime number is at batch 1 on one TPU-v4. The paper does not analyse batching.
- **The cost model is simplified.** It assumes the γ+1-wide verification pass costs the same as a one-token pass, and it treats β as i.i.d. The paper calls the i.i.d. assumption an approximation, and Table 4 shows predictions off by up to ±0.8X (T5-large EnDe was overpredicted; CNN/DM was underpredicted).
- **γ is fixed per run.** Adaptive γ, tree-shaped drafts and hierarchical drafting are left as future work (§3.5, §6). Beam search is only sketched (App. A.4).
- **You need a separate draft model** with the same tokenizer, usually from the same family. Medusa and EAGLE target this deployment cost.
- **Narrow evaluation.** Walltime is measured only for T5 on two text tasks; LaMDA and GPT-like results are α only.

## Relation to other systems

- **Chen et al., "Accelerating Large Language Model Decoding with Speculative Sampling" (DeepMind, arXiv 2302.01318).** This is the concurrent, independent version of the same algorithm. Per its abstract, a draft model proposes short continuations, the target scores them in parallel, and a modified rejection sampler preserves the target distribution "within hardware numerics". It reports 2–2.5x on Chinchilla 70B in a distributed setup. Leviathan et al. cite it as "similar 2X-2.5X" (§5). Chen et al. measure a large distributed decoder-only model; this paper adds the α/D_LK theory and the γ/c/FLOP analysis.
- **Medusa (Cai et al., arXiv 2401.10774).** Medusa drops the separate draft model. Extra decoding heads on the target predict several future tokens, and tree attention verifies many candidate continuations in one pass. Its abstract reports over 2.2x for Medusa-1 (frozen backbone) and 2.3–3.6x for Medusa-2 (joint fine-tune). Its "typical acceptance" scheme trades exact distribution preservation for a higher acceptance rate.
- **EAGLE (Li et al., arXiv 2401.15077).** EAGLE drafts at the feature level: it predicts the target's second-to-top-layer features, with the token sequence shifted one step ahead to resolve uncertainty. It keeps a distribution-preserving verifier. Its abstract reports 2.7–3.5x latency and 2x throughput on LLaMA2-Chat 70B.
- **SpecInfer (Miao et al., arXiv 2305.09781, ACM DOI 10.1145/3620666.3651335).** SpecInfer generalises a single draft chain to a token tree built from small speculative models. The LLM becomes a "token tree verifier" using tree-based parallel decoding. Its abstract reports 1.5–2.8x for distributed and 2.6–3.5x for offloading inference over existing serving systems.
- **vLLM speculative decoding (official docs, docs.vllm.ai).** vLLM is a production implementation inside a continuous-batching server. It supports draft models, EAGLE, MTP, n-gram and suffix decoding, configured through `speculative_config` (`method`, `model`, `num_speculative_tokens`, ...). The docs scope it to reducing inter-token latency "under medium-to-low QPS" for memory-bound workloads. They say sampling is "theoretically lossless up to the precision limits of hardware numerics" with the standard rejection sampler. Outputs and logprobs can still differ because of floating-point and batch-size effects, and the FLy verification mode is deliberately not distribution-preserving.

## Takeaways for practice

- **Measure α offline.** Because α = E[Σ min(p, q)] (Cor. 3.6), you can estimate α for a candidate draft from logged logits at the production temperature and top-k, then pick γ with Thm 3.8 before any latency benchmark.
- **Size the draft by c as well as α.** T5-large had the best α and the worst speedup (Table 2/4). Aim for about 100x smaller than the target, or for near-zero-c drafters (n-gram/suffix lookups, heads on the target).
- **Batching consumes the same idle compute (my analysis, not in the paper).** Speculation and batching compete for the same spare FLOPs. As batch size grows, decode moves from memory-bound to compute-bound. The "verification is as cheap as one token" assumption behind Thm 3.8 then breaks, and the wasted-FLOP factor of Thm 3.11 becomes a direct throughput loss. A scheduler should lower γ, or turn speculation off, as load rises, which matches vLLM's "medium-to-low QPS" scoping.
- **Plan for ragged accepted lengths (my analysis).** Each sequence in a batch accepts a different n per step. The scheduler must handle variable-length appends, reserve KV slots for γ+1 positions, and roll back rejected entries in both the draft and target KV caches.
- **Exactness depends on the sampler being implemented correctly.** Drafts must be sampled from the same standardised distribution the verifier assumes, and q must be kept, not just the token id. Heuristic or lenient acceptance (A.5, Medusa's typical acceptance, vLLM FLy) is a quality-versus-latency product decision, not a free win.
- **Adaptive γ is worth building.** The oracle estimate (~60%, §3.5) is the headroom for per-request or per-step γ control.
