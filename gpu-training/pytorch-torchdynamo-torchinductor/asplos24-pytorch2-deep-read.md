# PyTorch 2: Faster Machine Learning Through Dynamic Python Bytecode Transformation and Graph Compilation

> **Why it matters:** It shows that graph compilation can be added to an eager, define-by-run framework without asking users to rewrite code, by capturing graphs at the CPython bytecode level with guards and graph breaks, and lowering them through a small Python-defined loop IR to Triton/C++.

## Problem

Eager frameworks see one operator at a time, which blocks cross-operator optimizations such as fusion. Earlier PyTorch capture mechanisms (Section 2) each gave up soundness (`jit.trace`, `fx.symbolic_trace`), coverage (`jit.script`, all-or-nothing) or overhead (Lazy Tensors). The goal is capture that is sound, works on arbitrary Python, falls back gracefully, and adds little overhead.

## Core design

### TorchDynamo: bytecode-level graph capture (Section 3)

- **Hook point.** A custom hook on the CPython frame evaluation API (PEP 523) intercepts each frame, rewrites its bytecode and caches the result. Per frame: skip if marked or past cache size limits (no number given); if cached, run the guard function; otherwise analyze, compile and cache (Section 3.2).
- **Symbolic evaluation.** Dynamo interprets bytecode instruction by instruction, tracking the stack, locals, exception state, the FX graph being built, guards and pending side effects. Python values are modeled by `VariableTracker` subclasses (e.g., `TensorVariable`, `ListVariable`).
- **Guards.** For each transformed `PyCodeObject`, Dynamo generates one Python function that checks all guards and returns True if the compiled artifact is safe to reuse. The paper counts 30 guard types at the time of writing (Section 3.3).
- **Inlining.** Function calls are inlined where possible; if inlining fails, the analysis rolls back and places a graph break at the call site.
- **Side effects.** Python-state mutations are deferred and replayed in generated bytecode after the graph runs; repeated writes collapse into one.
- **Graph breaks (Section 3.8).** On unsupported code, Dynamo compiles the partial graph, emits bytecode that runs the graph, then runs the unsupported code in plain CPython, then calls a generated continuation `resume_at_X(...live vars...)` that jumps into the middle of the original function. Because continuations are ordinary Python functions, they re-enter Dynamo recursively, so the rest of the function is captured too.

### AOTAutograd (Section 3.9)

Runs eager autograd on fake tensors to capture a joint forward+backward graph. A min-cut algorithm splits it into forward and backward graphs optimized for memory, with backend-specific rematerialization of activations that are cheap to recompute. It also functionalizes the graph (mutations replaced by functional ops) and applies decompositions. Data-dependent operations do not work with fake tensors and cause graph breaks.

### TorchInductor (Section 4)

- **Decompositions and lowerings.** Large ops are decomposed into simpler ones (191 decompositions, 387 with overloads), then lowered into the IR (lowerings for 433 operators, 1605 with overloads). Operators without a lowering fall back to the eager kernel.
- **Define-by-run loop-level IR (Section 4.3).** Loop bodies are executable Python functions (`inner_fn`) that compute one element of a buffer by calling primitives in a virtualized `ops.*` namespace (54 primitives at the time of writing). Analysis and codegen work by swapping the handler behind `ops.*` and running the function, so the same body serves for dependency analysis, indexing analysis and code emission. `TensorBox`/`StorageBox` mirror `torch.Tensor`/`torch.Storage` (views vs. storage), `ComputedBuffer` holds a `Pointwise`, `Reduction` or `Scatter` body.
- **Scheduler and fusion (Section 4.4).** Greedy, iterative: `Scheduler.can_fuse` checks legality, `Scheduler.score_fusion` orders candidates (by fusion category, estimated memory traffic saved, and distance in the graph); the loop repeats until no fusion remains, since fusions can enable more fusions.
- **Triton codegen (Section 4.5).** Kernels operate on blocks of `XBLOCK` elements. Small reductions become persistent reductions (whole reduction in one block); larger ones loop with a block-sized accumulator. Generated code includes boilerplate for block-size heuristics and autotuning. Matmuls/convolutions can use Triton templates, selected by an autotuner under `mode="max-autotune"`.
- **C++ codegen (Section 4.6).** CPU kernels are C++ with OpenMP, in a vectorized variant (tiling, mapping ops to `at::vec::Vectorized`) and a scalar variant.
- **Wrapper codegen (Section 4.7).** Generates the Python or C++ code that allocates buffers and launches kernels. With `mode="reduce-overhead"`, CUDA Graphs remove wrapper overhead, enabled only when safety conditions hold.

### Dynamic shapes (Section 5)

Each symbolic size carries a hint (its value on the first input); shape conditionals follow the hint and add a guard. No dynamic rank. Sizes 0 and 1 become guarded constants; `mark_dynamic(tensor, dim)` forces a dimension symbolic. Data-dependent ops (`.nonzero()`, `.item()`) produce unbacked symbolic integers; control flow on them forces a graph break. Meta-function coverage was 2657 of 3028 ops (with overloads).

## Limitations

- No dynamic rank; shape specialization is driven by the first input's hints, so new shape patterns cost recompilation (Section 5).
- Data-dependent control flow, `.item()`/`.tolist()`, and non-PyTorch libraries such as NumPy still cause graph breaks (Section 6); TorchBench averages 21.1 graphs per model.
- CUDA Graphs only apply when safety conditions hold.
- The paper reports no compile-time or memory measurements, although compile cost is the main operational cost of a JIT.
- Single-GPU and single-CPU evaluation only; no distributed setting.
- (Own analysis) Guards are evaluated in Python per call, so very small or launch-bound models feel the overhead most, consistent with the 0.95x TorchDynamo-only TorchBench inference result in Table 3.

## Relation to other systems

- **TorchScript (`jit.trace`/`jit.script`):** trace silently misses control flow; script parses the AST and is all-or-nothing. Dynamo keeps Python semantics with guards and falls back via graph breaks (Table 1).
- **Lazy Tensors / PyTorch/XLA:** captures every iteration at the C++ level, delays launches and recompiles on graph-hash change; Dynamo captures once per guarded frame (Table 2).
- **torch.fx.symbolic_trace:** same FX output, but proxy tracing is unsound (can bake random values into constants, drops global side effects).
- **JAX (`jax.jit`) / XLA:** require pure functions and no data-dependent Python control flow; PyTorch 2 accepts arbitrary Python.
- **TVM, nvFuser, NNC (Halide-inspired, Section 4.8):** evaluated as alternative Dynamo backends in Table 3. (Own analysis) Inductor instead uses a Python define-by-run IR and leaves block-level codegen to Triton.

## Takeaways for practice

- (Own analysis) Interpreter-level capture with guards gives a "compile what you can, run the rest eagerly" contract: user code rarely breaks, but performance silently depends on graph-break count. Make graph breaks and recompilations observable per job.
- Fusion plus inlining carry most of the gain (Table 4); without both, Inductor is slower than eager.
- In Table 3, TorchInductor's training speedups are below its inference speedups in each GPU setting; do not assume inference-like gains for training capacity planning.
- (Own analysis) Compilation is JIT and shape-guarded, so variable-shape inference traffic (dynamic batch, sequence length) can trigger recompiles; warm caches, bucket shapes, or mark dims dynamic before putting compiled models behind a latency SLO.
- (Own analysis) Because compile time is not reported, measure it in your own pipeline: for short-lived jobs or autoscaled inference replicas, cold-start compile time may outweigh steady-state speedups.
