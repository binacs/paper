# Pond: CXL-Based Memory Pooling Systems for Cloud Platforms

## TL;DR

Pond is a CXL-based memory pooling system for public cloud platforms that combines small pools (8-16 sockets) with ML-driven per-VM allocation of local vs. pool memory to cut DRAM cost while staying within 1-5% of same-NUMA-node performance.

## Problem & Motivation

Public cloud providers must simultaneously satisfy stringent performance requirements and keep hardware costs low, and main memory (DRAM) is a major driver of both. Memory pooling can improve DRAM utilization and thus reduce cost, but naive pooling is hard to reconcile with cloud performance goals because remote/pool memory access adds latency and can degrade VM performance.

The paper asks whether pooling can be done in a way that both meaningfully reduces DRAM cost and keeps performance close to what VMs would get from memory on their own NUMA node.

## Key Ideas

- Build pooling on the CXL standard, which provides load/store access to pool memory rather than slower network-style access.
- Insight 1: production cloud trace analysis shows that pooling across only 8-16 sockets captures most of the utilization benefit, so a small pool with low access latency is sufficient.
- Insight 2: machine learning models can accurately predict how much local memory and how much pool memory to allocate to each VM so that its performance resembles same-NUMA-node memory.
- Combine small-pool topology with per-VM allocation prediction to meet cloud performance goals while reducing DRAM cost.

## System Design

- Pool memory is accessed via CXL load/store semantics, enabling fine-grained use of pooled DRAM.
- The pool is deliberately kept small (spanning roughly 8-16 sockets) to bound access latency while still capturing most pooling benefits.
- An allocation mechanism assigns each VM a split of local and pool memory, driven by ML models trained to predict allocations that yield same-NUMA-node-like performance.
- Control flow centers on predicting per-VM memory placement and provisioning pool capacity accordingly; data flow is direct load/store to pool memory over CXL.

## Evaluation

- Evaluated on 158 workloads.
- Headline result: DRAM costs reduced by 7% while performance stays within 1-5% of same-NUMA-node VM allocations.
- The evaluation validates both the small-pool sizing claim (from production trace analysis) and the accuracy of the ML-based local/pool allocation prediction.

## Takeaways

- Most memory-pooling benefit is achievable with modest pool sizes (8-16 sockets), which keeps latency low and avoids large-pool complexity.
- Accurate per-VM prediction of local vs. pool memory needs is the key enabler for meeting performance targets under pooling.
- CXL load/store access makes pooling viable for latency-sensitive cloud workloads in a way network-attached memory would not.
- A 7% DRAM cost reduction with 1-5% performance overhead is the concrete trade-off claimed for cloud deployment.

## Related Work

The abstract positions Pond against prior memory pooling approaches implicitly by arguing that pooling is challenging under cloud performance requirements; it builds on the CXL standard for load/store pool access and claims to be the first pooling system that both meets cloud performance goals and significantly reduces DRAM cost.

## Open Questions

- The abstract reports only a 7% DRAM cost reduction; how the benefit scales with larger pools, different workload mixes, or higher utilization targets is unclear.
- Reliance on ML models for allocation prediction raises questions about model accuracy drift, retraining overhead, and behavior on unseen workloads.
- The 1-5% performance overhead may be unacceptable for some latency-critical tiers; which workloads fall at the high end is not specified.
- Dependence on CXL hardware availability and maturity, plus fault handling and isolation for shared pool memory, are not addressed in the abstract.
