# Pond: CXL-Based Memory Pooling Systems for Cloud Platforms

## TL;DR

Pond is a CXL-based memory pooling system for cloud platforms that combines small 8–16 socket pools with ML-driven per-VM local/pool memory allocation to cut DRAM cost by 7% while staying within 1–5% of same-NUMA-node performance.

## Problem & Motivation

Cloud providers must simultaneously satisfy strict performance SLAs and keep hardware costs low, and main memory (DRAM) is a major driver of both. Memory pooling can raise DRAM utilization and lower cost, but conventional pooling approaches struggle to meet cloud-grade performance requirements, largely because remote/pooled memory access adds latency and can degrade VM performance.

The paper asks whether pooling can be done in a way that both meets cloud performance goals and meaningfully reduces DRAM cost, rather than trading one for the other.

## Key Ideas

- Build pooling on CXL, which provides load/store access to pool memory rather than slower network-style remote memory.
- Use production trace analysis to show that pooling across only 8–16 sockets captures most of the benefit, motivating a small-pool design with low access latency.
- Use machine learning models to predict, per VM, how much local versus pool memory to allocate so that performance resembles same-NUMA-node memory.
- Combine a small physical pool (for latency) with intelligent allocation (to avoid performance loss from placing too much hot data in the pool).

## System Design

- Pond is a memory pooling system for cloud platforms built on the CXL standard for load/store access to pooled memory.
- It adopts a small-pool topology spanning roughly 8–16 sockets, chosen because trace analysis shows this scale captures most pooling benefits while keeping access latency low.
- A per-VM allocation mechanism uses trained ML models to decide the split between local memory and pool memory for each VM.
- The allocation is tuned so that a VM's memory performance resembles that of a same-NUMA-node allocation, i.e., the pool is used to absorb capacity without pushing latency-sensitive working sets onto it.

## Evaluation

- Evaluated on 158 workloads.
- Headline result: DRAM costs reduced by 7%.
- Performance stays within 1–5% of same-NUMA-node VM allocations.
- The design choices are grounded in analysis of cloud production traces (pooling across 8–16 sockets suffices for most benefits).

## Takeaways

- Small pools (8–16 sockets) may be sufficient to realize most pooling gains, avoiding the latency penalty of large pools.
- CXL load/store semantics make pooled memory viable for cloud workloads in a way network-attached memory is not.
- Per-VM, ML-predicted local/pool memory splits are the key to hiding pooling's performance cost.
- Modest cost savings (7%) can be acceptable when paired with near-native performance (1–5% overhead).

## Related Work

The abstract positions Pond against prior memory pooling efforts implicitly, framing it as the first pooling system to both meet cloud performance goals and significantly reduce DRAM cost; it builds on the CXL standard rather than earlier interconnect approaches.

## Open Questions

- How robust are the ML allocation models across workload drift, new VM types, and adversarial or unpredictable tenants?
- What happens under CXL pool failure, contention, or oversubscription, and how is isolation maintained across tenants?
- Does the 7% cost reduction hold at larger fleet scales and with CXL hardware costs and refresh cycles included?
- How sensitive are results to the 8–16 socket pool size assumption and to production trace representativeness?
