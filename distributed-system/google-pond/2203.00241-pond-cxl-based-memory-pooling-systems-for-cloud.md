# Pond: CXL-Based Memory Pooling Systems for Cloud Platforms

## TL;DR

Pond is a CXL-based memory pooling system for cloud platforms that combines small-pool designs with ML-driven per-VM local/pool memory allocation to cut DRAM cost while staying within 1–5% of same-NUMA-node performance.

## Problem & Motivation

Cloud providers must simultaneously satisfy strict performance SLAs and keep hardware costs low, and main memory (DRAM) is a major driver of both. Memory pooling can raise DRAM utilization and lower cost, but naive pooling violates cloud performance requirements because remote/pool memory access adds latency and bandwidth overhead.

The paper asks whether pooling can be done in a way that both meaningfully reduces DRAM cost and keeps VM performance close to that of memory attached to the same NUMA node.

## Key Ideas

- Build pooling on CXL load/store access to shared pool memory rather than slower network-based disaggregation.
- Production trace analysis shows that pooling across only 8–16 sockets captures most of the utilization benefit, motivating a small-pool design with low access latency.
- Use machine learning models to predict, per VM, how much local versus pool memory to allocate so that performance resembles same-NUMA-node memory.
- Combine a small physical pool with intelligent placement/allocation to trade a small amount of performance for meaningful DRAM cost savings.

## System Design

- Pool memory is exposed via CXL and accessed with load/store semantics, keeping access latency low compared to remote-memory fabrics.
- The design is organized around small pools spanning roughly 8–16 sockets, chosen because trace analysis shows most pooling benefit is realized at that scale.
- A per-VM allocation policy, driven by trained ML models, decides the split between local DRAM and pool memory for each VM.
- Control flow: the allocator uses workload/VM characteristics to predict a suitable local/pool ratio, then provisions memory accordingly so that the VM's performance stays close to same-NUMA-node behavior.

## Evaluation

- Evaluated on 158 workloads.
- Compared against same-NUMA-node VM memory allocations as the performance reference.
- Headline result: DRAM costs reduced by 7% while performance stays within 1–5% of same-NUMA-node allocations.

## Takeaways

- Small pools (8–16 sockets) may be sufficient to capture most DRAM pooling benefits, avoiding the latency penalty of large pools.
- CXL load/store pooling is a viable substrate for cloud memory disaggregation when paired with careful allocation policy.
- ML-based prediction of local-vs-pool memory ratios is a practical lever for meeting performance targets while saving cost.
- A 7% DRAM cost reduction with 1–5% performance overhead is the claimed operating point for cloud deployment.

## Related Work

The abstract positions Pond against prior memory pooling approaches that fail to meet cloud performance requirements, and frames it as the first pooling system to both meet cloud performance goals and significantly reduce DRAM cost. It builds on the CXL standard for load/store pool access.

## Open Questions

- How robust are the ML allocation models across workload drift, new instance types, and adversarial or unseen workloads?
- What are the failure, isolation, and security implications of shared CXL pool memory across tenants?
- How does the 7% cost saving scale with pool size, CXL generation, and real deployment overheads?
- How sensitive are results to the 8–16 socket pool sizing assumption under different production trace mixes?
