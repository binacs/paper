# The Design and Operation of CloudLab

> **Why it matters:** A rare operator's-eye report on a multi-site bare-metal research cloud, showing that deep "under the hood" choices (the topology mapper, constraint checks, reservation admission control) shape user behavior as much as the hardware does.

## Problem

Systems researchers need what commercial IaaS hides: unmediated access to physical hardware, control over network topology down to layer 1, and performance predictable enough for repeatable experiments. CloudLab provides this as a shared, federated testbed. The paper (21 authors; the first eight are listed above) is not a new-mechanism paper. It has two stated contributions (Sec. 1): a description and usage analysis of the facility over its operation (Sec. 2), and an analysis of how specific low-level design decisions affect the user experience (Sec. 3). The abstract covers four years of operation; the prose does not give an exact end date for the overall data window.

## Core design

### Profile / experiment model (Sec. 2.1)

- A **profile** describes the hardware an experiment runs on (servers, switches, etc.) and the software to put on it: disk images, git repositories and scripts to run. Users can write their own profiles and share them.
- An **experiment** is an instance of a profile. Every instance runs on a separate set of hardware, so one profile can be instantiated many times concurrently. The paper says 200–300 experiments are typically active at once.
- **Lifetime is leased, not open-ended.** Every experiment starts with an expiration a few hours out. Short extensions (hours to days) are granted automatically. Longer ones (weeks to months) are reviewed by administrators, who use coarse idleness signals such as CPU load and packet counts.
- **Hardware types as the unit of repeatability.** Identical nodes from the same batch share one hardware type label, and users can request a type explicitly. CloudLab also excludes servers whose performance is not statistically representative of their type. The detection method is the authors' earlier OSDI 2018 work on performance variability, cited but not described here.
- The official manual (current, not the 2019 snapshot) fills in what the paper omits: profiles are GENI RSpecs, usually generated by geni-lib Python scripts, optionally kept in a git repo. They are versioned, so a paper can cite one exact version.

### Bare-metal provisioning and isolation

- The paper says only that instantiating a profile provisions the selected hardware with the profile's software and configuration (Sec. 2.1). It does not describe imaging or node reset.
- The official technology page states that CloudLab PXE-boots all physical nodes, uses a custom multicast disk loader (Frisbee is in its reading list), and runs a boot-stage state machine that can give up on a failed machine and provision a replacement. It also mentions TPM-based secure disk loading.
- **Performance isolation** is claimed as strong between tenants (Sec. 2.1). It comes from exclusive bare-metal allocation plus the exclusion of outlier servers.
- **Topology control:** at Utah, 200 servers sit on both a 25 Gbps Ethernet network and a "layer-1" network. That network can wire nodes to user-controllable Ethernet switches or directly to each other, and those switches are allocated to one user at a time (Sec. 2.2). The paper does not describe VLAN-level network isolation.

### Sites and federation (Sec. 2.1–2.2)

- Three hardware sites, each with its own focus: Utah (scale-out; 585 HPE Moonshot low-power servers, 45 per chassis), Wisconsin (networking and storage; dual-socket Cisco servers in a Clos network, many with GPUs) and Clemson (analytics and HPC; Dell servers plus a 40 Gbps QDR InfiniBand network).
- CloudLab is federated with other facilities, including Emulab and Apt. With them, the pool reaches about 2,250 servers. Its control software descends from Emulab, GENI and Apt. The paper gives no detail on aggregate managers or cross-site accounts. The official technology page says any testbed that supports the GENI APIs may federate with CloudLab.
- No hardware had been retired in the period covered, and the server count grew roughly fourfold over it (Sec. 2.2).

### Resource mapping and error messages (Sec. 3.1)

- Mapping a requested topology onto physical nodes and links is NP-hard; the paper says it resembles subgraph isomorphism. The mapper is derived from Emulab's and uses simulated annealing.
- The paper's key insight is about failure UX. A deterministic, conservative heuristic wrapper runs around the annealer and turns common failures into actionable messages, such as too few nodes of a type, a reservation conflict, or an OS that does not run on that hardware. It must never reject a request the mapper alone would have accepted. The least helpful messages come from inside the annealer.

### Interactive feasibility checks (Sec. 3.2)

- A simplified constraint model checks whether *some* mapping should exist, without computing one. Each group is a whitelist of acceptable combinations, and a candidate must match all groups. Memoization over unique candidates reduces the cost from O(c·g·s) to O(unique(c)·g).
- It runs in the browser in Jacks, the topology GUI, to disable conflicting options, and at instantiation to grey out clusters where a request will definitely fail. The paper contrasts this with EC2's dashboard, which also hides infeasible configurations.

### Reservations (Sec. 3.3)

- **Motivation:** pure FCFS favors small experiments and cannot guarantee resources for deadlines or scheduled events.
- **Model:** a reservation is a guarantee of N_r nodes *of one hardware type* in a window [s_r, e_r], not a scheduled job. Any number of experiments may run under it. Staff approve requests, small ones are auto-approved, and users can validate a request before submitting it.
- **Late binding:** because nodes within a type are interchangeable, the scheduler counts nodes instead of mapping them, and binds at instantiation. Feasibility uses a tentative free-node schedule built from active experiments and approved reservations: O(n log n) to build and O(n) to check, with n in the hundreds.
- **Admission control instead of preemption:** as a reservation's start approaches, new experiments and extensions that would leave too few free nodes are denied. Running experiments are not evicted. Reservations cannot span types such as "any server", a rigidity accepted to keep checks fast.

## Limitations

- It is a descriptive operations study. Provisioning, imaging and isolation mechanisms are delegated to earlier Emulab/Frisbee work and the manual, so the paper offers little on *how* bare-metal turnaround or network isolation is achieved.
- Reservations are per hardware type only. The authors call hardware-type confusion an open problem, and their claim that reservation value grows super-linearly as free capacity nears zero is a hypothesis, not a measurement.
- Trusting users to "reserve what they need and use what they reserve" relies on no direct penalties and on staff approval. (Own analysis) That may not carry over to a commercial or adversarial tenant base.
- Inconsistencies noticed: Sec. 3.1 refers to "four" unhelpful mapper messages, while Table 2 as extracted appears to mark three rows unhelpful. Table 2's column headers did not extract cleanly, so its per-row values are omitted here. (Own analysis) The Table 1 percentages, as extracted, do not form a clean partition, although Sec. 2.5 says papers were categorized by primary area.
- The 2,250 figure includes federated Emulab and Apt resources (Sec. 2.1), not CloudLab's three sites alone.

## Relation to other systems

- **Emulab / Apt / GENI:** CloudLab's control software descends from all three, and it federates with Emulab and Apt (Sec. 2.1). The mapper is derived from Emulab's annealer (Sec. 3.1).
- **Chameleon:** users there request specific servers by ID, which the paper says "trades flexibility for simplicity". CloudLab instead late-binds anonymous nodes of a type (Sec. 3.3).
- **Amazon EC2:** cited for its dashboard, which hides infeasible configurations. CloudLab uses a two-phase design: a fast in-browser constraint check, then the full mapper (Sec. 3.2).
- **PlanetLab, Grid'5000, Open Cirrus, PRObE, Jetstream, Comet:** prior facility studies. The paper's distinction is its focus on how the control framework affects user experience and behavior, which it says has not been studied for those facilities (Sec. 4).

## Takeaways for practice

- Treat scheduler and mapper **error messages as a product surface**. A conservative, deterministic pre-check wrapped around a stochastic solver can explain most failures without rejecting anything feasible.
- **Cheap feasibility checks belong in the request UI.** A simplified whitelist model run before submission prevents doomed requests.
- **Reservations as capacity guarantees with late binding** over interchangeable node pools keep admission control linear, and avoid preemption by denying overlapping new work instead of evicting old work.
- **Normalize hardware into performance-homogeneous types** and drop statistical outliers, so "same type" means comparable results.
- (Own analysis) Demand is bursty, deadline-driven and long-tailed. Capacity planning and fairness policies for GPU or sandbox fleets should be tested against such traces, not against steady-state averages. The released dataset is one such trace.
