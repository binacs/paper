# Hyperledger Fabric: A Distributed Operating System for Permissioned Blockchains

> **Why it matters:** With execute-order-validate, untrusted and possibly non-deterministic code runs before consensus, ordering becomes a pluggable state-blind service, and peers only run deterministic validation.

## Problem

Earlier permissioned blockchains (Tendermint, Chain, Quorum, and Fabric's own v0.6 prototype on PBFT, Sec. 2.1, 2.4) used **order-execute**: consensus orders transactions, then every peer executes them sequentially. The costs (Sec. 1, 2.2–2.3):

- **Sequential execution** limits throughput, and a slow or malicious contract can stall the chain. Gas needs a native currency.
- **Non-determinism** in general-purpose languages forks state, which v0.6 users actually hit (Sec. 2.4).
- **Confidentiality** suffers when every contract runs on every peer.
- **Trust and consensus are fixed**: the BFT assumption (n > 3f) and the protocol are hard-coded.

The v0.6 lesson: consistency, security and performance must not depend on developers behaving well (Sec. 2.4).

## Core design

### Roles and channels (Sec. 3.1)
- **Clients** submit proposals, collect endorsements and broadcast transactions.
- **Peers** hold ledger and state and validate every block. Some also **endorse** a given chaincode.
- **Ordering service nodes (OSNs)** only order. They neither execute nor validate, and hold no application state.
- **Channels** are separate blockchains sharing one ordering service. Consensus across channels is not coordinated.

### Phase 1: execute and endorse (Sec. 3.2)
- The client sends a signed proposal (identity, chaincode ID, operation, arguments, nonce, transaction ID) to the endorsers the policy requires.
- Each endorser **simulates** the chaincode on its local state, uncoordinated, in a Docker container (Go, Java, Node; Sec. 4.5). The output is a **readset** (keys with versions) and a **writeset** (keys with new values). Nothing is persisted.
- The endorser signs via the endorsement system chaincode (ESCC), by default just a peer signature (Sec. 4.6).
- The client gathers endorsements until the policy is satisfied. Results must match, so divergent endorsers (non-determinism or stale state) just fail to endorse. A non-deterministic chaincode "can only endanger the liveness of its own operations."

### Endorsement policies (Sec. 3.1, 4.6)
- A policy is a monotone logical expression over sets of principals, for example "three out of five" or `(A ∧ B) ∨ C`.
- Only administrators can set or change policies, through system management functions. Chaincode developers cannot.
- Each chaincode references an ESCC and a validation system chaincode (VSCC). The VSCC checks that valid endorsement signatures satisfy the expression. Fabcoin ships a custom VSCC (Sec. 5.1).

### Phase 2: ordering (Sec. 3.3, 4.2)
- Interface `broadcast(tx)` / `deliver(s)`, producing hash-chained blocks. Safety: agreement, hash-chain integrity, no skipping, no creation. Liveness: validity.
- The orderer does **not** filter duplicates or conflicts. Peers do.
- A block is cut at a maximum transaction count, a maximum byte size, or a timeout. On timeout an OSN broadcasts a *time-to-cut* transaction, and all OSNs cut at the first one for that block number, which keeps batching deterministic.
- Implementations: **Solo** (development), production **Kafka** (CFT, OSNs proxy to Kafka), and a proof-of-concept **BFT-SMaRt** without reconfiguration or access control.
- Optional **gossip** (push/pull over gRPC with mutual TLS, Sec. 4.3). An elected leader peer pulls blocks from the orderer.

### Phase 3: validate (Sec. 3.4, 4.4)
1. **VSCC policy check**, in parallel across a block's transactions. Failures are marked invalid.
2. **Read-write (MVCC) check**, sequential. The peer transaction manager (PTM) stores `(key, val, ver)`, where the version is the block number plus the writing transaction's index in that block. A readset version that differs from current state invalidates the transaction. For range queries the PTM re-executes the query and compares a hash kept in the readset.
3. **Ledger update**: append the block, persist a validity **bit mask**, apply valid writesets, and record a *savepoint* (highest applied block) for recovery.

Invalid transactions stay in the ledger for audit (Sec. 3.4). The block store is append-only files, and state lives in LevelDB or CouchDB (Sec. 4.4). The paper calls the whole scheme **hybrid replication**: passive replication before consensus, active replication after it, in the Byzantine model (Sec. 1). Trust is per organization, and the orderer's fault model depends on the plug-in (Sec. 3.5).

**Fabcoin** (Sec. 5.1), the benchmark workload, is a UTXO currency stored as `(txid.j, (amount, owner, label))`. MINT needs a central-bank signature. Its VSCC skips double-spend checks and leaves them to the MVCC step.

## Limitations

- **Contention.** Under hot keys a client may fail to satisfy the policy (Sec. 3.2). CRDTs and a per-chaincode lead endorser are future work.
- **Sequential validation.** VSCC scales "quasi-linearly" with CPU, but the read-write and ledger stages are sequential and dominate (Exp. 2). Pipelining and parallel read-write checks are open work.
- **CFT ordering in production.** BFT-SMaRt is only a proof of concept (Sec. 4.2). In the WAN runs the 3 Tokyo OSNs' links saturate (Sec. 5.2).
- **Large transactions**, because they carry certificates (Sec. 5.2).
- **Coarse confidentiality**: channels and endorser subsets, no cross-channel coordination, cryptographic techniques left to future work (Sec. 3.1, 8).
- **Narrow evaluation**: one synthetic workload on one cloud. The paper says Fabric "is not yet performance-tuned" (Sec. 5).
- **Internal inconsistency**: the abstract claims scaling to "over 100 peers", but the largest reported run has exactly 100 peers (Exp. 4, Table 2 caption).
- (Own analysis) The evaluation is of Fabric v1.1, so treat its numbers as a snapshot of that release, not of current Fabric.

## Relation to other systems

- **Kemme & Alonso replicated databases** (Sec. 7): the closest ancestor, but crash-fault only. Fabric generalizes it to Byzantine peers and per-application trust.
- **Eve** (Sec. 7): executes concurrently, checks matching outputs via consensus, and falls back to sequential execution. Fabric shares the independent execution but adds policies, a pluggable orderer and channels.
- **Byzantium / HRDB** (Sec. 7): active replication with deterministic operations and a fixed trust model.
- **Quorum, Tendermint, Chain, Sawtooth, MultiChain** (Sec. 7): all order-execute. Quorum's Raft leader assembles blocks.
- **Ethereum / Bitcoin** (Sec. 2.1, 3.4): permissionless, PoW, native currency, and ledgers that hold only valid transactions.
- **PBFT / BFT-SMaRt** (Sec. 2.1, 4.2): in Fabric these are orderer plug-ins, not the system's trust model.

## Takeaways for practice

- (Own analysis) **Separate deciding from ordering.** Speculative execution checked against versions at commit is the optimistic, shared-state scheduler pattern (Omega-style). It parallelizes until contention, then wastes work, so measure conflict rates first.
- **Keep the sequencer dumb.** A state-blind orderer can be swapped (Solo, Kafka, BFT). Ordering dominates latency (Table 1), and time-to-cut is the low-load latency knob (Sec. 5.2).
- **The commit path is the ceiling.** Signature checks scale with cores, but the sequential conflict check and storage writes do not. A RAM disk gained only about 9% (Exp. 3). (Own analysis) Profile per stage, as Table 1 does, before adding hardware.
- **Version keys by (block, tx index)** for cheap deterministic MVCC checks and an easy recovery savepoint. Hash range-query results to guard against phantoms.
- **Contain non-determinism at the edge.** Matching-output endorsement turns a buggy job into its own liveness failure, not a fork. (Own analysis) Agent sandboxes can reuse this: run in a container, sign the read/write effects, validate centrally.
- **WAN fan-out needs dissemination.** Gossip raised remote-site throughput over direct orderer delivery (Exp. 5, Table 2), because OSN uplinks saturated.
