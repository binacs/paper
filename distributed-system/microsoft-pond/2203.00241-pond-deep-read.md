# Pond: CXL-Based Memory Pooling Systems for Cloud Platforms

> **Why it matters:** Pond is the first full-stack design to show that a small CXL memory pool, combined with an ML-driven VM placement policy, can cut a public cloud's DRAM bill without breaking the "looks like local NUMA memory" performance contract for opaque VMs.

## Problem

DRAM is a large part of cloud server cost. Memory gets *stranded* when a server's cores are all rented out and its leftover memory cannot be sold. In Azure traces, about 6% of memory is stranded at 75% of cores scheduled. During high-utilization periods the 95th percentile reaches 25% (§3.1, Fig. 2a). Stranding shifts with the workload mix and hits many racks at once (Fig. 2b). A second inefficiency is *untouched* memory, meaning memory that customers rent but never touch. At the median it is about 50% of a VM's memory (§3.2).

Pooling would let capacity follow demand. But a cloud provider cannot change guest OSes or see inside customer VMs. It must also stay close to same-NUMA-node performance and avoid page faults on the critical path.

## Core design

### Small-pool CXL hardware (§4.1)
- Pond uses CXL.mem load/store access to a new **external memory controller (EMC)** ASIC. The EMC drives several DDR5 channels and exposes several ×8 CXL ports. It appears to each host as one logical device, which CXL standardizes as a *multi-headed device* (MHD).
- Up to **16 sockets** connect directly to one EMC, with no switch. Pools of 32–64 sockets need CXL switches in front of it.
- **Why small pools:** Trace simulation shows diminishing returns past 16–32 sockets (§3.1, Fig. 3). Pools of 8–16 sockets add about **70–90 ns** over NUMA-local DRAM. Switched rack-scale pools add more than 180 ns, because a switch costs at least 70 ns (§4.1, Fig. 7). The multi-headed EMC cuts latency by about one third against a switch-only design (Fig. 8).
- Capacity is managed in **1 GB slices**, each owned by at most one host. The EMC checks every access against a permission table.

### Pool management (§4.2)
- A **Pool Manager (PM)** on the EMC blade assigns slices with `Add_capacity(host, slice)`, which the host hot-plugs, and reclaims them with `Release_capacity`. Onlining takes microseconds per GB, but offlining takes **10–100 ms/GB**. VM starts would otherwise wait on offlining, so Pond keeps a buffer of unallocated pool memory and refills it asynchronously as VMs exit (§4.3, Fig. 9).
- Memory is statically preallocated to VMs, with no fault-driven paging (§7). Hosts interleave only across local memory, so an EMC failure affects only VMs with memory on that EMC.

### zNUMA (§4.2)
- Pool memory is presented to the guest as a **zero-core virtual NUMA node**. The hypervisor puts a memory block into SLIT/SRAT with no CPU entry. Guest kernels already prefer local-node memory, so if the zNUMA node is sized to the VM's untouched memory, the guest rarely touches it. No guest changes are needed.
- In production, zNUMA receives only 0.06–0.38% of accesses across the workloads shown (§6.2, Fig. 15).

### Prediction models (§4.4, §5)
- **Latency-insensitivity model:** a random forest (scikit-learn) over about 200 core-PMU counters, which work for opaque VMs. Top-down "DRAM bound" is a strong single feature, and the forest beats it slightly (§6.4.1, Fig. 12). Labels are pool-versus-local slowdowns from offline runs and internal A/B tests, and the model is retrained daily. It applies only to VMs with history, meaning a matching customer, VM type and location, which covers about 80% of VMs.
- **Untouched-memory (UM) model:** LightGBM quantile regression on VM metadata. The top feature is a high percentile (80th–99th) of untouched memory across the customer's VMs over the past week. The label is a VM's minimum untouched memory over its lifetime.
- **Decision (Fig. 13):** If the VM has history and is predicted insensitive, all of its memory goes on the pool. Otherwise, if UM is greater than 0, a GB-aligned, rounded-down UM amount goes on zNUMA and the rest is local. If UM is 0, the VM is all-local. Eq. 1 maximizes pool memory subject to *false positives + overpredictions ≤ 100 − TP*. Here **PDM** is the allowed slowdown versus all-local (for example 5%), and **TP** is the fraction of VMs that must stay within PDM (for example 98%).

### Control plane, QoS monitor and mitigation (§4.3, Fig. 11)
- Scheduling path: a VM request arrives (A1). The scheduler asks the ML serving system how much local memory to give it (A2), then tells the PM the host and the pool amount (A3).
- QoS path: the monitor reads hypervisor and PMU counters and uses the sensitivity model to judge whether a VM has exceeded PDM (B1–B2). If it has, the hypervisor moves the VM to **all-local memory** (B3). It copies pool pages to local DRAM at about **50 ms per GB** of pool memory (§4.2). This is a one-time, VM-level correction, not ongoing page migration. The monitor is budgeted for about 1% mispredictions (§6.4.3).

## Limitations

- **CXL latency was emulated.** CXL memory hardware was not available. The pool is emulated by disabling all cores on one socket of a two-socket server and using that socket's memory as remote NUMA memory (§5). The 182% and 222% scenarios match the measured remote/local ratios on the Intel and AMD testbeds (§6.1). This captures latency but not real CXL controller queuing, bandwidth or device behavior.
- The DRAM savings come from trace-driven simulation (§6.5), not from a pooled-hardware deployment. The EMC ASIC is assumed, not built.
- The sensitivity model is trained on 158 lab workloads, because opaque VMs report no performance. About 20% of VMs have no history and get only the conservative UM path.
- Allocation is static, so a VM found to be sensitive pays a full VM-level copy. Dropping static preallocation needs PCIe ATS/PRI or virtual IOMMUs (§7).
- The text is inconsistent in places. The §3.1 summary box gives p95 stranding as "3–27%, outliers 36%", while the body says 25% and 30%. Small-pool latency is 70–90 ns in the text and 75–90 ns in the Fig. 7 caption.

## Relation to other systems

- **Protean (OSDI 2020):** Protean is Azure's rule-based VM allocator for zones of 10k–100k machines, with multi-layer caches and concurrent allocation agents. It packs VMs onto servers with fixed local resources. Pond keeps that scheduler but changes the resource model under it. Memory becomes a per-VM local/pool split, with an ML prediction added to the allocation path (A2). Pond recovers the stranding that Protean-style packing leaves behind.
- **Google software-defined far memory (ASPLOS 2019):** Google builds far memory in software by compressing cold pages, using a kernel mechanism, a node agent and ML autotuning. About 20% of data sits in far memory at about 6 µs access latency. That approach needs kernel control and fault-driven page movement. Pond targets opaque VMs where neither is available. It pools memory in hardware at tens of nanoseconds and predicts the split at VM start instead of tracking page coldness at runtime.
- **TPP (ASPLOS 2023):** TPP is Meta's OS-level page placement for CXL tiered memory. It proactively demotes pages to CXL memory and promotes hot ones, staying within 1% of all-local on early CXL 1.1 samples. TPP needs a cooperating kernel and migrates pages dynamically. Pond assumes an untouchable guest and makes a static per-VM split through zNUMA. The two can be combined, with TPP-like tiering running inside a guest that sees a zNUMA node.
- **Heracles-style co-location (ISCA 2015):** Heracles is a feedback controller that co-locates best-effort tasks with latency-critical services, isolating shared resources to reach 90% average utilization without SLO violations. Pond's QoS monitor follows the same measure-and-back-off pattern. Its action, though, is coarse and one-shot (move the VM off the pool), and it reclaims stranded DRAM rather than idle cycles.

## Takeaways for practice

- Measure stranding per resource dimension first. A static local/pool ratio saves little (3%, against 7–9% with prediction, §6.5).
- Small pools keep most of the benefit. Topology (direct-attach versus switched) sets latency, and latency sets how many workloads can use the pool.
- Expose slow memory through interfaces the guest already understands, such as a zero-core NUMA node.
- Predict, then guard. Use false-positive-constrained models at placement time, an explicit misprediction budget (TP/PDM) and a cheap, bounded mitigation path.
- The same pattern fits accelerator platforms with tiered host or CXL memory: predict insensitive or untouched capacity per job at admission, rather than paging reactively.
