# Homa: a receiver-driven low-latency transport protocol using network priorities

## TL;DR

Homa is a receiver-driven transport protocol that uses in-network priority queues and controlled overcommitment to achieve ultra-low latency for short messages in datacenter networks, while also supporting high throughput for large messages.

## Problem & Motivation

Datacenter networks need to support a mix of short latency-sensitive messages (e.g., RPCs) and large throughput-sensitive flows. Existing transport protocols like TCP or DCTCP suffer from high tail latency for short messages under load, due to head-of-line blocking and inefficient priority management. The challenge is to provide both low latency for short messages and high utilization for long flows without sacrificing either.

## Key Ideas

- Receiver-driven priority allocation: each receiver dynamically assigns priorities to incoming flows based on remaining message size, ensuring short messages get highest priority.
- In-network priority queues: switches use strict priority queuing to preempt long flows for short messages.
- Controlled overcommitment: receivers intentionally overcommit their downlink bandwidth to keep links busy, using feedback to avoid congestion.
- Receiver-driven flow control: receivers grant credits to senders, controlling how much data can be sent, integrated with priority scheduling.

## System Design

Homa is a transport protocol implemented at the end hosts. Senders and receivers exchange control packets (GRANT, RESEND) to manage flow control and priority. Each receiver maintains a priority scheduler that assigns a priority to each incoming message based on its remaining size (smaller messages get higher priority). Senders transmit data packets with the assigned priority. Switches implement strict priority queues (e.g., 8 or 16 levels) to service higher-priority packets first. Receivers use a credit-based scheme to control sender transmission rates, and they overcommit their downlink capacity by issuing more credits than available bandwidth, relying on priority scheduling to resolve contention.

## Evaluation

The paper evaluates Homa using both a Linux kernel implementation on a 10 Gbps testbed and ns-2 simulations. Workloads include RPC-like traffic with varying message sizes. Baselines: TCP, DCTCP, pFabric, pHost, PIAS, NDP. Headline results: Implementation achieves 99th percentile RTT <15 μs for short messages at 80% load, ~100x lower than best published measurements. In simulations, Homa's latency is roughly equal to pFabric and significantly better than pHost, PIAS, and NDP for almost all message sizes and workloads. Homa also sustains higher network loads than pFabric, pHost, or PIAS.

## Takeaways

- Receiver-driven priority allocation is a simple yet effective way to achieve near-optimal latency for short messages.
- Controlled overcommitment can improve utilization without sacrificing latency.
- In-network priority queues are key to enabling preemptive scheduling of short flows.
- Homa demonstrates that a clean-slate transport can outperform existing protocols by orders of magnitude for tail latency.

## Related Work

Homa is positioned against prior datacenter transport protocols: pFabric (which also uses priorities but requires switch modifications and has scalability issues), pHost (host-based scheduling), PIAS (priority-based with limited priority levels), and NDP (receiver-driven but without priorities). Homa combines receiver-driven control with in-network priorities to achieve better latency and utilization.

## Open Questions

- How does Homa perform with very large numbers of priority levels (e.g., 64) or with shallow buffered switches?
- Can Homa be deployed incrementally in existing datacenters without switch upgrades?
- How does Homa handle congestion due to incast or transient bursts beyond overcommitment?
- What is the impact of Homa's control overhead (GRANT/RESEND packets) on CPU utilization at line rate?
