# Homa: A Receiver-Driven Low-Latency Transport Protocol Using Network Priorities

> **Why it matters:** Homa shows that a datacenter transport can get short-RPC tail latency close to the hardware minimum at high load. It does this with four ideas used together: blind transmission of the first RTT of data, the 8 priority queues commodity switches already have, receiver-side SRPT scheduling, and deliberate overcommitment of receiver downlinks.

## Problem

Request/response traffic in datacenters is dominated by very short messages. In three of the paper's five workloads, more than 85% of messages are under 1000 bytes (§2.1, Fig. 1). Existing transports were tuned for heavy-tailed workloads and for mean latency or throughput. Homa targets the 99th-percentile latency of short messages at high network load. Hardware can deliver one-way latencies of a few microseconds, so the remaining gap comes from queuing. Byte-stream transports (TCP, InfRC, and per-connection designs like pFabric, PIAS and NDP) also add head-of-line blocking, where a short message waits behind a long one to the same destination (§2.2, §3.1, §7). Central arbiters (Fastpass) and pure receiver credit schemes (ExpressPass) spend at least a round trip on scheduling, which is too slow for tiny messages (§2.2, §7).

## Core design

**Messages, not streams (§3.1, §3.8).** Homa is connectionless and RPC-oriented. Each RPC has an RPCid generated by the client. Server state scales with active RPCs, not with the number of clients. There are no explicit ACKs. Semantics are at-least-once: a server drops RPC state after it sends the last response packet, and duplicate suppression is left to higher layers.

**Packet types (§3, Fig. 3).** DATA carries a byte range and the total message length. GRANT authorizes bytes up to an offset and assigns a priority. RESEND asks for a byte range again. BUSY tells the receiver that a reply to RESEND will be late. All control packets travel at the highest priority.

**Sender (§3.2).** The first RTTbytes of every message go out immediately ("unscheduled"). The rest go out only as GRANTs arrive. The sender runs SRPT across its own outgoing messages and sends control packets first. In the RAMCloud implementation the sender keeps at most about two full-size packets queued in the NIC, so it can still reorder when a shorter message shows up (§4).

**Receiver-driven flow control (§3.3).** The receiver grants packet by packet and keeps about RTTbytes of granted-but-unreceived data outstanding per active message. Each incoming message therefore uses at most about RTTbytes of TOR buffer.

**Priorities (§3.4).** Priority levels (typically 8) are split between unscheduled and scheduled traffic.
- *Unscheduled.* The receiver measures what fraction of its incoming bytes is unscheduled and gives that share of the top levels to unscheduled packets. It sets size cutoffs so that each level carries the same number of unscheduled bytes, with smaller messages on higher levels. Senders learn the cutoffs from information piggybacked on other packets.
- *Scheduled.* Each GRANT carries a priority. Messages with fewer ungranted bytes get higher levels (SRPT). When there are fewer active messages than scheduled levels, the receiver uses the *lowest* scheduled levels. That leaves the higher levels free for a new, shorter message, which avoids "preemption lag" except when all scheduled levels are in use (Fig. 5).

**Controlled overcommitment (§3.5).** Senders do not always respond to grants at once. Granting to only one message at a time therefore wastes downlink bandwidth. A Homa receiver grants to at most one message per scheduled priority level, so the degree of overcommitment equals the number of scheduled levels. Messages that get no grants simply wait.

**Incast (§3.6).** Homa counts each node's outstanding RPCs. Above a threshold, new RPCs are marked so that their responses send only a few hundred unscheduled bytes.

**Loss (§3.7).** Receivers detect loss with timeouts of a few milliseconds and send RESEND.

**Implementation (§4).** Homa is a new transport inside RAMCloud. It uses DPDK kernel bypass with polling and is 3660 lines of C++, about half of them comments. The implementation does not yet measure incoming message lengths online, so priorities were precomputed from the benchmark workload.

## Limitations

- **Core assumed uncongested (§6).** Homa assumes congestion happens mainly at host downlinks. It relies on per-packet spraying and enough aggregate core bandwidth. The paper says latency would degrade if the core became congested.
- **Priorities are a scarce, shared resource.** Results depend on about 8 switch levels, and the split is tuned per workload. Multiple Homa instances sharing a link "may make conflicting decisions"; the paper leaves this to future work (§6). Tenant isolation is not discussed.
- **Workload knowledge.** Cutoffs come from the observed message-size distribution. The implementation used precomputed values (§4), so adaptation to changing workloads is not demonstrated in hardware.
- **Starvation of large messages.** SRPT gives the largest messages 99p slowdowns of 100x or more. The paper suggests reserving a small fraction of bandwidth for the oldest message but does not evaluate it (§5.1).
- **Bandwidth waste.** No protocol reaches 100% load. Homa's loss comes from the limited number of scheduled levels and from senders that do not respond (§5.2). The remaining tail comes mostly from link-level preemption lag, which only hardware changes could remove (Fig. 14).
- **Scale of evaluation.** The hardware testbed is 16 nodes on one switch. Multi-tier results come only from simulation, and the simulator omits software queuing delays (§5.2). Wide-area use is called "unlikely to work well" (§6).
- **Inconsistencies noticed in the paper.**
  - §5.2 says overcommitment accounts for up to 56 KB of the 146 KB maximum queue, "RTTbytes in each of 6 scheduled priority levels". The maximum is in the W4 column of Table 1, and W4 is configured with 1 unscheduled level and overcommitment 7. (Own analysis) One possible reading is that 6 messages are queued while a 7th drains at line rate, but the paper does not say so.
  - The "about 14 µs in all three loads" sentence (§5.1) is ambiguous about whether it means three workloads or three load levels.
  - The OMNeT++ reference URL is malformed ("http://https://...").
- (Own analysis) Later work, for example Aeolus (SIGCOMM 2020), questioned how proactive and receiver-driven transports handle the blind first-RTT burst under heavy load. That burst is exactly Homa's unscheduled traffic.

## Relation to other systems

- **pFabric:** Latency is similar, but pFabric needs switch features that do not exist today and loses bandwidth through drops and retransmissions. Homa uses standard priority queues and sustains higher load (§5.2, §7).
- **pHost:** Also receiver-driven, but it uses only two static priority levels and no overcommitment, and it cannot preempt a large message right away. Its maximum load is 58–73% (§2.2, §7).
- **PIAS:** Assigns priorities at the sender (multi-level feedback queues), which limits how well it approximates SRPT. Its tail latency is high for both short and long messages, and results are erratic across workloads (§2.2, §5.2).
- **NDP:** Trims packets and uses receiver pulls, but it schedules by fair share instead of SRPT and does not overcommit. It wastes 27% of receiver bandwidth at 70% load (§5.2, §7).
- **DCTCP / HULL / PDQ:** These use rate or queue control without in-network priorities, so they cannot preempt quickly (§7).
- **Fastpass, ExpressPass, QJUMP:** Central or receiver-credit scheduling adds about an RTT before the first byte. QJUMP's priorities are set manually per application (§2.2, §7).

## Takeaways for practice

- **Schedule where the bottleneck is.** Homa puts the scheduler at the receiver downlink, the resource that is actually congested, and lets senders transmit blindly only for the first RTT. Pull-based admission at the scarce resource generalizes to KV-cache transfer, parameter-server traffic and shuffle traffic in training and inference clusters.
- **Overcommit to hide straggling peers.** Granting to several candidates at once, bounded by the number of priority classes, trades a bounded amount of buffer for utilization. The W4 result, about 63% load versus 89% (§5.2), is a concrete argument against strict one-at-a-time admission in any credit-based scheduler.
- **Derive class cutoffs from measured size distributions.** Balancing bytes per class, not message counts, matters: a count-balanced cutoff (about 200 bytes) was clearly worse than the byte-balanced 1930 bytes (Fig. 18).
- **Few priority levels suffice.** Four were nearly as good as eight (§5.1). Budget hardware queues (switch priorities, NIC queues, GPU stream priorities) with that in mind.
- **Plan for SRPT starvation from day one.** Large transfers, such as checkpoints or weight loads, need an aging or reserved-bandwidth escape hatch.
- **Keep the NIC queue short.** Holding at most about two packets in the NIC (§4) preserves the sender's ability to reorder. Deep device queues silently defeat software priorities.
