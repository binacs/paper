# Analysis of Large-Scale Multi-Tenant GPU Clusters for DNN Training Workloads

> **Why it matters:** The Philly study was an early public, log-correlated characterisation of a production multi-tenant DNN training cluster. It showed that gang scheduling plus locality drives queueing, that locality and colocation drive GPU utilisation, and that most failures are cheap user errors. Its released trace became a standard input for GPU-scheduler research.

*Numbers below are from the USENIX ATC'19 camera-ready (pp. 947–960). Where arXiv v1 differs, this is noted. arXiv v2 was not compared.*

## Problem

Enterprise DNN training runs on shared GPU clusters. Two properties of this workload break assumptions inherited from big-data schedulers:

1. GPUs are a monolithic resource that is not shared at fine grain across users.
2. Distributed training frameworks need **gang scheduling**: all of a job's GPUs must be allocated together. This makes jobs rigid and vulnerable to any runtime failure.

The paper asks how these properties, combined with locality-aware placement, affect queueing delay, GPU utilisation and job completion in Microsoft's Philly cluster. It then turns the answers into guidelines for next-generation schedulers.

## Core design

A measurement study: the "design" is the cluster and scheduler under study plus the analysis method.

### Cluster and scheduler (§2.2–2.4, Fig. 1, Table 1)
- Hundreds of machines, thousands of GPUs of one model; two SKUs (2 or 8 GPUs/server). Each rack is an RDMA domain (100 Gbps InfiniBand); cross-rack is Ethernet. One Docker container per machine per job; HDFS storage.
- YARN Fair Scheduler; each team owns a **virtual cluster (VC)** with a GPU quota and queue. Fair-share preemption across VCs starts only at 90% GPU occupancy. CPU/memory are allocated in proportion to requested GPUs.
- **Locality policy:** a gang first waits for a tight placement (fewest servers, one RDMA domain); after a 2–3 min timeout it backs off 2 min and retries; after a fixed retry count the constraint is relaxed and the job may spread across servers/racks.
- Outcomes: *passed*, *killed* (by the user), *unsuccessful* (failed after the fixed number of retries). Table 1 contrasts Philly ("consolidation", "locality-based") with Gandiva, Optimus and Tiresias.

### Trace and method (§2.4, §4.2)
- 75 days (Oct–Dec 2017), 96,260 jobs, 14 VCs, hundreds of users.
- Per-job join of YARN logs (arrival, GPUs requested, allocation, status), framework stdout/stderr (loss curves, errors) and per-minute Ganglia server stats (CPU, memory, network, GPU). Failures are tagged by a classifier of 230+ rules.

### Finding 1: gang scheduling plus locality causes queueing (§3.1)
- Delay is split into **fair-share** (VC over quota) and **fragmentation** (quota allows it, but no locality-satisfying gang of free GPUs exists). Fragmentation dominates and grows with job size (Table 2); preemption fixes fair-share delay but not fragmentation.
- Even at two-thirds occupancy, fewer than 4.5% of servers are fully empty, scattered across RDMA domains.
- Relaxing locality shortens waits: >8-GPU jobs placed on 16 servers start much sooner than ones packed onto 2–4 (Fig. 4, VC2).
- Out-of-order scheduling (small jobs overtaking waiting gangs) is common and mostly fills idle GPUs without delaying the waiting jobs (§3.1.1).

### Finding 2: locality and colocation drive utilisation (§3.2)
- In-use GPUs average ~52% utilisation, lowest for 16-GPU jobs (Table 3); spreading a 16-GPU job over more servers lowers it monotonically (Table 5).
- A controlled 2-GPU ResNet-50 experiment (P100, TensorFlow; Table 4) separates **locality** (SameServer vs DiffServer, −8.1 points) from **interference** relative to DiffServer: sharing server and CPU socket (IntraServer, −12.1) or the RDMA network (InterServer, −13.1). Interference costs more than losing locality.
- Many servers leave CPU idle while memory runs hot, which the paper ties to GPU-proportional allocation (Fig. 7).

### Finding 3: failures and their causes (§4)
- Killed plus unsuccessful jobs are 30.7% of jobs but ~55% of GPU time (Table 6).
- Classes are Infrastructure, AI Engine and User (overlapping). User/programming errors dominate (incorrect inputs, semantic/syntax errors, CPU OOM) and repeat: 2.3× per job and 38.8× per user on average for the top-8 reasons (§4.2.2).
- User errors fail within minutes (low median runtime-to-failure, RTF). Checkpoint and MPI runtime failures have very long RTF and waste disproportionate GPU time (§4.2.3). Weighting by GPU demand raises semantic errors' cost, as large jobs fail later (§4.2.4).
- Most jobs come within 0.1% of their lowest loss long before they stop, an early-termination opportunity (§4.1).

### Design guidelines (§5)
1. **Prioritise locality.** Jobs last hours to days, so waiting longer for good placement, or migrating to it later, can pay off; a 10–20% efficiency drop can add hours. User expectations about waits must be managed.
2. **Mitigate interference.** Give small jobs dedicated servers; since that worsens fragmentation, use **job migration** to defragment.
3. **Improve failure handling.** Syntax checks before submission; pre-run the first iteration on a cheap VM pool or single GPU; dataset schema checks; online error classification so deterministic errors are not retried but transient ones (e.g. network timeouts) are.

## Limitations

- **Coverage of convergence data (paper):** loss curves were usable for only about 2,502 jobs, so the early-stopping finding comes from a subset (§4.1).
- **Classifier coverage (paper):** about 4.2% of failures have no matching signature. Failure classes overlap, so the paper gives no clean infrastructure-vs-user split (Table 7).
- **Single cluster, single GPU model (paper setting):** one 2017 Microsoft cluster with homogeneous GPUs. *Own analysis:* MLaaS in the Wild later showed that heterogeneous GPUs and CPU bottlenecks are first-order issues that this trace cannot show.
- **Workload era (own analysis):** the jobs are mostly sub-week and pre-LLM. In 2024-era LLM pre-training (Llama 3, Acme), hardware failures dominate. Philly's "user errors dominate, so pre-run cheaply" conclusion does not carry over to multi-thousand-GPU synchronous jobs.
- **Utilisation metric (own analysis):** "GPU utilisation" is a per-minute Ganglia sample, presumably the driver's busy-time metric rather than achieved FLOPs. A 52% figure can understate or overstate real efficiency.
- **Causality (own analysis):** the trace-level link between spread and low utilisation (Table 5) is correlational. Only the small 2-GPU ResNet-50 experiment (Table 4) isolates locality and interference, and it does not show how the effect scales to large gangs.
- **Guidelines not evaluated (own analysis):** §5's migration, pre-run and adaptive-retry proposals are not built or measured in this paper.

## Relation to other systems

The descriptions below come from each paper's own abstract unless noted.

- **Gandiva (OSDI 2018):** a scheduler that exploits intra-job predictability (repeated mini-batches) for GPU time-slicing and introspective migration. It claims up to 10x faster hyper-parameter search and 26% higher utilisation on a 180-GPU cluster. Philly supplies the production evidence (fragmentation, interference) for why migration matters. Gandiva is a mechanism paper; Philly is a measurement paper whose §5 calls for Gandiva-style migration.
- **Tiresias (NSDI 2019):** targets average JCT with 2D-Gittins / 2D-LAS scheduling under unknown job durations, and relaxes the consolidated-placement constraint when it is safe to. It reports up to 5.5x better JCT than a production YARN-based manager. Philly's paper is about utilisation and failures, and its §5 argues for waiting *longer* for locality. That stance contrasts with Tiresias selectively *relaxing* consolidation, so the two look at the locality trade-off from opposite sides.
- **MLaaS in the Wild (NSDI 2022):** a two-month trace from Alibaba's 6,000+ GPU heterogeneous cluster. It re-finds low utilisation and long queueing, and adds picky high-end-GPU tasks, imbalance across GPU types and CPU bottlenecks. That extends Philly's homogeneous single-model view; its CPU finding echoes Philly's own CPU/memory observation in §3.2.
- **Acme (NSDI 2024):** a six-month trace of LLM development from the Acme GPU datacenter. Its abstract stresses frequent hardware failures and complex parallelism. It builds LLM-assisted failure diagnosis with automatic recovery, plus decoupled scheduling for evaluation jobs. This is Philly's failure-handling guideline updated for LLMs, but the dominant failure source has moved from user code to hardware.
- **Llama 3 (arXiv 2024):** the abstract does not cover infrastructure. The following is from §3.3.4, "Reliability and Operational Challenges". Over a 54-day snapshot of 405B pre-training on up to 16K H100s there were 466 interruptions, 419 of them unexpected, and about 78% of the unexpected ones were attributed to confirmed or suspected hardware issues. Effective training time stayed above 90%. Compared with Philly, where failures are mostly early user errors, this is the same "failures waste gang-scheduled GPU time" theme. The fix shifts toward fast detection and restart, and away from pre-submission checks.

## Takeaways for practice

- Measure **fragmentation delay separately** from quota delay. Preemption fixes the latter but not the former, and fragmentation dominates for large gangs.
- Treat locality as a **cost model, not a timeout**. A fixed 2–3 minute relax-and-retry is cheap for queueing but can cost hours of runtime for long jobs. Weigh expected runtime against expected wait, or schedule loosely and migrate later.
- Treat **colocation interference** (PCIe, CPU socket, shared RDMA) as at least as costly as the locality loss (Table 4). Isolate small jobs or use interference-aware packing, and budget migration to undo the fragmentation that isolation causes.
- **Allocate CPU and memory by profile**, not in proportion to GPUs. Philly's servers ran memory hot while CPU sat idle.
- Put a **cheap gate before the gang**: syntax checks, a dataset schema check and a one-iteration dry run on a single GPU. Classify errors online so deterministic failures are not blindly retried.
- **Long-RTF infrastructure failures** (checkpoint, MPI) are rare but expensive. Checkpoint frequency and health checks matter more as job size grows; LLM-era traces make this the dominant concern.
- Expose **early-stopping signals**. Much GPU time goes to the last 0.1% of loss improvement.
