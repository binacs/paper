# Pollux: Co-adaptive Cluster Scheduling for Goodput-Optimized Deep Learning

> **Why it matters:** Pollux showed that a DL scheduler should not treat batch size and learning rate as user-fixed inputs: co-tuning them with the GPU allocation against a "goodput" objective (throughput × statistical efficiency) beats schedulers that only resize jobs (OSDI 2021 Best Paper).

## Problem

Users pick GPU count, batch size and learning rate up front, usually without the expertise to choose well (§1, §2.2). The choices interact: more GPUs only help if the batch grows, and a larger batch raises throughput but lowers statistical efficiency (progress per example), by an amount that changes during training. Existing schedulers either take a fixed GPU count (Tiresias, Gandiva) or adapt the GPU count while ignoring statistical efficiency (Optimus, SLAQ, Gavel, AntMan, Themis) (§2.3). Pollux minimises average job completion time (JCT), with tunable fairness, by optimising allocation and training configuration together.

## Core design

### Goodput metric (§3)

- Configuration Θ = (a, m, s): a is the per-node GPU allocation vector, m the per-GPU batch size and s the number of gradient-accumulation steps. The total batch is M = ΣA·m·(s+1).
- GOODPUT_t(Θ) = THROUGHPUT(Θ) × EFFICIENCY_t(M(Θ)) (Def. 3.1, Eq. 4): "the portion of the throughput that is useful for training progress."
- **Statistical efficiency** (Eq. 6): EFFICIENCY_t(M) = (φ_t + M0) / (φ_t + M), measured relative to the user's initial batch size M0. φ_t is the *preconditioned gradient noise scale* (PGNS), tr(PΣPᵀ)/|Pg|² (Eq. 5). For plain SGD the PGNS equals the gradient noise scale, and the preconditioner P extends the estimate to Adam-like optimisers. φ_t usually grows as training goes on, so large batches become cheaper in efficiency later in training.
- φ_t is estimated online from per-GPU gradients, or from consecutive gradients (a differenced estimator) when there is one GPU and no accumulation (§3.1). The application may cap the batch size. The paper reports that batches up to 32× larger than M0 work well in most cases (§3.1).
- **Throughput model** (§3.2, Eqs. 7–11): THROUGHPUT = M / T_iter. T_grad(m) = α_grad + β_grad·m. T_sync is piecewise linear in K = ΣA, with separate (α, β) for a single node and for multiple nodes, and is 0 when K = 1. Compute/communication overlap is modelled as T_iter = (T_grad^γ + T_sync^γ)^(1/γ) with γ ≥ 1, plus s·T_grad for accumulation steps. That gives seven parameters per job.
- **Learning-rate plug-in:** SCALE_LR(M0, M) runs before every update. Supported rules are AdaScale, square-root scaling, linear scaling and LEGW (§3).

### PolluxAgent: per-job loop (§4.1)

- Runs inside each job. It records (a, m, s, T_iter) tuples and gradient statistics, and fits the seven throughput parameters by minimising RMSLE with L-BFGS-B, with α, β ≥ 0 and γ ∈ [1, 10].
- **Prior-driven exploration:** parameters for regimes the job has not yet seen (multi-GPU, multi-node) are set to 0, so a new job is assumed to scale perfectly. The scheduler is not allowed to give a job more than 2× the largest GPU count it has received so far. This lets the model learn as the allocation grows.
- **Batch-size choice** (Eq. 13): for the current allocation a, pick (m*, s*) = argmax GOODPUT(a, m, s). In practice it samples candidate total batch sizes and uses the smallest s that fits in GPU memory. The learning rate follows through the plug-in rule (for example AdaScale for SGD, square-root scaling for Adam).
- The agent reports its fitted model and φ_t to the scheduler every 30 s (§5.1).

### PolluxSched: cluster-wide loop (§4.2–4.3)

- **Speedup** (Eq. 15): SPEEDUP_j(A_j) = max_{m,s} GOODPUT_j(A_j, m, s) / max_{m,s} GOODPUT_j(a_f, m, s), where a_f is a fair exclusive 1/J share of the cluster. Because each job's agent supplies its goodput function, the scheduler can evaluate an allocation's value assuming the agent will re-tune batch size and learning rate for it.
- **Fitness** (Eq. 14): FITNESS_p(A) = ((1/J) Σ_j SPEEDUP_j(A_j)^p)^(1/p), a power mean over running and pending jobs. p = 1 favours well-scaling jobs; p → −∞ approaches max-min fairness; default p = −1.
- **Re-allocation penalty:** each speedup is multiplied by REALLOC_FACTOR_j(δ) = (T_j − R_j·δ)/(T_j + δ). Here T_j is the job's age, R_j its number of past re-allocations and δ the estimated restart delay (30 s in the experiments, against measured checkpoint-restart delays of 15–120 s). Jobs that are restarted often become expensive to move again.
- **Search:** a population-based search "that perturbs and combines candidate allocation matrices" (§4.3). In effect it is a genetic algorithm, and the Sia paper calls it one. Each candidate is repaired to satisfy node capacity and interference constraints, and the fittest matrix is applied. The paper does not specify operators, population size or number of generations.
- **Interference avoidance:** at most one distributed (multi-node) job per node, enforced as a search constraint (§4.2).
- **Mechanics:** a Kubernetes service runs every 60 s. Allocations are applied by creating and deleting pods, with checkpoint-restart to CephFS. PolluxAgent is integrated with PyTorch (§4.3, §5.1).
- **Cluster auto-scaling (§5.4.1, preliminary):** add nodes while goodput per GPU stays above U = 2/3 of the ideal single-GPU goodput, targeting about L = 1/2.

## Limitations

- **Homogeneous GPUs only.** The throughput model does not cover accelerator heterogeneity (§2.3). Sia later argues that the "no-pre-profiling" learn-by-scaling-up model is what prevents Pollux from handling GPU types.
- **Data parallelism only.** The model assumes synchronous data-parallel all-reduce with linear compute and communication costs. The authors note it may not hold for other parallelism strategies, specialised interconnects or larger scales (§3.2). Pipeline, tensor and hybrid-parallel jobs, the norm for LLM training, are not modelled.
- **Search scalability.** The search space grows with node count and GPUs per node. Sia reports the genetic algorithm takes tens of minutes at 1000+ GPUs and has no optimality guarantee. Pollux was evaluated on 64 GPUs.
- **Checkpoint-restart elasticity.** Each re-allocation costs 15–120 s; the ~8% overhead will grow with checkpoint size.
- **Semantics change for users.** Changing batch size and learning rate mid-training relies on scaling rules preserving model quality; the paper concedes large-batch generalisation is "not completely understood" (§2.2). Jobs needing reproducibility or hand-tuned schedules may object.
- **Biased baselines in both directions.** The tuned baselines are "unrealistically biased" in their favour, and the realistic ones favour Pollux (§5.1). The 37–50% headline uses the tuned baselines.
- The fairness knob p is left to the operator. The auto-scaling and HPO results are preliminary (§5.4).

## Relation to other systems

- **Optimus (EuroSys 2018):** fits per-job throughput and convergence models online and allocates resources greedily by marginal gain to cut JCT. Pollux keeps the online throughput modelling (its Optimus+Oracle baseline reuses Pollux's throughput model and is told exact remaining iterations) but adds statistical efficiency and per-job batch-size retuning. That is where most of the gain comes from.
- **Tiresias (NSDI 2019):** works without knowing job durations, using discretised multi-level priority queues (least attained service) over fixed GPU-count jobs. Pollux instead treats the GPU count as a variable, and its fitness function replaces queue priority with goodput speedup.
- **Gandiva (OSDI 2018):** also takes the GPU count as given but improves utilisation with fine-grained time slicing, migration and introspection (§2.3). Pollux re-allocates at 60 s granularity through checkpoint-restart, not GPU time-sharing, and avoids co-locating distributed jobs instead of exploiting sharing.
- **Gavel (OSDI 2020):** makes scheduling policies heterogeneity-aware through a throughput metric that is comparable across accelerator types (§2.3). It adapts placement but is agnostic to statistical efficiency and leaves batch size alone. Pollux has the opposite profile: goodput-aware but homogeneous-only.
- **Sia (SOSP 2023, same CMU group, Pollux first author among co-authors):** combines the two. It keeps goodput-optimised adaptive jobs, adds heterogeneous GPU types and hybrid-parallel elastic jobs, bootstraps per-GPU-type throughput models with little profiling, and replaces the genetic algorithm with an ILP (GLPK_MI via CVXPY). It reports 35% lower average JCT than Pollux on a 44-GPU heterogeneous cluster, parity on homogeneous clusters (2.0 h vs 1.9 h avg JCT), and a solver about 100× faster at scale, up to 2048 GPUs.

## Takeaways for practice

- Optimise **goodput, not throughput**. A scheduler that scales a job out without changing its batch size wastes GPUs, and one that scales the batch without regard to the gradient noise scale wastes samples. Gradient noise scale is cheap to estimate online from gradients that are already computed.
- **Split model ownership.** The per-job agent learns its own seven-parameter throughput model and φ_t and exports a goodput function. The central scheduler only compares speedups. This keeps the scheduler model-agnostic and lets it evaluate hypothetical allocations.
- **Optimistic priors plus a capped growth rate** (at most 2× the largest GPU count seen so far) give a safe exploration scheme for learning scaling curves without pre-profiling.
- **Put fairness in the objective.** A power mean over per-job speedups (p = −1) gave the best average JCT with good finish-time fairness. It is simpler to reason about than separate fairness queues.
- **Charge for churn.** The age- and history-based re-allocation penalty cheaply stops an elastic scheduler from thrashing.
- **Plan for scale and heterogeneity.** Heuristic search over full allocation matrices works at 64 GPUs, not thousands; Sia's ILP over (job, GPU type, count) shows a restructured search.
