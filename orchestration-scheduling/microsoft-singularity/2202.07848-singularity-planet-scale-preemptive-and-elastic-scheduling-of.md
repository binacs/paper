# Singularity: Planet-Scale, Preemptive and Elastic Scheduling of AI Workloads

> **Why it matters:** It shows that preemption, cross-region migration and resizing can be offered to *every* unmodified DL job by interposing at the CUDA/NCCL boundary, which lets a scheduler treat a global GPU fleet as one cluster with tiered SLAs instead of static reservations.

## Problem

Microsoft wants to run training and inference across a global fleet of "hundreds of thousands of GPUs and other AI accelerators" (§1) as one logical shared pool, with no idle capacity, no static reservations, and job-level SLAs (§1.1). Policy papers (Tiresias, Themis, Gavel, Pollux, Optimus) assume jobs can be checkpointed, preempted or resized, but in practice that needs framework changes (Gandiva), elastic training loops (PyTorch Elastic, DeepSpeed), or epoch-level restarts that lose work (§8). Singularity's claim is that the mechanism layer has to be **transparent** and **work-conserving**: no user code changes, no custom library, and the job resumes from the exact program state where it was preempted, across nodes, clusters or regions (§1.2, §2.2).

## Core design

### Device proxy (§3, Fig. 2)
- An `LD_PRELOAD` client in each worker intercepts accelerator APIs at the low-level driver/launch layer (e.g. `cudaLaunchKernel`), so any library that eventually launches kernels is covered (§3.1). Stubs are generated automatically from library headers.
- Calls go over lock-free shared-memory channels to a **device-proxy server** in a separate address space, one per device (§3). This keeps GPU mappings out of the worker process, so stock **CRIU** can checkpoint the host side, and it lets several workers share one GPU through one proxy (time-slicing).
- Two kinds of interceptor: *dispatch interceptors* (DInt) only serialize and forward; *semantics-aware interceptors* (SAInt) implement barriers, memory management, collectives wrapping and time-slicing (§3). The proxy owns allocation, wraps NCCL/RCCL, handles device synchronization, and virtualizes stream/context/event handles so they can be logged and replayed after restore (§3.2, §4.2.1). Libc file APIs are also intercepted to log writable files that must travel with the checkpoint (§3.3, §4.4).
- Most SAInt logic sits on a hardware abstraction layer; the implementation targets NVIDIA GPUs (§3.2).

### Consistent checkpoint via a semantics-aware barrier (§4)
- The hazard: if one rank is frozen after its n-th allreduce while another has issued its (n+1)-th, the job deadlocks. All ranks must stop after the same set of collectives (§4.3).
- No out-of-band channel (TCP, storage) is used, to avoid new failure modes. Instead, an asynchronous **tandem meta-allreduce** is issued before every data allreduce on the job's own communicator, carrying two summed integers: `need_barrier` (some rank got a barrier request → enter Phase 2) and `ack_barrier` (sum = world size → barrier acquired). In Phase 2 collectives become synchronous so the protocol finishes quickly; it is "guaranteed to complete within at most two mini-batches" (§4.3.1).
- For tensor/pipeline-parallel jobs, the barrier is taken only at mini-batch boundaries, when nothing is in flight: a few seconds of extra delay, but a smaller checkpoint (§4.3.1).
- Checkpoint contents: CRIU dump of the host process, plus only the **live** GPU buffers (the proxy knows what is allocated). The proxy reserves all GPU memory at start-up and maps allocations so that device addresses are reproduced on restore, keeping host-held pointers valid (§4.2). The proxy itself is stateless: on the destination it is respawned, replays logged state-changing calls, restores tensors at their original addresses, and the job does a fresh rendezvous to rebuild the NCCL ring (§4.1, §4.5).
- Buffers are checksummed and uploaded once across workers; CRIU pages are content-deduplicated across time, so incremental dumps are small (§4.6). Periodic checkpoints at a user-specified interval ("e.g., every 30 minutes") cover unplanned failures (§4.5).

### Elasticity without changing world size: replica splicing (§5)
- The job's **logical world size stays fixed**; resizing changes only the rank→GPU mapping. Scale-down from 4 GPUs to 1 runs four ranks time-sliced on one device (§5, Fig. 3). Because the world size and hence the global batch do not change, the training semantics do not change either.
- Basic time-slicing (§5.1): one rank runs at a time; switches happen only around collectives. Ranks sharing a GPU accumulate gradients into proxy scratch buffers, and only the last local rank issues the real NCCL allreduce, so NCCL sees one rank per GPU.
- Naive swapping is too slow: swapping 32 GB out and in per mini-batch costs 2–4 s versus mini-batches of hundreds of ms (§5.2). Replica splicing exploits the fact that data-parallel replicas hold identical parameters and optimizer state after each step:
  - **Checksum-based swap elision**: skip swap-out/in when an identical buffer already exists on host/device, or do a device-to-device move if only the address differs.
  - **Bidirectional allocator**: stable buffers (parameters, optimizer state, recognized by allocation stack trace) go to the top of the address space, transient ones to the bottom, so stable buffers keep the same addresses across ranks. Mislabelling only costs performance.
  - **Squashing**: optimizer-step kernels run on one root rank per device; others skip them. Squashing is validated on the first mini-batch and periodically by checking buffer mutations and D2H copies match across ranks; on mismatch it is disabled (§5.2.1–5.2.3).
  - A guardrail disables time-slicing for a model if overhead exceeds about 5% of mini-batch time (§5.2.3).
- Model parallelism (§5.3): only data-parallel replicas of the same partition share a GPU. The proxy infers communicator roles by forcing a switch after each `ncclCommInitRank` and treating communicators seen more than once as data-parallel; Megatron/DeepSpeed rank layouts are mirrored, and custom launchers can supply a rank→topology map. ZeRO needs a small change decoupling the sharding factor from the DP degree ("around 30 lines of Python", §5.4).

### Scheduler and SLAs (§1, §2.5, Fig. 1, Table 1)
- Hierarchical scheduling with global, regional and workload-scope micro-services (Fig. 1); the paper gives little detail on the policies themselves.
- SLA metric is **GPU fraction** = T_ideal / T_real, enforced hourly. Illustrative tiers (Table 1): Premium 95% (almost never preempted), Standard 70% (infrequent), Basic best-effort like spot VMs. Jobs request a soft quota, may get more or less, and pay for use (§2.5). Training is scaled down or preempted when inference load rises (§1.1).

## Limitations

- **arXiv preprint only**; no peer-reviewed version found. The evaluation uses V100s, PyTorch 1.6–1.8 and CUDA 10.1–11.1 (§7.5), i.e. small models by today's standards. The largest model is 8B parameters on 32 GPUs; there are no results at thousands of GPUs.
- **Migration is store-and-forward through blob storage**; transfer dominates latency (Table 5), and P2P InfiniBand transfer is future work. Migration times of minutes for an 8B model would grow with modern model and optimizer-state sizes.
- **Model-parallel barrier waits for a mini-batch boundary**, and in-flight collectives cannot be captured because the collective library is treated as a black box (§4.3.1).
- **Fragility of interposition**: driver-level interception has to track CUDA/NCCL APIs, JIT kernels (parameters recovered via cuobjdump/PTX parsing, §6) and new hardware features. Portability is claimed as "negligible" effort only across the versions tested (§7.5). Non-NVIDIA accelerators are designed for but not shown.
- **Replica splicing relies on DP replica identity**, and squashing must be validated and may turn itself off.
- **Scheduler policy is under-specified**: placement and victim selection across regions are described only at a high level. Inference is a stated goal but is not evaluated.

## Relation to other systems

- **Gandiva (OSDI'18)**: same group lineage. Gandiva used DL's mini-batch predictability for GPU time-slicing and migration, but needed framework modifications (§8). Singularity moves the mechanism below the framework into a device proxy and adds cross-region migration and SLA tiers.
- **MAST (OSDI'24, Meta)**: also a global, cross-region training scheduler, but it decides where to place data and jobs at submission time (temporal/scope decoupling, exhaustive search). Singularity's distinguishing bet is runtime mobility: jobs are preempted and moved after they start.
- **Twine (OSDI'20, Meta)**: one control plane per region managing up to a million machines, with application-specific lifecycle hooks (TaskControl). Twine relies on application cooperation for safe preemption and moves; Singularity makes preemption transparent for GPU jobs instead.
- **Oobleck (SOSP'23) / ByteCheckpoint (NSDI'25)**: framework-level fault tolerance. Oobleck reconfigures heterogeneous pipeline templates using in-memory replicas; ByteCheckpoint offers a parallelism-agnostic, reshardable checkpoint format with fast save/load. Both change the parallel configuration or world size and require framework integration. Singularity keeps world size fixed and checkpoints raw process plus device state. That makes it transparent, but checkpoints are not reshardable and are tied to the same rank layout.
- **Kubernetes / Kueue preemption**: Kueue evicts lower-priority or over-quota workloads within a ClusterQueue or cohort (fair sharing, borrowing). Eviction there means losing work unless the job checkpoints itself. Singularity's tiers look similar on the policy side, but its preemption is work-conserving, and it can resize instead of evicting.

## Takeaways for practice

- Put the mobility mechanism at the narrowest stable interface (driver launch, allocator, collectives) and keep the proxy stateless and replayable. That makes stock CRIU usable for the host side.
- A consistent cut can piggyback on the job's own collectives (a tiny asynchronous meta-allreduce), which avoids new control-plane dependencies.
- Owning the GPU allocator pays off several times: live-buffer-only checkpoints, deterministic addresses on restore, and stable/transient segregation for dedup.
- Holding world size fixed while remapping ranks to GPUs is a clean way to offer elasticity without touching hyperparameters. Its cost is set by how much state is not identical across replicas, so measure and gate it (Singularity uses a 5% cutoff).
- An SLA expressed as a GPU-time fraction (T_ideal/T_real) lets the scheduler preempt and shrink jobs while keeping a contract users can reason about.
- Budget for checkpoint transfer bandwidth. With blob-staged migration, transfer is most of the latency, and with today's model sizes P2P or tiered in-memory checkpointing is required.
